# hammerola — техническое задание

Витрина 3D-моделей: хаб, который принимает по HTTP ИСХОДНИК CadQuery-проекта, сам
считает геометрию и раздаёт по каждому проекту свой веб-вьювер на публичном домене.
Один контейнер на все проекты; заведение нового проекта не требует никаких действий
снаружи каталога модели — только `hammerola commit` из него.

Документ начинался под именем `cad_snapshot_hub` и описывал хаб, который принимал
готовые артефакты сборки из Gitea Actions. Это состояние ДО переезда — см. врезку
выше и §8A.

Задача выросла из чата по `home-network` 21.08.2026. Всё, что помечено ниже как
проверенное, проверено эмпирически — командой, вывод которой приведён. Перепроверять
это не нужно, это уже стоило времени.

## 1. Пользовательский сценарий

**Сценарий A — автор модели.**

1. Автор делает подпапку в `~/Data/Projects/3d/<project>/`, заводит репозиторий в
   организации `3d` в Gitea, пишет модель на CadQuery.
2. `git push` в `main`.
3. Gitea Actions: собирает модель, проверяет геометрию, экспортирует тесселяцию и
   файлы для печати, пушит артефакты в хаб.
4. Через минуту `https://<хаб>/project/<pid>/latest/` показывает текущее
   состояние модели.

**Сценарий B — тот, кому кинули ссылку.**

1. Открывает `https://<хаб>/project/<pid>/<commit>/`.
2. Видит модель: крутит, зумит, выключает отдельные детали, режет плоскостью,
   разносит сборку.
3. Жмёт STL / STEP / 3MF — получает файлы **той самой** сборки, которую видит на
   экране, а не «последней».
4. Ссылка показывает то же самое и через год: сборка по коммиту неизменяема.

**Сценарий C — обзор.**

1. Открывает `https://<хаб>/` — индекс всех проектов карточками: заголовок,
   короткий sha последней сборки, дата, число деталей, вес.

## 2. Внешние интерфейсы и факты (проверено эмпирически)

### 2.1 CadQuery: что умеет экспортировать

Версии, на которых проверено всё в этом разделе (`importlib.metadata.version`):

```
cadquery       2.8.0
cadquery-ocp   7.9.3.1.1
ocp_vscode     4.0.1
ocp-tessellate 3.4.1
trimesh        4.12.2
build123d      NOT INSTALLED
```

**Вывод: стек фактически CadQuery, а не build123d.** Это важно: часть публичных
рецептов написана под build123d и здесь не применима как есть.

Реально проверенный экспорт (тестовая коробка 20×10×5 со скруглением):

```
glb   OK     20596 bytes      step  OK     33721 bytes
gltf  OK      4381 bytes      stl   OK     26284 bytes
vrml  OK     17557 bytes      3mf   FAIL  ValueError: Unknown extension
```

Актуальный (не устаревший) API:

```python
a = cq.Assembly(part, name="part", color=cq.Color("steelblue"))
a.export(path, exportType="STEP"|"STL"|"GLTF"|"VRML"|"XML"|"XBF"|"VTKJS")
```

Точная сигнатура: `Assembly.export(self, path, exportType=None, mode='default',
tolerance=0.1, angularTolerance=0.1, unit='MM', outputUnit=None, **kwargs)`.

Две ловушки:

- `Assembly.save()` работает, но помечен `FutureWarning: save will be removed in the
  next release`. Использовать `.export()`.
- **3MF не берётся через `Assembly`** — расширение не распознаётся. Только через
  `exporters.export(shape, path, exportType=exporters.ExportTypes.THREEMF)` и только
  для `Workplane`/`Shape`, не для сборки. Проверено: 1239 bytes на той же коробке.

Полный список `exporters.ExportTypes`: `AMF, BIN, BREP, DXF, STEP, STL, SVG, THREEMF,
TJS, VRML, VTP`.

### 2.2 Вьювер: three-cad-viewer, тот же, что в OCP CAD Viewer

Главная находка разведки: **вьювер писать не надо**. Библиотека `three-cad-viewer`
(bernhard-42) — ровно тот рендерер, что внутри OCP CAD Viewer, и она лежит прямо
внутри пакета `ocp_vscode`:

```
<venv>/lib/python3.12/site-packages/ocp_vscode/static/js/three-cad-viewer.esm.js   3.57 MB
<venv>/lib/python3.12/site-packages/ocp_vscode/static/css/three-cad-viewer.css
```

Она полностью работает **статикой**, без вебсокета и без живого сервера. Данные для
неё генерирует `ocp_tessellate`:

```python
from ocp_tessellate.convert import export_three_cad_viewer_js

export_three_cad_viewer_js(
    None,                       # var=None → в файл пишется ГОЛЫЙ JSON,
                                # а не `var shapes = {...}` — это ключевой момент
    *objs, names=[...], colors=[...], alphas=[...],
    filename="assembled.json",
)
```

Страница поднимает вьювер так (проверено, рендерит реальную модель):

```js
import { Viewer, Display } from "/_v/three-cad-viewer.esm.js";
const shapes  = await (await fetch("./assembled.json")).json();
const display = new Display(box, displayOptions);
const viewer  = new Viewer(display, displayOptions, () => {}, null);
viewer.render(shapes, renderOptions, viewerOptions);
```

Что сохраняется по сравнению с GLB: дерево деталей с именами и цветами, поштучное
включение/выключение, изометрические виды, clip-плоскости, explode, рёбра. В GLB всё
это схлопнулось бы в один безымянный меш.

**Иконки тулбара — инлайновые data-URI прямо в CSS** (проверено: ноль внешних `url()`
кроме `data:`). Никаких дополнительных ассетов копировать не нужно, хватает двух
файлов выше.

### 2.4 Уже существующая практика в проектах моделей

В `~/Data/Projects/fusion/` лежит `VIEWER.md` и в каждом проекте — самодостаточный
`show_in_viewer.py`, который уже делает **ровно тесселяцию**, только пушит её в
вебсокет живого OCP CAD Viewer'а. Переезд на публикацию — это смена приёмника, а не
новый код: у него уже есть `load_model()` (исполняет модель без её side-effects) и
`collect(ns, layout)`, возвращающий `(objs, names, colors, alphas)` для вида
`assembled` / `print`.

Отсюда формат: **сборка содержит список видов, а не одну модель.** У T13 их два и оба
осмысленны. Для проекта с одной деталью список из одного элемента.

Известная ловушка оттуда же (задокументирована в их `VIEWER.md` и в коде): `show()` из
`ocp_vscode` после меша шлёт `send_backend(...)` и ждёт `ws.recv()` **без таймаута**;
подтверждение присылает только backend расширения VS Code, поэтому со standalone-вьювером
скрипт виснет навсегда с уже нарисованной моделью. Лечится
`importlib.import_module("ocp_vscode.show").send_backend = lambda *a, **kw: None`.
К нашему пути это не относится (мы не используем `show()`), но при переносе кода из
`show_in_viewer.py` этот патч тащить не надо.

### 2.5 Gitea: что можно и чего нельзя

Проверено curl-ом против Gitea:

```
GET /api/v1/packages/projects?limit=3
    → 401 {"message":"token is required"}          # ЛИСТИНГ ТРЕБУЕТ ТОКЕН ДАЖЕ ДЛЯ ПУБЛИЧНЫХ

GET /api/packages/projects/generic/nonexistent/latest/x.bin
    → 404                                          # не 401 → СКАЧИВАНИЕ анонимно разрешено

GET ... с Origin: https://example.com
    → в ответе НЕТ ни одного заголовка Access-Control-*
```

Три вывода:

- generic-пакеты **читаются анонимно**, если владелец публичный;
- **перечислить** пакеты без токена нельзя — автодискавери проектов через Gitea API
  требует PAT на стороне хаба;
- **CORS не настроен**, поэтому страница хаба не может фетчить модель напрямую из
  Gitea. Любой путь через Gitea требует серверного проксирования. Это одна из причин
  отказа от варианта «хаб тянет из реестра».

### 2.6 Почему адресация путём, а не поддоменом

Проект адресуется путём — `<хост>/project/<pid>/`, — а не собственным поддоменом.

Причина в стоимости заведения нового проекта. Поддомен на проект стоит отдельной записи
в имени и отдельного сертификата НА КАЖДЫЙ проект, и вайлдкардом это не спасается:
вайлдкард матчит ровно один лейбл, поэтому `<проект>.<хаб>` им уже не накрывается. Путь
не стоит ничего — сколько бы проектов ни завелось, имя одно и сертификат один.

Отсюда же следует схема URL целиком (раздел 3) и её кэширование (3.2).

Само размещение в требования не входит: под каким именем сервис отвечает и как туда
попадает — вопрос выката, а не этого документа.

## 3. Схема URL

Живой список маршрутов — докстринг `src/app.py`: он стоит рядом с диспетчером и
правится вместе с ним. Здесь он больше не повторяется. Копия, которая тут стояла,
успела разойтись с кодом на тринадцать маршрутов — всё семейство
`/api/v1/proposals/`, переименование и удаление проекта, чтение и разрешение
комментариев, исходники ревизии — и заодно обещала редирект там, где хаб отдаёт
HTML-резолвер. Это и есть причина, по которой её тут нет.

Схема адресации, которую объясняет остаток раздела: проект — `/project/<pid>/`,
сборка — сегмент под ним (`latest`, `dev` или имя ревизии), вид — `?v=<view>`,
документ поверх модели — `?d=<id>`, кадр камеры — `?c=<11 чисел>`,
сравнение пары — `/project/<pid>/<a>/compare/<b>/`, приём и задачи — под
`/api/v1/`. Что из этого публично, а что под `EDIT_TOKEN` — §7.4 и §5.4.

`c=` — позиция x,y,z, кватернион x,y,z,w, точка, на которую смотрит камера,
x,y,z и зум через запятую, округлённые (`encodeCamera` в `ui/src/hub.js`).
Страница модели держит его в адресной строке: камера постояла 400 мс — адрес
переписан `replaceState`, без новой записи в истории; после Fit — тоже. После
свежей отрисовки (первая загрузка, другая вкладка вида, сцена сравнения)
переписываются и `c=`, и `v=`, так что скопированный адрес называет вид на
экране, а не тот, с которым страницу открыли. Его несут адреса, которые страница
пишет сама (смена ревизии, сравнение), и ссылка окна «Поделиться». Адрес с `c=`
открывается с этого кадра один раз, при первой отрисовке (у ссылки на сравнение —
при отрисовке сцены сравнения); Fit возвращает к кадру, который подобрала
библиотека. Не разобралось ровно одиннадцать чисел — страница открывается так,
будто `c=` нет.


Сравнение (issue #10) — задача в той же очереди, что и сборка, и по той же
причине: считает его отдельный процесс с ядром OCCT внутри, а хаб раздаёт
страницы в своём. Обе ревизии уже собраны и опубликованы этим хабом, поэтому
провалившееся сравнение — это 500, а не 422: винить в нём нечего, кроме самого
хаба.

**У сравнения два ответа, и это не дублирование.** Без четвёртого сегмента
хранилища у ответа нет — **лог задачи и есть отчёт**, пофайлово: сколько
материала у каждой детали прибавилось и сколько убыло. Так спрашивает CLI
(`hammerola diff --material`), которому нечего рисовать. С четвёртым сегментом
задача дополнительно кладёт в кэш `scene.json` и `report.json` — геометрию
сцены и статус каждой детали, — потому что браузер не умеет получить вид иначе,
чем скачав его по адресу.

**Кэш сравнений лежит ВНЕ каталогов сборок:** `data/compare/<pid>/<a>/<b>/<view>/`.
Каталог сборки отдаётся с годовым `immutable`: JSON и PNG — анонимно, остальное —
по токену или ключу (§7.4); сравнение — вещь под токеном, но тоже с годовым кэшем,
потому что ОБА конца пары всегда коммиты. Кэш этот `private`, а не `public`, как и
у закрытых файлов сборки: токен едет в `X-Hammerola-Token`, а не в `Authorization`,
поэтому общий кэш не знает, что запрос был под паролем, и сохранить ответ ему мешает
только `private` — `public` здесь дал бы прокси держать сравнение год и отдать его
тому, кто токена не предъявлял.
Указатель (`latest`, `dev`) концом пары быть не может, и это отказ на всех
маршрутах: запись кэша лежит под теми именами, которыми её попросили, поэтому
запись под `latest` протухает в тот момент, когда указатель сдвинулся, — и
заголовком ответа такой файл не чинится. Клиент разрешает `latest` в коммит до
запроса (`builds.json` его и несёт), а у `dev` постоянного адреса нет вовсе,
так что локальный слот сравнить нельзя. Сама страница сравнения, как и страница
сборки, всегда `no-cache` (7.4). Каталоги вложены, а не склеены в одно имя
через разделитель: `SAFE_ID` разрешает `_`, поэтому у склейки
`<a>__<b>__<view>` пара `x` + `y__z` и пара `x__y` + `z` дают одно имя — и одно
сравнение получило бы чужую геометрию.

У ЧЕТВЁРТОГО СЕГМЕНТА СВОЁ ПРАВИЛО, `SAFE_VIEW_ID`, и оно шире, чем у трёх
первых: id вида валидируется на сборке по `MEMBER_RE` — точка в нём законна,
длина до 128, — так что держать его под `SAFE_ID` значило бы, что вид `top.v2`
публикуется и рисует вкладку, а сравнить его нельзя. Тест держит эти два
правила равными. Имя, которым сегмент назвать всё-таки нельзя, маршрут
отвергает 422 с объяснением, а не глухим 404: ограничение появилось здесь
впервые — раньше id вида никогда не был куском пути — и автор модели про него
ниоткуда не узнает.

Два **разных** идентификатора в пути, и это намеренно:

- `<pid>` — идентификатор **проекта**, живёт вечно;
- `<commit>` — идентификатор **сборки**, их накапливается много.

**Имя сборки чеканит хаб, а не пушер** — маршрут без последнего сегмента. Пушер
его и не знает: `hammerola commit` значит «опубликуй версию этого», а не
«опубликуй под таким-то именем», и к git имя отношения не имеет (§7.7). Отсутствие
сегмента — это и есть просьба назвать; правило «куда что ложится, решает URL, а не
тело» при этом не трогается. Маршрут с именем остаётся: под ним публикуют
репозитории моделей, у которых `publish.yml` ещё жив (§8A.2, шаг 7) — но клиент им
не пользуется и своего имени не выдумывает.

Третий идентификатор, `<id>` задачи сборки, в эту схему намеренно не встроен: он не
адресует ничего опубликованного — только ход одной сборки и то, что она напечатала, — и
он **непредсказуемый** — 16 байт из `secrets`, а не счётчик. Временным он при этом БЫТЬ
ПЕРЕСТАЛ: ретенции у задач нет (§7.3), лог сборки не подрезается и запись о ней с тома
сама не уходит, — то есть непредсказуемость больше не подпирается тем, что цель ссылки
рано или поздно исчезнет, и работать обязана сама по себе. Он появился вместе с
асинхронным приёмом (§8A.2, шаг 5) и он единственное, что отделяет лог сборки одного
пушера от лога другого: последовательный номер позволил бы вычитанием единицы
пройтись по логам всех чужих проектов, имея тот же самый `EDIT_TOKEN`.

### 3.1 Откуда берётся `<pid>` — и почему не из имени

Требование: ссылка не должна ломаться при переименовании проекта. Значит pid
**нельзя вычислять из имени** — иначе он меняется ровно тогда, когда должен был спасти
ссылку. Вычислять его не из чего, значит он должен храниться.

Решение: pid лежит **в самом репозитории проекта**, в `project.json`, генерируется
один раз при заведении проекта из шаблона:

```json
{
  "id":      "7f3c1a9e04d2",
  "project": "t13-ceiling-mount",
  "title":   "T13 ceiling mount (t13-ceiling-mount)"
}
```

Свойства: переживает переименование репозитория, переезд между организациями и смену
форжа; виден в репозитории, а не спрятан в чужой БД; CI его читает, а не вычисляет.
Цена — правило «руками не редактируем», и оно только про `id`. Два других ключа
редактируются: `title` переписывает `hammerola rename` (`project` при этом не
трогает), а `project` правится руками — и когда он в файле есть, только так слаг
и меняется: пишет его `hammerola create` один раз, и дальше его никто не
пересчитывает.

`project` — **латинское имя, под которым проект публикуется**: имя каталога автора и
его репозитория, оно же стоит в скобках титула. Пишет его `hammerola create` на
машине автора, и это единственное место, где на вопрос есть ответ: хаб распаковывает
пуш в каталог со своим собственным именем (`.src-<uuid4 hex>`), поэтому сборка,
вычислявшая имя сама, однажды вывела на главную карточку
`.src-89fb7abdeb1d48b5985bcb519850b284`. Ключа может не быть — тогда имя берётся из
скобок титула, а если и их нет, проект публикуется под своим `id`, и сборка пишет об
этом `warning:` в лог.

Правила два, и живут они в разных местах. Алфавит слага и разбор скобок — в
`hammerola/projectslug.py`: только он и есть общий, потому что его читают обе стороны
провода (клиент stdlib-only и импортировать сборочную половину не может). Сама ФОРМА
титула — «что это и зачем», потом слаг в скобках, и он же должен совпадать с именем
публикации — проверяется в `src/cadbuild/project_title.py` (`title_problem`), внутри
сборки и только предупреждением.

Отвергнуто: брать id репозитория из Gitea (`github.repository_id`) — привязка к форжу,
и наличие этого контекста в Gitea Actions не проверено.

### 3.2 Кэширование следует из схемы

- `/project/<pid>/<commit>/*` — неизменяемо по построению → `Cache-Control: immutable,
  max-age=31536000`. **Ровно одно исключение — поле `message` в `meta.json`** (issue
  #67): повторный пуш того же дерева не пересобирает ничего, но переписывает текст,
  которым ревизия себя называет. **Читателю это ничего не стоит, и это не совпадение:**
  ни одна страница не берёт `message` из `meta.json` — единственный, кто его оттуда
  читает, это сам хаб, когда собирает `builds.json` из каталога (`render._picker_entry`),
  а список отдаётся под `no-cache`. Устаревает, таким образом, поле в файле, который
  никто не рисует; переключатель ревизий всегда свежий. Кэш поэтому никто и не
  сбрасывает: вечный URL сборки — то, на чём держится вся схема, и на строку заголовка
  его не меняют. Геометрия, виды и файлы сборки неизменяемы без исключений.
- `/project/<pid>/latest/` и `/project/<pid>/dev/` — движущиеся имена, только они
  требуют `no-cache`
- `/_v/*` — общий бандл, один на весь сайт → тоже вечный кэш

`latest` реализуется **симлинком** на каталог коммита: не дублирует данные и, главное,
переключается атомарно — читатель никогда не увидит наполовину опубликованную сборку.
Публикация = «залить `<commit>/` целиком, потом перекинуть симлинк».

`dev` (§7.6) — не симлинк, а **сам каталог**: слот, который перезаписывает каждый
успешный пуш, и `build`, и `commit`. Общего у них ровно одно — `no-cache`, и для
`dev` это не оптимизация, а условие корректности: перезапись содержимого под одним
URL допустима **только** потому, что годовых кэшей на него никто не раздавал.

## 5. Подводные камни

### 5.1 Данные вьювера нельзя грузить как ES-модуль

Наступили в прототипе. Если подключить данные как
`<script type="module" src="model.js">`, где внутри `var shapes = {...}`, то `shapes`
**остаётся в области видимости модуля и в `window` не попадает**. Внешне это выглядит
как полностью исправный вьювер: рисуются вкладки Tree/Clip/Material/Studio, рамки
тулбара — но сцена пустая, и ошибок в консоли нет.

Поэтому: данные лежат отдельным `.json` и грузятся `fetch`-ем (`var=None` в
`export_three_cad_viewer_js`). Плюс страница обязана иметь **видимый блок ошибки** —
молчаливый провал здесь неотличим от пустой сцены.

### 5.2 Размер канваса брать из контейнера, а не из окна

Тоже наступили. Если считать высоту как `window.innerHeight - <константа>`, шапка
уезжает за экран, потому что угаданный отступ не совпадает с реальной высотой шапки.
Правильно: `body` — flex-колонка, шапка `flex: 0 0 auto`, обёртка вьювера
`flex: 1 1 auto; position: relative; overflow: hidden; min-height: 0`, а размеры брать
из `box.clientWidth` / `box.clientHeight`. `position`/`overflow` на обёртке нужны, чтобы
в режиме `glass: true` дерево и тулбар не вылезали поверх шапки.

### 5.3 Ретенции нет

Камень настоящий: каждая сборка — примерно 2 МБ на вид, и том растёт линейно от числа
пушей. **Решение 2026-08-27 — принять этот рост и не заводить механизма очистки вообще:**
ни у сборок, ни у задач, ни у локального слота, ни у комментариев. У комментариев
механизма не было и раньше — там стояли ПОТОЛКИ, отказывавшие в следующем вместо
удаления старого (§7A.4), что то же решение и та же цена, только в более жёсткой
форме: не «выбросим давнее», а «дальше нельзя», причём навсегда.

Довод — цена сторон, а не «место бесплатное». Десятки мегабайт на ревизию против
механизма, который надо написать, покрыть тестами, объяснять в документе и который умеет
удалить не то. Правило «держим последние N на проект» опирается на метку времени, которую
хаб ставит сам, на порядок создания, который после рестарта приходится восстанавливать, и
на исключение «а на что смотрит `latest`» — три места, где ошибка стоит безвозвратно
удалённой чужой работы, а выигрыш меряется гигабайтами на дешёвом томе. Размен не в пользу
механизма.

**Взамен появляется свойство, которого с ретенцией не бывает.** Сборка неизменяема,
`latest` всегда указывает на новейшую, и ничего не удаляется — значит ни одна ссылка,
розданная наружу с годовым `immutable` (§3.2), никогда не перестаёт разрешаться. Не «почти
никогда» и не «пока не выпала из окна»: никогда. Ровно ради этого обещания и построена вся
адресация в §3, и ретенция была единственным, что его подтачивало.

**Цена называется честно:** том растёт монотонно, и когда он однажды кончится, это будет
ручная работа — человек, разбирающий проекты, а не автоматика, срабатывающая по потолку.
Это принято сознательно: редкое ручное решение об удалении лучше частого
автоматического, которое некому проверить.

**Растёт том на то, что изменилось, а не на всё, что запушено.** После каждой публикации
хаб связывает жёсткими ссылками файлы сборок проекта с одинаковым sha256
(`Store._dedupe`, решение 2026-10-23 в §4): деталь, не менявшаяся между ревизиями, лежит
на диске один раз. Хеши своих файлов сборка хранит в `.files.sha256`; у сборки без этого
файла они считаются при первом проходе. Держится это на неизменяемости каталога сборки:
запись в опубликованный файл на месте попала бы во все связанные копии сразу. Поэтому
meta.json и dot-файлы, которые хаб пишет в сборку сам, не связываются никогда, копия в
слот `dev` делается копированием, а `tests/test_dedupe.py` прогоняет всё, что пишет в
проект после публикации, и сверяет каждый файл с его хешем.

### 5.4 Публичность

Домен наружу означает, что модели доступны всем, кто знает URL, а индекс на `/` делает
их ещё и перечислимыми. Выбор сделан сознательно (владелец выбрал «наружу, чтобы кидать
ссылку» + публичный индекс). Если появится проект, который нельзя показывать, — это
отдельная работа, а не флажок.

**Публичны СТРАНИЦЫ сборок и то, из чего браузер рисует модель, — не API и не
файлы деталей.** Всё, что под `/api/v1/`, требует `EDIT_TOKEN` (§7.5): публикация,
задачи сборки, исходники ревизии, маршруты переименования и удаления и вся очередь
комментариев вместе с записью в неё. Сборку по ссылке видно анонимно, и так и
задумано — ссылку кидают людям, а не раздают им секрет: страница, `meta.json`,
JSON-сетка каждого вида и PNG-картинки. Всё остальное, то есть STEP, STL и 3MF,
отдаётся только по `EDIT_TOKEN` или по ключу в ссылке (`?files=<ключ>`, §7.4); такую
ссылку выдаёт окно «Поделиться» владельца, если в нём поставить галочку «с файлами».
Исключение — перечисления: `/index.json` и `/project/<pid>/builds.json` под
`EDIT_TOKEN` (§7.4).

### 5.5 Мелочи, на которых уже споткнулись

- Шаблон `.code-workspace` из скилла содержит JSONC-шапку, а `wscolors.py` отказывается
  трогать файлы с комментариями. Шапку надо снять — сам шаблон об этом и пишет.
- В `home-network` шаблон проекта лежит в каталоге с **подчёркиванием**

## 7. Протокол приёма пуша

```
POST /api/v1/publish/<pid>            имя ревизии чеканит хаб (§7.7)
POST /api/v1/publish/<pid>/<commit>   имя приносит пушер
?force=1                              не вызывать checks() модели (issue #52)
X-Hammerola-Token: <EDIT_TOKEN>
Content-Type: application/gzip
<тело: gzip-сжатый tar>
```

`?force=1` — единственный параметр запроса на этом маршруте, и читается ровно
это написание; всё остальное в query игнорируется. Он меняет то, КАК идёт
сборка, и не входит в дайджест: те же исходники с флагом и без получают одно
имя, и повторный пуш отвечает 200 «unchanged» в обоих случаях. Гейты хаба —
провенанс, каталог, план печати, пересечения, пофайловые проверки экспорта —
под флагом работают как обычно; пропускается только `checks()` самой модели.

`pid` и `commit` берутся **из URL, а не из тела**: сервер — власть над тем, куда
что ложится. Токен сверяется `hmac.compare_digest`, не `==`. Отсутствие последнего
сегмента — не исключение из этого правила, а его частный случай: имени в запросе нет
вообще ни в URL, ни в теле, и хаб выводит его из содержимого сам (§7.7).

Архив — **дерево**, без ведущего каталога (§8A.2, шаг 2: сюда едет исходник модели, а
он деревом и является). Имя члена — относительный путь; правила имён и потолки — в
§7.1. Файлы, на которые `meta.json` ссылается — где бы ссылка ни стояла, — сверяются
**не с членами архива, а с тем, что записала сборка**: внутрь
едет исходник, а объявляет сборка свой собственный выход. `meta.json` пишет тоже
она — хаб его только перезаписывает после проверок, а сборку, которая его не
записала, отвергает 422-м (`Store._read_meta`). Лежать объявленное моделью обязано в
корне выходного каталога: там его ищут вьювер и `hammerola artifacts`. Глубже лежат
только документы — файлы, которые `project.json` перечисляет в `documents` (§7.1);
каждый публикуется под своим путём в дереве, и раздача отвечает по
`/project/<pid>/<commit>/<путь>` на любую глубину.

**Документы** (решение 2026-10-23, issue #122): `"documents": ["docs/cut-list.md",
"ref/terr-raspil.svg"]` в `project.json` — пути в дереве исходников, порядок —
порядок строк в списке видов. Расширение решает только, **как страница показывает**
файл (`render.DOCUMENT_TYPES`: `.md`, `.pdf`, `.png`, `.jpg`, `.jpeg`, `.gif`, `.webp`,
`.html`, `.htm`, `.svg`, `.kicad_sch`, `.kicad_pcb`, `.glb`, `.zip`); файл любого
другого расширения публикуется типом `file` (`render.FILE_TYPE`, решение 2026-10-25,
issue #125) — строка в списке видов остаётся, но вместо просмотра даёт скачивание, и
на странице модели такой файл стоит в меню Downloads группой своего расширения (DXF,
CSV) рядом с STL и герберами. Ничего не
находится по расширению: документ — то, что перечислено. Запись списка — путь или объект
`{"file": "ref/terr-raspil.svg", "title": "Схема распила", "hidden": true}`: `title` — подпись
документа в списке видов вместо пути (`meta.documents[].name`, правило как у названия
проекта), без него подписью остаётся путь; адрес, `id` и тип от подписи не зависят.
`"download": true` в записи публикует файл типом `file`, какое бы ни было расширение:
этим архив логов отличают от zip герберов, который страница распаковывает и рисует.
Схема или плата KiCad под `download` не тянет за собой ни листы, ни `.kicad_pro`:
рисовать из дизайна нечего. Ключ живёт только в `project.json`, в `meta.json` от него
остаётся разрешённый тип.
`hidden: true` (в `meta.json` поле есть, только когда оно истинно) оставляет документ
без строки в списке: он опубликован и открывается по `?d=<id>`, как любой другой, и
не бывает документом по умолчанию; если скрыты все, по умолчанию открывается
первый. Так к проекту прикладывают файлы, на которые только ссылаются (даташиты).
Хаб читает список сам, до сборки
(`src/docsbuild.py`), и что строить, решает по дереву: есть модель (`model.py` или
пакет `model/`) — модель строится как всегда, а после успешной сборки документы
копируются рядом и попадают в `meta.json` полем `documents`; модели нет, а список
есть — сборка из одних документов, без дочернего процесса, с `"kind": "documents"`
вместо `views` и `parts`; нет ни того, ни другого — сборка модели отвечает 422-м
«нет model.py и нет documents». Модель без списка публикует ровно то же, что до
документов. `id` документа — его путь, где `/` записан как `__` (`?d=docs__cut-list.md`
в адресе страницы); два пути с одним `id` (`a/b.md` и `a__b.md`) — 422. У сборки с
моделью документы — строки списка видов в плавающей панели внизу страницы, сразу
после видов: имя слева, тип и размер серым справа (у проекта KiCad подписи свои, см. ниже). Выбранный документ закрывает
область 3D, модель остаётся смонтированной под ним; дерево деталей прячется, панель и
шапка остаются; выбор вида возвращает модель. Панель внизу одна и та же везде
(`toolBar` в `ui/src/viewlist.jsx`, решение владельца, §4): список видов, Measure,
Comment, Add primitive, Fit, Frame, Settings — и на странице модели, и под документом,
и на странице сборки без модели. Кнопка, неприменимая к тому, что на экране, остаётся
на месте, но серая и нажатию не отвечает (`OFF` в `ui/src/panelstyle.js`): под
документом это четыре кнопки про модель, а Fit и Frame — пока вид документа не скажет
странице, что умеет их (`onTools`, `ui/src/DocumentView.jsx`). Умеют герберы, плата и
схема KiCad и 3D платы; текст, картинка, PDF и HTML — нет. Fit возвращает вид в кадр,
с которого он открылся, Frame сохраняет нарисованное как PNG с именем сборки, как у
модели. На узком окне панель, как и у модели, оставляет список и Fit.
Пока вид документа качает свой файл, на месте «Loading…» стоит `Loading… 2.1 / 40.7 MB`
(у файла меньше мегабайта — в `kB`) и тонкая полоса под ней, доля от поля `bytes`
документа в `meta.json`, а не от `Content-Length` сжатого прокси ответа
(`ui/src/loadbar.jsx`), с последнего байта до готового вида — полная полоса под
`Preparing…`; что на экране, качается первым: страница, открытая на документе (`?d=`),
отдаёт вьюпорту модель под ним только после того, как этот документ получил свой файл
или закрыт, а документ, открытый потом из списка, уже идущую загрузку модели не
останавливает; дизайн KiCad, открытый на 3D-виде, качает файлы схемы и платы после
`.glb` или сразу, как читатель перешёл на схему или плату.

`?d=<id>` при открытии страницы открывает документ, как `?v=`
открывает вид, и ссылка из окна «Поделиться» несёт `d=` открытого документа; выбор в
списке адрес не двигает. Markdown рисуется со своими относительными ссылками,
разрешёнными от его каталога в сборке; ссылка на другой перечисленный документ
(`[подрядчики](glass-vendors.md)`) открывает его на странице, как строка списка, а
её адрес — адрес страницы с `d=`, так что Ctrl-клик и скопированная ссылка ведут
туда же (`docLinks` в `ui/src/DocumentView.jsx`). Голый длинный адрес переносится
где угодно, чтобы не раздвигать страницу (`overflow-wrap:anywhere`). Сборка без модели — своя страница (`DocShell`): шапка,
документ на всю остальную высоту и та же плавающая панель внизу с тем же списком
(`ui/src/viewlist.jsx` рисует её на обеих страницах), в нём одни документы, без видов.
Открыт документ из `?d=`, иначе первый; выбор в списке
переписывает `?d=` в адресе (`replaceState`, у первого документа его нет).

**Схема, плата и 3D платы KiCad** (issue #123) — документы сами по себе, по строке
списка на каждый, с любой подписью: схема — `.kicad_sch` (тип `schematic`), плата —
`.kicad_pcb` (`board`), 3D платы — готовый `.glb` (`board3d`); сколько их в проекте,
столько агент и перечислил, две платы — две строки. `.kicad_pro` документом не бывает
(перечисленный — 422 «перечислите схему или плату»): он только файл-спутник, который
публикуется рядом со схемой или платой, если лежит в дереве под тем же путём без
расширения. Подлисты хаб находит сам для каждой записи-схемы (`docsbuild._kicad_schematic`):
из `(property "Sheetfile" "<путь>")` каждой найденной схемы (KiCad 6 пишет
`"Sheet file"`, принимаются оба написания), путь относительно
каталога схемы, которая его называет (так их находит KiCad); лист, найденный
раньше, второй раз не читается, так что цикл в иерархии конечен. Не больше 64
схем вместе с корневой (`render.MAX_KICAD_SHEETS`) и не глубже 8 уровней под
корнем (`docsbuild.MAX_KICAD_DEPTH`); лист, которого нет в дереве или чьё имя
хаб не раздаёт, — 422 с его путём. Все файлы публикуются под своими путями. В
`meta.json` у схемы `"kicad": {"schematics": [она сама, ...подлисты], "project": путь или
null}`, у платы `"kicad": {"project": ...}`, у `.glb` ничего лишнего; `bytes` — сумма
всех файлов записи; поле пересобирается и проверяется при публикации, как остальные
(`render._kicad`). Подпись справа в строке: у схемы `N sheets`, у платы `board`, у `.glb`
`3D`. **Дизайн** — записи-схема, -плата и -3D с одним путём без расширения
(`hw/main.kicad_sch`, `hw/main.kicad_pcb`, `hw/main.glb`; `designKey` в
`ui/src/KicadView.jsx`); перечислена одна запись — дизайн из одной. Страница держит
только id открытого документа, а `KicadView` — по одному смонтированному виду на
каждого перечисленного члена дизайна (схема и плата — свои `<ecad-viewer>`,
`static/_v/ecad-viewer.js`, грузится только при открытии; 3D — `BoardView3D`),
невидимый скрыт; переход между членами одного дизайна не пересоздаёт их. Выбор общий
на весь дизайн: одинарный клик по детали в любом виде выделяет ту же деталь, по
обозначению, в остальных, не меняя экран; клик мимо детали и Escape снимают выделение
везде, в том числе на виде, где кликнули. Переход между видами — правая кнопка
(решение владельца, §4): на детали (на схеме и плате ещё на цепи — метка, символ
питания, дорожка, переходное, полигон, площадка) у указателя открывается меню. Деталь и
цепь — отдельные пункты: `Show <обозначение> in <подпись вида>` на каждый другой
перечисленный вид и `Show net <имя> in <подпись вида>` (цепь — не в 3D); у площадки есть
и те и другие, у вывода на схеме — только деталь. Символ питания (`#PWR`) — не деталь, а
цепь с именем из его `Value`. Глобальные метки и символы питания одного имени — одна цепь
на весь дизайн, и вместо одного пункта схемы у неё пункт на каждый лист, где она есть:
`Show net <имя> in <подпись схемы> · <лист>` ведёт к первому её вхождению на этом листе
(с платы — все листы, со схемы — остальные). Локальная и иерархическая метки — цепь
своего листа, пунктов других листов у них нет. Какие цепи на каких листах, страница
читает из текстов схем, которые и так скачивает для вьювера (`ui/src/kicadnets.js`).
Выбранный пункт открывает вид или лист и выделяет там ту же деталь или цепь. У
вьювера нет вопроса «что под этой точкой», поэтому правый клик заново проигрывает его
собственный левый клик в той
точке (движение мыши и `click` по холсту, на который пришлась кнопка) и строит меню по
выбору, о котором вьювер сообщает; правое перетаскивание по-прежнему двигает вид. Меню
закрывают Escape, нажатие в другом месте, колесо, смена размера окна и уход вида с
экрана. Колесо на схеме и плате работает как у герберов (решение агента по жалобе
владельца, §4): двухпальцевое движение тачпада сдвигает рисунок, щипок и Ctrl+колесо
зумят к указателю. Делает это сам вьювер: его обработчик колеса — наша правка в
вендорённом файле (`static/_v/PROVENANCE.md`, «Our edits»), арифметика та же, что у
герберов. Остальные правки там же касаются выделения на плате: корпус обводится, а
не заливается (вьювер закрашивал его целиком циановой заливкой, и при переходе со
схемы деталь пропадала под пятном), и медные полигоны остаются на экране (вьювер
прятал все слои заливок, пока деталь выбрана); подсветка цепи затемняет только
плату, а не лист вокруг неё. Fit и Frame нижней панели для схемы и платы идут к
собственному виду вьювера внутри его shadow DOM (`zoom_fit_top_item`, `draw_now`
и чтение холста), 3D платы
отвечает за себя само (`BoardView3D`): камеру там крутит тот же трекбол, что у модели
(`CADTrackballControls` нашей сборки `three-cad-viewer`, скорости её же — поворот 1.0,
зум 2.0, панорама 0.22), а колесо — вторым слоем поверх него, как у страницы модели
(`ui/src/viewport/wheel.js` и `zoom.js` написаны под её ортокамеру и годятся только ей):
двухпальцевое движение сдвигает плату, щипок и Ctrl+колесо зумят к указателю. Настройка
«тачпад/мышь» страницы модели до видов-документов не доходит: там колесо всегда
сдвигает, зум — только щипок и Ctrl+колесо, как у герберов и видов KiCad. Ближняя
точка держится точно в плоскости, на которую камера смотрит. Событие снимается
слушателем в фазе capture на держателе холста — трекбол слушает сам холст, а два
слушателя одного элемента срабатывают в порядке подписки. `.glb` автор выгружает у себя: `kicad-cli pcb export glb
--subst-models --include-tracks --include-pads --include-zones --include-silkscreen
--include-soldermask -o <имя>.glb <плата>` (дорожки видны под маской; файл платы из 235
деталей — 41 МБ против 10 МБ без дорожек; `kicad-cli` в образ хаба не ставится); у `.glb` KiCad каждая деталь — потомок корня
сцены, названный обозначением (C523, R104), прочие потомки платы — слои с именами вида
`=>[0:1:1:98]`.

Вид платы — не «всё разом»: `hide-chrome` прячет собственные панели вьювера, а залитые
полигоны четырёх медных слоёв без них сливались в одно пятно, в котором дорожек не
прочесть. Поэтому в левом верхнем углу холста платы, там же, где у модели дерево деталей, и
строками того же вида — глаз в начале строки, за ним цвет и имя, — лежит своя панель
(`ui/src/PcbPanel.jsx`, сворачивается; решение владельца, §4): пресеты All, Front,
Back, Copper, ползунок непрозрачности полигонов
(при открытии платы 0.2 против 0.6 у вьювера — подобрано на четырёхслойной плате
dionis_speaker: дорожка нижнего слоя видна сквозь три заливки примерно наполовину, а
полигон ещё читается как медь) и строка на каждый слой — цвет, имя, глаз; щелчок по имени
делает слой активным. Состояние хранит вьювер, панель перечитывает его после каждой своей
правки, по его событиям и когда плата возвращается на экран. Щелчок по дорожке, площадке,
переходному отверстию или полигону подсвечивает всю цепь средствами вьювера
(`setHighlightedNets`) и называет её в заголовке панели; щелчок по футпринту или мимо
подсветку гасит.

**Даташит детали** — штатное поле `Datasheet` KiCad (решение агента, §4): у детали,
чьё значение — путь к файлу из `documents` (скрытому или нет), в меню по правой кнопке,
на всех трёх видах, последним пунктом стоит `Open datasheet · <имя
документа>`, и он открывает документ во всплывающем окне поверх вида (владелец: «пусть
открывает во вплывающем окне чтобы можно было вернуться назад. щас неудобно возвращаться,
надо выбирать внизу вид старый»): страницу ни о чём не просит, вид, выделение и камера под
ним не меняются, окно закрывают `×`, щелчок рядом и Escape (он закрывает только окно;
следующий снимает выделение); оно уходит при смене вида. Рисует его
тот же `DocumentView`, что и страница. Escape, нажатый внутри самого PDF, до страницы не
доходит: его забирает встроенный просмотрщик браузера. У детали с даташитом и без других
видов дизайна в меню один этот пункт. Путь читается так, как KiCad читает
`${KIPRJMOD}` (каталог `.kicad_pro`, а без него — схемы): срезаются `${KIPRJMOD}/` и
`file://`, `\` становится `/`, `..` сворачиваются; веб-адрес, абсолютный путь и путь за
корнем проекта ссылки не дают. Поле берётся со схемы (размещённый символ, не
`lib_symbols`), у детали без значения на схеме — с платы (`ui/src/kicadsheets.js`).

**Герберы** (решение 2026-10-24, §4) — один `.zip` в `documents`, тип `gerbers` по расширению, открыт без ключа, как файлы KiCad. Страница распаковывает его сама (`DecompressionStream('deflate-raw')`, размеры берутся из центрального каталога) и слой каждого файла определяет по `%TF.FileFunction` внутри него (`ui/src/gerber.js`). Рисует вендорённый `wasm-gerber-renderer` 0.8.1 (MIT; `static/_v/wasm_gerber_processor.js` и `.wasm`, подгружаются по адресу при открытии вида; нужен `'wasm-unsafe-eval'`, он уже в политике страницы, а `/_v/*.wasm` отдаётся как `application/wasm`) через его `GerberProcessor`: документированный интерфейс библиотеки перечитывает все слои на каждом кадре. На виде (`ui/src/GerberView.jsx`) панель слоёв слева, как дерево деталей (Top/Bottom, глаз в начале каждой строки), перетаскивание и двухпальцевое движение сдвигают плату, щипок и Ctrl+колесо зумят, двойной клик и Fit возвращают плату в кадр, ссылка на скачивание zip; тот же zip в меню Downloads страницы модели — группа GERBERS после STL. Слой без единой фигуры (в zip владельца это `B_Paste.gbp`) библиотека рисовать отказывается, в панели такая строка бледная, без глаза. Вид платы герберы не заменяют: это вид того, что уйдёт на производство.

Вьювер рисует выводы размещённого символа только по его собственным записям
`(pin "N" (uuid …))` и графику каждого берёт из библиотечного символа по
номеру; KiCad эти записи пишет, а konnect нет, и без них на схеме остаётся один
корпус, к которому цепи не доходят на длину вывода. Поэтому `KicadView` отдаёт
вьюверу каждую схему через `ui/src/kicadpins.js`: символ без единой записи
получает по записи на каждый вывод своего символа из `lib_symbols` того же листа
— всех юнитов, стиля 0 и своего (`body_style`, иначе `convert`, иначе 1), с uuid,
выведенным из uuid символа и номера вывода; какой юнит рисовать, вьювер решает сам
по месту размещения и записи чужих юнитов отбрасывает. Символ с записями и
текст, который не разбирается, уходят вьюверу байт в байт; файлы на хабе
остаются как опубликованы.

(issue #75). Экспорт детали — в её записи каталога (`parts[<ключ>].files`, карта

разбором ключа.

**Картинок у вида две, потому что их смотрят в двух разных местах.** `preview` —
лист со всем, что нужно человеку, открывшему сборку: кадр, заголовок и подвал с
габаритом, числом треугольников и водонепроницаемостью. `card` — тот же кадр и
ничего больше: он едет плиткой на главную, где подпись рисует сама страница, а
подвал в 190 пикселей высоты всё равно нечитаем. Одной картинкой это было, и
плитка резала её по краям — подпись съедала высоту, а деталь не влезала.

Так было не всегда, и прежняя форма — четыре плоские карты рядом (`downloads` с
ключом вида `<деталь>.<формат>`, `overview` и `previews` со стемом, который был
то деталью, то видом, `notes` с именем детали) — заставляла КАЖДОГО читателя
восстанавливать по ключу, что он держит, разрезая строку. Браузер именно это и
делал: резал имя по последней точке — и на детали с точкой в имени приписывал
файл не той строке дерева. Теперь такого разбора нет ни у кого.

**Каталог перечисляет ВСЕ детали, а не только печатаемые.** У каждой записи есть
`kind` (`printable`, `hardware`, `mock`), и экспорт есть только у печатаемой:
покупному винту и стене, к которой крепится кронштейн, экспортировать нечего.
Читателю, которому отдали бы только печатаемые, остальных было бы не восстановить
ничем.

**Кнопок при этом рисуется меньше, чем объявлено, и это разные вопросы.**
`assembled.stl` и `print.stl` кнопок не получают: сборка и так на странице в 3D, а
плита — это то, что положил вид `print`, и там законно может лежать макет
покупного подшипника; плита нужна КАРТИНКОЙ, той самой, что ловит деталь, лежащую
вверх ногами. Картинки кнопок не получают тем более — десять деталей дали бы
десять кнопок в меню, где всё остальное печатают. Объявлены они всё равно, и в
этом весь смысл объявления: каталог сборки хаб не перечисляет, так что до
необъявленного файла можно добраться только собрав URL руками, а такая инструкция
ломается молча в день переименования. Читает объявленное клиент — `hammerola
artifacts`.

**Чего нет — того нет в документе: поля отсутствуют, а не пусты.** Пустой объект —
это сборка, ЗАЯВЛЯЮЩАЯ, что ничего нет, и читателю пришлось бы задавать один вопрос
двумя способами. Правило держится отказом, а не подчисткой:
`files: {}` — такое же 422, как `note: ""` (§7.1), потому что хаб не редактирует
документ, который писал не он.

**Необязательность при этом у полей РАЗНАЯ, и складывать два её вида в одно
«необязательно» нельзя.** По-настоящему необязательны `overview`, `preview` и
`card` вида, `preview` и `note` записи каталога: их может не быть ни у одной
записи, и документ без них законен. `files` в этот список не входит — его наличие продиктовано видом
записи, а не выбором автора: печатаемая обязана нести `files`, непечатаемая обязана
их НЕ нести, и оба нарушения — тоже 422 (§7.1).

Объявляется при этом строго то, что реально
записано, — не намерение: хаб принимает только имя, которое есть в дайджесте
выхода, так что объявленный, но не записанный файл превращает мягкую деградацию в
отказ публикации. Без вида `print` нет ни `print.stl`, ни его картинки; на python
без графического стека нет ни одной картинки вовсе (обе деградации поддержаны).
`assembled.stl` при этом есть всегда: его пишет каждая сборка либо падает.

Ответы:

| Код | Когда | Тело |
| --- | --- | --- |
| 202 | пуш принят, сборка поставлена в очередь | `{"job", "status_url", "log_url"}`, заголовок `Location` = `status_url`; на маршруте без имени ещё и `revision` |
| 201 | опубликовано | `{"url": "/project/<pid>/<commit>/"}` |
| 200 | этот коммит уже опубликован, содержимое совпадает | то же; на маршруте без имени ещё и `revision` |
| 400 | `Content-Length` отрицательный, либо тело оборвалось раньше объявленной длины | `{"error": ...}` |
| 403 | нет или плохой токен | `{"error": ...}`, без `WWW-Authenticate`: 401 хаб не отвечает никогда, этот код оставлен прокси перед ним (§4) |
| 408 | тело не пришло целиком за `BODY_DEADLINE_SECONDS` (300 с) | `{"error": ...}` |
| 409 | коммит уже есть, но содержимое ДРУГОЕ | `{"error": ...}` |
| 411 | заголовка `Content-Length` нет или он не число | `{"error": ...}` |
| 422 | битый архив, невалидный `meta.json`, битые ссылки, небезопасное имя члена архива, плохой `pid`/`commit` | `{"error": ...}` |
| 503 | нет свободного слота публикации за `PUBLISH_WAIT_SECONDS` | `{"error": ...}`, заголовок `Retry-After: 30` |

**Где именно теперь появляется 201.** С шага 5 (§8A.2) пуш асинхронный, и таблица
выше читается по одному правилу: всё, что решается **из самого пуша**, отвечается на
пуше, а всё, для чего нужна СБОРКА, уезжает в задачу. Токен, целость архива,
имена членов и «этот пуш уже опубликован» — свойства загруженного тела, поэтому 403,
411, 408, 400, 422, 409 и 200 приходят там же, где приходили всегда. 201 и
422-от-сборки приходят из задачи: их узнают через `GET /api/v1/jobs/<id>` (§7.4).
409 умеет прийти обоими путями, и это не дубль проверки: на пуше отвечает
`Store.settled`, а перед самым `rename` та же проверка делается ещё раз под локом
проекта — окно между ними теперь не миллисекунды, а целая сборка, и два пуша одного
коммита с разным содержимым запросто оказываются в нём одновременно.
503 бывает двух видов — «нет слота приёма за `PUBLISH_WAIT_SECONDS`» (тело не читалось
вовсе, `Retry-After: 30`) и «очередь сборки полна» (тело принято, задача заведена и
сразу помечена провалившейся, `Retry-After: 60`); для CI оба означают одно и то же —
повторить тем же телом.

409, а не перезапись: сборка по коммиту объявлена неизменяемой, и на неё выданы
вечные заголовки кэша. Молча подменить её содержимое — значит соврать всем, у кого
она уже в кэше. 200 на побайтово идентичный повтор делает ретрай CI безопасным.
На маршруте, где имя чеканит хаб, «то же имя с другим содержимым» вообще не
возникает — там 409 значит уже другое, см. §7.7.

**Что ретраить, а что нет.** 503 значит «попробуй ещё раз тем же телом»: хаб просто
занят, пуш ни в чём не виноват. 408 и 400 — про оборвавшуюся передачу, повтор тоже
имеет смысл. Остальные 4xx — про сам запрос, и повтор без изменений даст ровно тот
же код; CI должен упасть и показать `error` из тела. 403 закрывает соединение
(`Connection: close`), чтобы непрочитанное тело не разобралось как следующий запрос
на keep-alive-соединении; по той же причине его закрывают 400, 408 и 411.

**Дедлайн на тело — отдельно от таймаута сокета.** `HubHandler.timeout` меряет
паузу между пакетами и взводится заново каждым из них, так что клиент, отдающий по
байту раз в 29 секунд, не трогает его никогда — и держит слот публикации сколько
захочет. Четверых таких хватает, чтобы занять весь `MAX_CONCURRENT_PUBLISHES`, и
вся легитимная CI получает 503; цена атаки — четыре сокета и ноль трафика. Поэтому
у тела есть свой дедлайн на всю передачу (`BODY_DEADLINE_SECONDS`, 300 с — тело в
64 MiB проходит за них на ~1.7 Мбит/с, и чем крупнее проект, тем быстрее должен быть
канал). Читать при этом надо `rfile.read1()`, а не
`read()`: буферизованный `read(n)` крутится внутри, пока не наберёт все n байт, и
до проверки дедлайна управление просто не возвращается.

### 7.1 Валидация до публикации

- **каждая ссылка на файл** — где бы она ни стояла: `views[].file`,
  `views[].overview`, `views[].preview`, `views[].card`, в записи каталога
  каждый `parts[<ключ>].files[*]` и `parts[<ключ>].preview`, а у документа
  `documents[].file` — названа
  среди файлов, которые **записала сборка** (а не среди членов архива — в архив едет
  исходник, см. §7), лежит **в корне её
  выхода** (в подкаталоге — 422, см. §7; документ — исключение: он лежит под своим
  путём, и правило ниже проверяет каждый сегмент пути,
  `buildnames.unservable_path_reason`), **не
  начинается с точки, не содержит непечатаемых символов** и **не**
  совпадает с `meta.json`, `index.html` или файлом дайджеста: `meta.json` хаб
  перезаписывает уже после этой проверки, а `index.html` из каталога сборки не
  раздаётся вовсе (§7.4), так что ссылка на них указывала бы не туда, что померили.
  Проверка одна на ВСЕ точки намеренно (`render._check_declared_file`):
  утверждение про имя у них одинаковое — «сборка записала файл с таким именем, и
  хаб его отдаст», — а различаются они только тем, ЧЕМУ файл принадлежит, и это
  теперь сказано МЕСТОМ ссылки, а не смыслом ключа, который читателю надо было
  разбирать (issue #75, см. §7). Каждый из вопросов — это способ
  принять пуш и раздать не то, что померили. `views` пришёл в общую проверку
  последним и пришёл через баг: у него оставалась своя проверка на месте, которая
  спрашивала членство, `/` и генерируемые имена — и не спрашивала ни точку, ни
  непечатаемые, — так что ровно тот дефект, ради которого правило и собирали в
  одно место, жил на ссылке, без которой страница сборки пустая.
  **Правило «какое имя хаб вообще раздаёт» живёт в ОДНОМ месте** —
  `hammerola/buildnames.py`, отдельный модуль на одном stdlib, — потому что его
  спрашивают трое: раздача
  (`_safe_build_path` в `src/app.py`, правило на каждый сегмент пути),
  объявление (`render._check_declared_file`) и
  КЛИЕНТ, который перепроверяет каждое имя перед записью на диск автору
  (`hammerola/artifacts.py`) и импортировать `render` не может вовсе. Две копии
  одного правила разошлись ровно там,
  где это не видно: ведущую точку объявление принимало, а раздача не отдаёт, так
  что сборка публиковалась 201-м в неизменяемый каталог с годовым кэшем и
  отвечала 404 на каждый GET файла, который сама же назвала. Членство в списке
  записанного этого не ловит и не может: оно отвечает только «файл там есть».
  Алфавита к выходному имени не применяет никто — имена выбирает код модели, а
  `runner._verify_output_file` проверяет форму пути, симлинки и существование, и
  алфавита нет и там. Непечатаемые символы
  в имени — про читателя, а не про браузер: имя печатает `hammerola artifacts` и
  кладёт файл на диск автору, так что U+202E разворачивает строку отчёта;
- ни один член архива не убегает из каталога. Фильтруем сами, а не через
  `tarfile(filter="data")`. Имя члена — относительный путь, и проверяется он
  **покомпонентно**: каждый кусок между `/` обязан целиком совпасть с
  `\A[A-Za-z0-9][A-Za-z0-9._-]{0,127}\Z` (якоря именно `\A`/`\Z` — `$` в Python
  матчится и перед завершающим `\n`, так что `model.stl\n` прошёл бы). Отдельного
  списка запрещённых форм нет и не нужно — всё умирает об это правило: `..` не
  начинается с буквы или цифры, у абсолютного пути и у ведущего `/` первый компонент
  пустой, у `a//b` и `a/./b` пустой или `.` компонент в середине, а backslash, NUL и
  любой не-ASCII (включая гомоглиф `⁄` U+2044) в алфавит не входят. Тип — только
  обычный файл, симлинки/хардлинки/устройства/FIFO отвергаются. Дальше две
  независимые линии, и после переезда на дерево их именно две, а не одна:
  `os.path.realpath(target)` обязан лежать **внутри** staging-каталога — проверка по
  компоненту пути, а не по префиксу строки, иначе соседний `<staging>-evil/`
  считается «внутри», — и весь путь проходится по одному компоненту за раз через
  `mkdirat`/`openat` с `O_DIRECTORY|O_NOFOLLOW`, а файл создаётся
  `O_CREAT|O_EXCL|O_WRONLY|O_NOFOLLOW` относительно уже открытого каталога. Ядро при
  этом ни разу не разрешает путь длиннее одного компонента, поэтому симлинк на любом
  уровне — ошибка, а не перенаправление, даже если его положили между двумя членами;
- **записи-каталоги пропускаются молча, а каталоги хаб создаёт сам.**
  `tar -czf build.tar.gz .` — самая очевидная команда для CI модели — кладёт в архив
  запись `.` и по записи на каждый подкаталог, и отвергать их значит ломать всех на
  первом же шаге. Из записи-каталога не берётся ничего: ни имя, ни режим, ни сам факт
  её наличия. Каталоги делаются из путей ФАЙЛОВ, которым они нужны, с режимом 0755
  (`fchmod` по дескриптору, а не `mkdir(mode)`, — иначе umask процесса решал бы, сможет
  ли `app` читать собственную сборку), так что архив со списком `scripts/` и архив без
  него распаковываются одинаково;
- те же якоря и тот же принцип — для `pid` и `commit` из URL;
- `title`, `project` и `built` — не длиннее 200 (у `built` — 64) символов и без
  непечатаемых. Категория `Cf` отвергается вместе с `Cc`: U+202E RIGHT-TO-LEFT
  OVERRIDE печатаемым не считается ничем, но `textContent` его честно применяет и
  разворачивает соседний текст. `built` проверяется наравне с остальными именно
  потому, что он едет ещё и в общий `/index.json`, который с `no-cache` качает
  каждый посетитель `/`: полмегабайта `built` от одного проекта — это испорченный
  индекс у всех. На дату он при этом **не** парсится (см. §7.3);
- ключи `parts[<ключ>].files` — только `\A[A-Za-z0-9._-]{1,32}\Z` (`SAFE_LABEL`):
  это расширение, и оно едет в подпись кнопки скачивания. Правило то же, что было у
  меток плоского `downloads`; довод про подпись переехал вместе с файлами в запись
  детали, а разбор имени на «деталь» и «формат» кончился — их теперь два поля;
- **ключ каталога `parts` — НЕ по этому правилу, а по правилу имени детали**
  (печатаемый текст, без угловых скобок, до 200 символов): это ИДЕНТИЧНОСТЬ, а не
  подпись, — на неё ссылаются `views[].parts`, каждый лист файла вида и строка
  дерева во вьювере. Потолок в 32 символа отверг бы честный пуш: свой потолок у
  имени детали ЕСТЬ, но он вчетверо больше — 128 символов (`MEMBER_RE`) на стороне
  сборки и `MAX_TEXT` здесь, — так что имя символов на 48 законно и было бы
  отвергнуто подписью. Угловые скобки запрещены по той же причине, что и всюду в
  имени детали: вендоренный вьювер присваивает имя в `innerHTML`;
- **`kind` у каждой записи каталога** — `printable`, `hardware` или `mock`
  (транскрипция `cadbuild.parts.KINDS`, а не импорт: раздача не лезет в сборочную
  половину, равенство держит `tests/cadbuild/test_naming.py`). Неизвестный —
  422, а не «нарисуем что знаем»: браузер рисует запись ПО виду, так что молча
  отброшенная запись означала бы, что пуш сам выбирает, какой детали читатель не
  увидит. Плюс два утверждения, зеркальные тому, что сборка вообще умеет
  произвести: печатаемая обязана нести `files`, непечатаемая обязана их НЕ
  нести. Каталог без единой печатаемой — законная сборка: купленный корпус
  вокруг заводских плат печатать нечего, а смотреть на него надо;
- **любое необязательное поле читается явным сравнением с `None`**, а не
  `record.get(...) or {}`: последнее превращает `[]`, `""` и `0` в «ничего нет» и
  молча публикует пуш, который описывал что-то другое. И **пустое написание
  отвергается, а не подчищается**: `files: {}` — такое же 422, как `note: ""`,
  потому что хаб не редактирует документ, который писал не он, а написать такое
  может только рукодельный пуш (сборка пишет каждый из этих ключей под проверкой,
  что ей есть что туда положить);
- **потолок на ЧИСЛО ЗАПИСЕЙ считается ДО обхода** (а бюджет на ССЫЛКИ из
  записей — нет, он тратится по ходу; про него в конце этого же пункта): отвергать
  после прохода по документу значит заплатить ровно за то, ради отказа от чего
  потолок и существует. Ловится форма, которую правило на отдельную запись не
  видит: записи все до одной законные, но их сто тысяч, и получившийся `meta.json`
  качает каждый посетитель этой сборки — под годовым `immutable`, из пуша, который
  уже не отозвать (`Store._read_meta` читает документ одним `read_text()` без
  своего потолка). Числа при этом РАЗНЫЕ, и читать их как паритет нельзя; общее у
  них только одно — потолок наследуется от того, что сборка реально записала, а не
  выдумывается вторым числом, которое с источником разойдётся.
  У `views` это `len(files)` — сколько файлов сборка объявила (`_check_map_size`):
  каждая запись обязана называть файл из этого списка, а честная сборка пишет по
  файлу на вид, так что всё сверх — повторы уже названного; число наследуется от
  `limits.output_files` (4096). Нужен он там сильнее всего: запись этого списка
  стоит не поиска в словаре, а полного разбора файла вида (`check_view_file`) и
  полного gzip'а его же (`measure_view`) — ~18 мс на файле 0.9 МБ, — и указывать N
  записей на ОДИН файл никто не мешает (`seen` запрещает повтор id вида, а не
  имени файла). Сто тысяч таких — это часы CPU внутри `_finish_staging`, в потоке
  воркера сборки, которых на весь процесс четыре, и очередь сборки после этого не
  двигается.
  У каталога `parts` это константа `MAX_PARTS` (200), одна с обеих сторон провода
  (`cadbuild.hubspec.MAX_PARTS`, равенство держит
  `tests/cadbuild/test_naming.py`). Потолок считает ЗАПИСИ, а не заметки среди
  них: дорого стоят как раз записи БЕЗ заметки — каталог из ста тысяч покупных
  винтов весит те же мегабайты и не несёт ни одной (#75).
  У ссылок на файлы ИЗ каталога это ОДИН бюджет на весь каталог — снова
  `len(files)`, но тратится по мере обхода (`_spend_file_budget`). Именно на весь,
  а не на запись: запись законно называет `len(files)` имён, и 200 × 4096 ссылок —
  это пятидесятимегабайтный `meta.json`, на порядок хуже плоских карт, которые эта
  форма заменила. Три ссылки самих видов на этот бюджет не идут: они ограничены как
  ЗАПИСИ, по три указателя на запись.
  Сам `files`, от которого считаются оба производных потолка, приходит ровно
  одним путём, и он же единственный, который сюда доходит: `build_meta` зовётся
  только из `Store._finish_staging`, а `files` там всегда `_hash_output` от того,
  что объявила СБОРКА. `MAX_MEMBERS` тут ни при чём — он считает членов
  загруженного архива, и та карта уходит в `_payload_digest`, больше никуда;
- **`views[].parts` — список ключей каталога, а не число.** Число было фактом про
  файл вида, который не сходился ни с чем: пять пинов — это пять ссылок на ОДНУ
  запись каталога. Каждый ключ обязан быть в `parts`, повторов нет, длина считается
  против размера каталога ДО обхода (`_view_parts`), а сам список сверяется с тем,
  что реально несут листья файла вида, — в обе стороны (`_match_selection`), иначе
  сводка обещает то, чего в файле нет;
- **содержимое каждого файла вида** — тоже вход, а не «данные». Файл целиком
  уходит в `viewer.render()`, а вендоренный `three-cad-viewer` строит дерево
  деталей через `label.innerHTML = node.name` и дописывает
  `<span style="color:${color}">`. Библиотеку править нельзя (3.6 МБ, меняется
  целиком с релизом), поэтому дерево `{"version":…, "parts":[…]}` обходится
  рекурсивно на приёме: `name` — печатаемый текст без угловых скобок (для `title`
  скобки безобидны — их рисует наш `textContent`, — а здесь это тег), `color` —
  только `\A(#[0-9A-Fa-f]{3,8}|[A-Za-z]{1,32})\Z` или список таких значений.
  CSP тут подстраховка, а не замена: она гасит `<script>`, но не `form-action` и
  не переходы, а URL сборки вечный и того же origin, что все остальные проекты —
  отозвать stored HTML injection оттуда нечем. Тем же обходом проверяется `key`:
  лист обязан его нести, группа — нет, и каждый встреченный ключ обязан быть в
  каталоге `parts`. Он в списке разбираемых полей (`VIEW_KEPT_KEYS`) именно
  поэтому: буферы вершин и индексов парсер выбрасывает на лету, и пока `key` летел
  вместе с ними, он был единственной строкой, доезжающей из пуша до DOM и не
  проверенной ничем;
- минимум один вид;
- потолки: число членов архива (`MAX_MEMBERS`, 1024 — было 256 под плоскую
  сборку, поднято под исходник, где `scripts/` и `ref/` на несколько десятков файлов
  каждый — норма) и глубина пути (`MAX_PATH_DEPTH`, 8 компонентов вместе с именем
  файла: `ref/vendor/rev2/part.step` — это 4, а восемь компонентов по 128 символов
  плюс staging-префикс всё ещё далеко от `PATH_MAX`, так что принятый архив не может
  упасть на `ENAMETOOLONG` посреди распаковки, то есть 500-м на архиве, который
  ничего не нарушил);
- дубли членов ловятся по **всему пути** и со свёрткой регистра: `a/File` и `A/file` —
  один файл на APFS и на bind-mount Docker Desktop, а `a/model.py` и `b/model.py` —
  два разных, так что свёртка только последнего компонента ломала бы обычное дерево;
- имя, занятое и файлом, и каталогом (`a` рядом с `a/b.py`), — это 422, а не 500:
  `EEXIST`/`ENOTDIR`/`EISDIR`/`ELOOP`/`ENAMETOOLONG` считаются виной пуша, всё
  остальное от ФС (в первую очередь `ENOSPC`) остаётся `OSError` и уходит 500-м —
  ровно по тому же правилу, по которому битый архив не путается с полным диском.

### 7.2 Атомарность

1. распаковка в `data/project/<pid>/.tmp-<commit>-<uuid>/`;
2. валидация и запись нормализованного `meta.json`;
3. `os.rename` → `data/project/<pid>/<commit>/` — атомарно в пределах ФС;
4. копия этой же ревизии в слот `dev` (§7.6, issue #78) — тем же swap'ом, что и
   локальный пуш;
5. переключение `latest`: `os.symlink(commit, tmp)` + `os.rename(tmp, latest)` —
   атомарная замена симлинка, читатель не видит промежуточного состояния;
6. `builds.json` и корневой `index.json` — тоже «временный файл + rename»;
7. дедупликация (§5.3): файлы сборок проекта с одинаковым sha256 становятся жёсткими
   ссылками на одну копию — ссылка под временным именем и `rename` поверх файла, так что
   читатель видит те же байты и никогда не находит имя пустым. Идёт под локом проекта
   сразу после `builds.json`, раньше `index.json`.

Последним шагом здесь стояла ретенция — её нет с решения 2026-08-27 (§5.3). На её месте
стоит дедупликация, которая ничего не удаляет.

**Что может измениться в каталоге сборки ПОСЛЕ шага 3.** Ровно одно поле —
`message` в `meta.json`, том самом файле, который хаб и так пишет сам (§7.1, и
белый список Content-Type ниже). Повторный пуш того же дерева не собирает ничего
и отвечает 200 из запроса (`Store.settled`, §7.7), но если он принёс другой текст
`-m`, то под локом проекта переписывает `meta.json` ревизии и следом `builds.json`
(issue #67). Всё остальное в `<commit>/` — геометрия, виды, экспортированные
файлы — неизменяемо без исключений, и 409 на «то же имя, другое содержимое»
остаётся ровно тем же. Что это исключение стоит читателю — записано в §3.2:
ничего, потому что `message` из `meta.json` не рисует ни одна страница, а
переключатель читает `builds.json` под `no-cache`.

Байты остальных файлов не меняются, но их записи в каталоге — меняются: шаг 7
заменяет файл жёсткой ссылкой на другую копию с тем же sha256, а сборке, у которой
нет `.files.sha256`, этот файл дописывает. Читатель этого не видит — по каждому URL
отдаются те же байты.

**До чего именно зеркало обязано идти.** До шестого шага — `builds.json` и
`index.json` пишутся из того, что лежит на диске: `has_dev` и флаг на карточке —
оба ответы про слот, и слот, заполненный ПОСЛЕ них, не появился бы ни в одном до
следующей публикации этого проекта. С `latest` (шаг 5) такого довода нет ни в одну
сторону, и зеркало стоит перед ним просто потому, что шаги перечислены в этом
порядке. Плата за это — `latest` переключается позже на время полного `copytree`,
и она приемлема: ревизия уже опубликована по своему вечному URL, а `latest` —
указатель на неё, не сама публикация.

Ни на одном шаге не должно существовать момента, когда `latest` указывает на
наполовину распакованный каталог.

Публикация в локальный слот (§7.6) идёт по тем же шагам 1–2, а вместо 3–5 делает swap
каталога: старый `dev/` переименовывается в `.trash-<uuid>`, новый занимает его место,
старый удаляется. Дальше — только шаги 6 и 7 (`builds.json`, чтобы переключатель узнал, что
слот занят, плюс перезапись `index.json`, и дедупликация): `latest` локальная сборка не трогает, а
корневой индекс — трогает, потому что в карточке есть флаг «есть незакоммиченная
работа» (§7.6). Что она не может — это создать карточку: её нет у проекта без
коммит-сборки. Инвариант тот же: читатель не оказывается внутри каталога, который
наполняют.

Тело запроса пишется сразу в файл `data/.upload-<uuid>` и оттуда открывается
`tarfile` — не через `BytesIO`: сборка в памяти давала пик в два тела (64 MiB
превращались в 128 MiB), и нескольких параллельных ретраев CI хватало на OOM.
Принятый пуш это тело не выбрасывает, а переименовывает в `.body-<uuid>`: оно
живёт до конца сборки и на успешном пути становится кодом ревизии (§7.8).
Переименование — и есть смена владельца: `.upload-` удаляет поток запроса всегда,
`.body-` принадлежит задаче.

Все временные имена — с точки: `.tmp-*`, `.latest-*`, `.upload-*`, `.trash-*`,
`.wip-*`, `.src-*`, `.body-*`. Поэтому их не видит ни `builds_of`, ни раздача — и
поэтому же после SIGKILL они остаются на томе навсегда. `Store.__init__` сметает
такие записи старше часа (младше — могут принадлежать живой публикации; четыре
часа покрывают и `.src-*`/`.body-*`, живущие очередь плюс сборку, — это двадцать
минут при сегодняшних `MAX_QUEUED_JOBS` (16), `wall_seconds` (300 с) и ЧЕТЫРЁХ
воркерах (`16 × 300 / 4`). **Был час против шестнадцати минут, пока
`wall_seconds` был 120 с;** подъём до 900 с 2026-08-29 сделал бы час МЕНЬШЕ
худшего честного ожидания, то есть подметание вырывало бы исходники из-под
сборки, всё ещё стоящей в очереди — молча с обеих сторон. Дальше ожидание падало
дважды и в обе стороны от него запас только рос: вдвое 2026-09-09, когда воркеров
стало четыре (issue #80), и втрое 2026-09-10, когда `wall_seconds` вернулся к
300 с (issue #81). Само число четырёх часов не двигалось ни разу — падение
ожидания его сломать не может).

**`.trash-` в этом списке остался, хотя удалять сборки больше некому:** через него идёт
перезапись слота `dev` (§7.6, `_swap_dev_slot`) — старый каталог сначала уезжает в
`.trash-<uuid>` и только потом `rmtree`. Правило, ради которого так делалось у ретенции,
переживает саму ретенцию: `rmtree(ignore_errors=True)` НА МЕСТЕ оставляет каталог,
который всё ещё раздаётся, но уже потерял `meta.json`, — то есть выпал из `builds_of` и
не будет убран уже ничем. Переименование, наоборот, одним атомарным шагом делает каталог
невидимым для раздачи, а саму уборку — необязательной: не доделали `rmtree` — остаток
подметёт часовое отсечение.

### 7.3 Ретенции нет

Механизма нет ни у сборок, ни у задач, ни у локального слота, ни у комментариев —
решение 2026-08-27, обоснование в §5.3. Из кода удалены `RETENTION_BUILDS`, `Store._prune`,
`Store._delete_build` и всё, что существовало только ради них; тем же решением ушли
`COMMENT_MAX_PER_BUILD`, `COMMENT_MAX_TOTAL` и весь подсчёт комментариев, который их
обслуживал (§7A.4). Опубликованная сборка
лежит на томе, пока её не удалит человек, и другого способа нет.

Локальный слот исключением не является, но у него есть и своя причина не копиться: это
один каталог, который каждый пуш перезаписывает целиком (§7.6).

Единственное, что удаляется автоматически, — то, что сборкой и задачей НЕ является:
временные имена с точкой старше `LEFTOVER_MAX_AGE_SECONDS` (четыре часа;
`Store._sweep_leftovers`, §7.2), в том числе
недописанные записи реестра задач (§7.4). Это уборка мусора, и путать её с ретенцией
нельзя: под неё не попадает ни одна опубликованная сборка и ни одна запись о задаче.

### 7.4 Раздача

| Путь | Кэш |
| --- | --- |
| `/project/<pid>/<commit>/*.json`, файлы с расширениями документов и файлы KiCad (`OPEN_SUFFIXES`), а также любой путь, перечисленный в `documents` этой сборки (`_listed_document`), — описание, сетка видов, картинки, документы | `public, max-age=31536000, immutable` |
| `/project/<pid>/<commit>/*` — остальные файлы сборки (STEP, STL, 3MF), по токену или ключу | `private, max-age=31536000, immutable` |
| `/project/<pid>/<commit>/` и `.../index.html` — сама страница | `no-cache` |
| `/project/<pid>/latest/*` и `/project/<pid>/dev/*` — файлы сборки | `no-cache` + слабый `ETag` (размер, mtime, inode), условный запрос отвечает 304: 3D платы весит 40 МБ, и без валидатора его качали бы заново при каждом открытии |
| `/_v/*` — всё целиком | `no-cache` + слабый `ETag`, условный запрос отвечает 304 |
| `/`, `/index.json`, `/project/<pid>/builds.json` | `no-cache` |
| `/api/v1/jobs/<id>` и `/api/v1/jobs/<id>/log` | `no-cache` |
| `/api/v1/sources/<revision>` и `/api/v1/sources/<revision>/log` | `no-cache` |

Файл сборки адресуется путём любой глубины (`/project/<pid>/<commit>/docs/cut-list.md`):
документ лежит под своим путём в дереве (§7). Каждый сегмент проверяется тем же
правилом имени, что и одиночное имя (`app._safe_build_path`,
`buildnames.unservable_path_reason`), так что `..`, `.` и скрытые имена не отвечают
ни на какой глубине. `/<a>/compare/<b>/` остаётся адресом сравнения, поэтому путь
документа, начинающийся с `compare/`, отвергается при объявлении.

`immutable` не получает НИЧЕГО в `/_v/`: каждый файл там меняется вместе с образом под
одним и тем же именем, а год на таком имени означает, что после деплоя все, кто уже
открывал сайт, до года сидят на старом JS, и отозвать выданный кэш нечем. Исключением
был `three-cad-viewer.*` — на том основании, что имя несёт версию библиотеки и новая
приезжает файлом с другим именем. Форк (`viewer/`, issue #14) это основание отменил:
`make viewer` переписывает ровно это имя, так что патч вьювера обязан доезжать до
браузеров так же, как патч `hammerola.js`.

Цена этого — слабый `ETag` из размера и mtime на каждой отдаче `/_v/`. Без валидатора
`no-cache` заставляет браузер тянуть файл целиком при каждом открытии страницы, а в
каталоге теперь 3.6 МБ вьювера и three; с валидатором повторный визит стоит одного
условного запроса и 304.

Ровно поэтому **страница сборки не лежит в каталоге сборки**. Она одинакова для всех
сборок и всех проектов и меняется вместе с образом — первый же скрипт страницы,
которому понадобится новый элемент разметки, сломал бы все ранее опубликованные
сборки, если бы
их HTML был вкопан в каталог под годовым `immutable`. Хаб отдаёт её из шаблона
(`render.build_page_html()`), как и `/`, с `no-cache`; неизменяемо кэшируется только
содержимое сборки. По этой же причине `index.html` из архива не раздаётся никогда:
этот URL принадлежит генерируемой странице.

Плюс `GET /health` для healthcheck из compose и `GET /project/<pid>/` — страничка,
которая выбирает указатель по тому, что читатель смотрел в прошлый раз (§9);
302 на неё отдаётся с URL без завершающего слеша. Живой список маршрутов — шапка
`src/app.py`, и её держит `tests/test_route_inventory.py`.

**Статус и лог сборки** (§8A.2, шаг 5) — единственная часть раздачи, которая не
публичная:

| Путь | Ответ |
| --- | --- |
| `GET /api/v1/jobs/<id>` | `application/json`: запись задачи целиком плюс `log_url` |
| `GET /api/v1/jobs/<id>/log` | `text/plain; charset=utf-8`: что напечатала сборка |

Непубличного на раздаче с тех пор стало больше: там же живёт КОД опубликованной
ревизии, `GET /api/v1/sources/<revision>` и `/log`, под тем же `EDIT_TOKEN` и
по тем же правилам, что ниже. Раскладка, инвариант и типы — §7.8.

И там же — **`GET /index.json`, СПИСОК ПРОЕКТОВ** (решение 2026-08-27, вместе с
переносом главной на React). Линия проходит не по «страницы публичны, API — нет», и
это стоит проговорить, потому что рядом две половины выглядят несогласованно.
СБОРКУ видно по ссылке: страница, `meta.json`, JSON-сетка видов и PNG-картинки
отдаются анонимно и с годовым `immutable`. Она и есть продукт — постоянная ссылка,
которую человеку ДАЛИ и которую он кинул в чат; ссылка, спрашивающая у получателя
секрет, продуктом быть перестаёт. Файлы деталей устроены иначе — см. ниже.
ПЕРЕЧИСЛЕНИЕ — наоборот: `index.json` единственный отвечает на вопрос «что вообще
есть на этом хабе», его никому не дают, и каждый id в нём — префикс всех постоянных
URL этого проекта навсегда. Правило: по выданной ссылке открывается ЭТА сборка, а
перечисление не открывается ничем.

То же правило действует и внутри проекта (решение 2026-10-11): **`builds.json`,
список ревизий проекта** вместе с `latest` и признаком черновика, — тоже под
`EDIT_TOKEN`. Получатель ссылки на ревизию видит эту ревизию и ничего больше:
переключателя ревизий у страницы без токена нет. Это не замок: `latest/` и `dev/`
по-прежнему открываются любому, кто наберёт их руками. Противника здесь нет — есть
получатель, которому не надо показывать историю и черновик.

**Файлы сборки — по токену или по ключу в ссылке** (решение 2026-10-16, §4).
Открыто только то, без чего не нарисовать модель и не показать картинку, и
документы сборки — их страница сборки показывает по той же ссылке: `.json` и все
расширения документов, `.md`, `.pdf`, `.png`, `.jpg`, `.jpeg`, `.gif`, `.webp`,
`.html`, `.htm`, `.svg`, `.kicad_sch`, `.kicad_pcb`, `.glb`, `.zip` (герберы), и файл-спутник схемы и
платы, `.kicad_pro` — без них вьювер не нарисует схему (решение 2026-10-23, §4)
(`OPEN_SUFFIXES` в `src/app.py` из `render.DOCUMENT_TYPES` и
`render.KICAD_SUFFIXES`). Расширение — первая из двух причин открытости; вторая —
**список самой сборки** (решение 2026-10-25, §4): путь, который `meta.json` этой
сборки перечисляет в `documents`, открыт
по обычной ссылке, какое бы ни было расширение, — иначе DXF или прошивку, которые
страница не рисует, нельзя было бы отдать по ссылке (`_listed_document` в
`src/app.py`). Вопрос этот задаётся только запросу, который не предъявил ни токена,
ни ключа, и только про `meta.json` этой сборки, так что перечисленное в одном
проекте ничего не открывает в другом, а экспорты детали остаются закрытыми, сколько
бы файлов того же расширения ни лежало рядом. Всё остальное — STEP, STL, 3MF, STL вида
целиком и любой будущий формат выгрузки — отдаётся тому, кто предъявил
`EDIT_TOKEN`, или тому, у кого в query есть `files=<ключ>`; иначе — 403 с
`this link does not include the files of this build`. Ключ — первые 32
hex-символа HMAC-SHA256 от `EDIT_TOKEN` по строке `<pid>/<сегмент>`, где сегмент —
`latest`, `dev` или имя ревизии, как он стоит в адресе (`files_key`). Хаб ключ не
хранит, а каждый раз вычисляет заново, поэтому секрет в системе по-прежнему один.
Ключ открывает только свой адрес: ключ ревизии — файлы этой ревизии, ключ `latest`
— файлы того, что последнее сейчас и будет последним потом. Отозвать один ключ
нельзя: все отзываются разом сменой `EDIT_TOKEN`. Закрытый файл ревизии уходит с
`private`: ответ зависит от того, что предъявлено, и общий кэш не должен отдать его
другому.

Ключи владелец получает в ответе `builds.json`: хаб, отдавая его под токеном,
дописывает поле `files_keys` — ключ к `latest`, к каждой ревизии `builds[]` и к
`dev`, если слот занят. На диск ключи не пишутся. Страница подставляет ключ к сборке
на экране в свои ссылки на файлы, потому что ссылка-скачивание `<a download>`
токен передать не умеет. Читатель без токена берёт ключ из `?files=` адреса, с
которым открыл страницу; нет ключа — нет ни меню Downloads, ни файлов в меню детали.
Ссылки выдаёт окно «Поделиться»: значок на строке `latest` и на каждой строке
истории в списке ревизий; у черновика значка нет, постоянного адреса у него нет.
Галочка «Include files» по умолчанию снята. Без неё ссылка — обычный постоянный
адрес сборки с видом, документом и кадром камеры на экране (`v=`, `d=`, `c=`, §3),
с ней — тот же адрес с `files=<ключ>`. Кнопки копирования адреса в
шапке нет: адрес без ключа, пересланный дальше, незаметно терял бы файлы. Честная
цена: упорный получатель вытащит треугольники из JSON-сетки, которую браузер
получает для показа; закрыты только сами файлы.

Токен проверяется **до** чтения файла с тома — по той же причине, что и у задач:
иначе хаб с сорока проектами отвечает не так, как пустой, самим временем ответа.
Из этого следует форма главной: без токена она показывает не «список только на
просмотр», а экран входа, потому что показывать нечего — 403 приходит с сервера.
Оболочка `/` при этом публична (в ней нет данных, один `<div>` и `<script>`),
иначе браузеру нечем было бы нарисовать сам экран входа.

Оба — под `EDIT_TOKEN`, и токен проверяется **до** того, как хаб посмотрит на
`<id>`: иначе разница между 403 и 404 сама по себе рассказывает, какие задачи
существуют. Несуществующий `<id>`, чужой `<id>` и синтаксически кривой `<id>` дают
**одинаковый** 404 с одинаковым телом — id это единственное, что отделяет лог одного
пушера от лога другого (§3), и ответ, подтверждающий существование, отдал бы половину
этого разделения.

`text/plain` для лога — не косметика: это вывод МОДЕЛИ, а origin тот же, на котором
лежат сборки всех остальных проектов. С `text/html` всё, что сборка напечатала,
стало бы страницей этого origin, которую никто не публиковал.

Лог отдаётся **с тома** на каждый запрос, и это надо читать вместе с 8A.4: том
полностью доступен сборке на запись, так что модель может переписать чужой `log.txt`,
прочитать любой лог мимо HTTP и завести в `data/jobs/` сколько угодно собственных
записей. Разграничение по `<id>` действует на уровне HTTP и НЕ является границей на
уровне тома; границы там нет вообще, и появится она только вместе с отдельным uid или
mount namespace на сборку. Запись при старте разбирается коротко и не
переписывается, кроме застрявших в `queued`/`building` (ниже): что не разобралось,
пропускается с предупреждением в логе.

**Потолка на ЧИСЛО записей при этом нет — и это принятое следствие отказа от ретенции
(§5.3), а не недосмотр.** Сколько записей прочитает один старт, ограничено только тем,
что лежит на томе. Счётного потолка нет потому, что любое число на его месте — это
решение «какие задачи выбросить», а такого решения хаб больше не принимает: удалять
записи некому и незачем.

**Цена этого называется прямо, потому что раньше документ обосновывал ею обратное.**
Каталогов в `data/jobs/` ровно столько, сколько сделала последняя писавшая на том
сборка, и все они читаются целиком: куча на старте растёт примерно 1:1 с местом, которое
записи занимают на диске. То есть сборка, заполнившая том, назначает, сколько памяти
нужно хабу, чтобы подняться. Это
принято, а не решено, и принято ровно потому, что стоит в одном ряду с остальным, что
может сделать сборка, имеющая том на запись (8A.4): она и так может снести чужой каталог
задачи, переписать чужой `log.txt` и просто занять весь том — счётный потолок закрывал
одну грань из нескольких, а платой за него была потеря настоящих записей (см. ниже).
Листинг при этом идёт `os.scandir`, а не `iterdir` (тот материализует все имена сразу),
то есть обход остаётся потоковым: сверх самих записей в памяти держатся только имена их
каталогов.

**И вот чего счётный потолок стоил, пока был, — это и есть та половина размена, ради
которой его не надо возвращать.** Он применялся ДО чтения, по ПОЗИЦИИ, а нечитаемая
запись до реестра не доезжает и одну живую задачу собой не удерживает. Порча N записей у
свежего конца стоила поэтому до N настоящих задач у старого, и сборка выбирала и N, и
какие именно: 20 задач, потолок 5, пять испорченных `job.json` — реестр поднимался
ПУСТЫМ (пятнадцать старых удалены не читая, а прочитанные пять — это ровно испорченные).
Лечилось это срезом не по самому потолку, а по числу записей, которые хаб МОГ написать
сам, — то есть ещё одной подпоркой; без потолка ни подпорки, ни самой потери нет.

**Что делает запись непригодной.** Запись принимается как есть, если выполнено всё
сразу: это JSON-объект; `id` равен имени каталога (а значит, строка формы
`SAFE_JOB_ID`, иначе расхождение указывает запись одной задачи на лог другой); `state`
входит в четыре известных (неизвестное ни идёт, ни закончилось: `_load` такое не
проваливает — он закрывает только `queued` и `building`, — так что хаб отдавал бы
пушеру статус, которого сам никогда не пишет). Иначе каталог пропускается с
предупреждением в логе, где названы он и причина, и **остаётся лежать на томе как
есть** — ретенции нет (§5.3), и он чьё-то свидетельство. Остальные поля не
приводятся и не проверяются: порванной записи хаб сам не пишет (`atomic_write_bytes` —
временный файл, fsync, rename), неконечного числа тоже (`finish` проводит длительность
через `_number`).

**Метки времени при этом не проверяются, и это тоже поменялось
вместе с ретенцией.** Раньше `created` из будущего зажимался в «сейчас» (`_created`,
`_epoch`), потому что дата из 2999 не старше никакого отсечения — она давала записи
иммунитет от возрастного потолка навсегда. Потолка нет, `created` больше ничем не
меряется и ничем не сортируется: это строка, которую видит тот, кто читает запись.
Поэтому обе функции удалены, а не оставлены «на всякий случай» — код, приводящий
значение, которое никто не читает, со временем начинают считать проверкой. Цена названа
честно: подложенная дата из 2999 доедет до пушера в статусе как есть. **Но если на этом
томе что-нибудь снова начнёт МЕРЯТЬ метку — возраст, порядок, что угодно, — оно обязано
сначала ответить на этот вопрос заново**, потому что вернётся ровно тот иммунитет.

Порядка в записи при этом нет вообще — и отдельным файлом он тоже больше не лежит, см.
ниже.

**Обратно на том старт пишет только задачи, застрявшие в `queued`/`building` после
рестарта.** Их провал (`failed` с кодом рестарта) обязан доехать до тома — иначе
следующий старт снова найдёт их незакрытыми и снова проиграет тот же переход, а пушер
по логу решит, что сборка живёт. Остальные записи старт не трогает: ни inode, ни mtime
их `job.json` не меняются. Это ещё и бюджет старта: `_load` работает до привязки сокета,
а каждая запись — два fsync и rename.

**И у этого правила есть вторая половина, которой оно само же и научило: то, что
является свойством НАБОРА записей, нельзя хранить ПО ЗАПИСИ.** Проход пишет записи по
одной, одна запись может не удаться, и доехавший наполовину проход смешивает на томе два
поколения разом — состояние, в котором живой хаб не был НИКОГДА. Свойство набора едет
одной атомарной записью или не хранится вовсе.

**Порядка создания задач при этом нет вообще — ни числом в записи, ни отдельным файлом,
и это решение, а не пропуск.** Порядок существовал ровно ради ретенции: он отвечал на
единственный вопрос «кого подрезать первым». Ретенции нет (§5.3) — вопроса нет, и
`data/jobs/order.json` удалён вместе со всей механикой чтения и записи порядка. Других
потребителей у него не было и нет: эндпоинта со списком задач не существует, `GET
/api/v1/jobs/<id>` и `/log` читают запись ПО ID, а загрузка восстанавливала порядок
только затем, чтобы подрезке было что считать. Заводить его обратно «на всякий случай»
не надо: на писчем для сборки томе файл порядка — это ещё одна вещь, которую сборка
пишет сама и неотличимо от нас, а единственное, что он когда-то покупал (точечный отказ
записи не переставляет реестр), теперь не покупает ничего — переставлять реестр стало не
для чего.

Каталог, в котором записи нет вообще (пустой или с мусором вместо JSON), не удаляется
НИКОГДА — ни сразу, ни по возрасту: старт пропускает его с предупреждением, как любую
непригодную запись. Если запись `job.json` в `create` не удалась (полный том),
`create` удаляет только что созданный каталог и пробрасывает ошибку; хаб, убитый между
`mkdir` и записью, оставляет пустой каталог, и его убирают руками — иначе каталог провисел бы вечно и давал
предупреждение на каждом старте.

**Временные файлы записей реестра (`.wip-*`) пишутся в корень данных, а не в
`data/jobs/` и не в каталог задачи.** Там их собирает `Store._sweep_leftovers` (§7.2),
который обходит корень данных и каталоги проектов; том тот же, так что rename остаётся
rename. Остаток от записи, убитой на полпути, живёт до старта не меньше
`LEFTOVER_MAX_AGE_SECONDS`.

**Заголовки безопасности.** На каждом ответе — `X-Content-Type-Options: nosniff`; на
HTML-страницах самого хаба (из `templates/`) — `Content-Security-Policy: default-src
'self'; img-src 'self' data: blob:; script-src 'self' 'wasm-unsafe-eval'; style-src
'self' 'unsafe-inline'` (`CSP_HTML` в `src/app.py`). Отсюда требование: ни одного
инлайн-скрипта в шаблонах, весь JS страниц — файлами в `/_v/`. HTML-файл из сборки
идёт без этой политики (ниже).

`img-src ... data:` обязателен: `three-cad-viewer.css` держит весь тулбар в 74
свойствах `--tcv-icon-*: url("data:image/svg+xml,...")` (§2.2), а `'self'` схему
`data:` **не покрывает** — с голым `default-src 'self'` браузер молча режет все
иконки и тулбар приезжает пустыми квадратами. `blob:` там же — ради вьювера KiCad
(`/_v/ecad-viewer.js`): иконки его панелей — SVG-спрайт, который он сам собирает в
`blob:`-адрес; без `blob:` браузер отказывает в каждой их загрузке, и при
открытии проекта в консоли около 70 нарушений политики. Скриптов это не
ослабляет: SVG, загруженный как картинка, скрипт не исполняет.

`script-src 'self' 'wasm-unsafe-eval'` — ради того же вьювера: полигоны он
триангулирует модулем WebAssembly, вшитым в его собственный файл, и без этого
ключа компиляция модуля запрещена — вьювер пишет `wasm triangulation unavailable,
falling back to JS earcut` и считает на JS. Ключ разрешает только компиляцию
WebAssembly: `eval` и `new Function` обычного JS, инлайн-скрипты и скрипты с
других адресов по-прежнему запрещены. И `blob:`-картинки, и модули WebAssembly
создают только скрипты самой страницы, то есть файлы из `/_v/`; хаб
однопользовательский, и защиты от враждебного автора этих файлов в политике нет
(§4).

**Content-Type файлов сборки — по белому списку** (`BUILD_CONTENT_TYPES` в
`src/app.py`). `.json` → `application/json`, `.stl`/`.step`/`.stp`/`.3mf` → свои
`model/*`, и каждый тип документа (`render.DOCUMENT_TYPES`) — своим типом: `.md` →
`text/markdown; charset=utf-8`, `.pdf` → `application/pdf`, `.png`/`.jpg`/`.jpeg`/
`.gif`/`.webp` → свои `image/*`, `.html`/`.htm` → `text/html; charset=utf-8`, `.svg`
→ `image/svg+xml`, файлы KiCad `.kicad_pro`/`.kicad_sch`/`.kicad_pcb` →
`text/plain; charset=utf-8`, `.glb` → `model/gltf-binary`, `.zip` → `application/zip`. **Всё остальное** → `application/octet-stream` +
`Content-Disposition: attachment`. Исключение — `meta.json`, который хаб перезаписывает
сам после валидации, и `index.html`, который вообще не берётся из каталога сборки
(см. выше). Ссылаться на них нельзя ниоткуда: `GENERATED_FILES` отвергается в
каждой из точек, где `meta.json` называет файл (§7.1).

**HTML и SVG сборки исполняются как написаны** (решение 2026-10-23, §4): страница
или чертёж, выложенные автором, отдаются своим типом, со скриптами, и HTML-файл
сборки идёт БЕЗ политики хаба — с `default-src 'self'` страница со встроенным
скриптом не работает. Цена названа в §4: такой файл исполняется в том же origin,
что страницы хаба и все проекты; хаб однопользовательский, и пишет в него только
владелец `EDIT_TOKEN`. Страница-оболочка сборки свою политику сохраняет.

### 7.5 Переменные окружения

| Переменная | Обязательна | Назначение |
| --- | --- | --- |
| `EDIT_TOKEN` | да, без дефолта | ЕДИНСТВЕННЫЙ секрет системы |
| `HOST` / `PORT` | нет | по умолчанию `0.0.0.0` / `8000` |
| `DATA_DIR` | нет | по умолчанию `data` |
| `COMMENT_MAX_TEXT_CHARS`, `COMMENT_MAX_PHOTO_BYTES`, `COMMENT_MAX_BODY_BYTES` | нет | потолки на РАЗМЕР комментария, §7A.4. Других нет: ни `COMMENT_MAX_PER_BUILD`, ни `COMMENT_MAX_TOTAL`, ни `COMMENT_RATE_*` больше не существует — решение 2026-08-27, §7A.4 |
| `PROPOSAL_MAX_BODY_BYTES` | нет | по умолчанию 256 KiB — потолок на тело запроса, который сохраняет Proposal проекта. Много меньше комментарийного: в Proposal нет картинок, это несколько десятков строк чисел |
| `LOG_LEVEL` | нет | `INFO` |

**Секрет ровно один, и имя у него не `PUBLISH_TOKEN`.** До шага 0 переменных было
две — `PUBLISH_TOKEN` на приём пуша и `COMMENT_READ_TOKEN` на чтение очереди, — и
схлопнулись они в одну по решению 2026-08-27 (issue #26): «можно делать что
угодно», на систему, а не на проект. Имя выбрано новое, потому что старое врало
задолго до того, как лишилось пары: тем же `PUBLISH_TOKEN` уже открывались
исходники ЛЮБОГО проекта на хабе (§7.8) и маршрут, УДАЛЯЮЩИЙ проект. Переменная с
таким именем читается как «креденшл для CI на пуш» — и ровно поэтому её тянет
отдать CI общей организации, что после переезда (§8A.1) означает выдать
исполнение кода. `EDIT_TOKEN` называет право, а не один из способов им
воспользоваться, и совпадает со словом, которым это же значение уже называет
интерфейс: без него «View only», с ним «Editing on».

**Токен, а не пароль** — хотя человек и вводит его в форму. Это одна общая
строка, сверяемая на равенство; не на человека, не хешируется, отзывается только
вместе со всеми, и кто её предъявил, хаб не записывает. Слово «пароль» обещало бы
аутентификацию, которой нет (issue #26 говорит это прямо), а
`hammerola login` значит «сохрани общий секрет», и ничего сверх.

**Миграция стоит одной строки в compose.** Переименование не трогает тех, кто
публикуется: по проводу едет ЗНАЧЕНИЕ в заголовке `X-Hammerola-Token`, а как
свой секрет называет чужой workflow — его дело.

Часть потолков **не** конфигурируется через ENV и живёт константами — их значения ни
от окружения, ни от проекта не зависят, а лишняя ручка в конфиге, которую никто не
крутит, только даёт возможность выставить её неправильно:

| Константа | Где | Значение | Зачем |
| --- | --- | --- | --- |
| `SOCKET_TIMEOUT` | `app.py` | 30 с | таймаут сокета на соединение. Соединение принимается до проверки токена (токен — в заголовке), так что без таймаута неаутентифицированный клиент держит поток бесконечно — slowloris |
| `MAX_CONCURRENT_PUBLISHES` | `app.py` | 4 | сколько **приёмов** идёт одновременно. Каждый держит тело на диске, tar-ридер и распакованное дерево; ретраи CI нескольких проектов разом — это ровно тот случай, который иначе всё умножает |
| `PUBLISH_WAIT_SECONDS` | `app.py` | 60 с | сколько ждать свободный слот приёма. Дальше — 503 с `Retry-After`, который CI отретраит, а не поток, залипший до таймаута сокета |
| `MAX_CONCURRENT_BUILDS` | `jobs.py` | 4 | сколько **сборок** считается одновременно. ЗАМЕРЕНО на выкатанном хабе 2026-09-09 (145 задач, 20 ядер, load average 0.6) и поднято с двойки. Скорости это число не покупает: сборка фактически однопоточная, ядра простаивают, расширение пула OCCT с 2 до 8 дало ~7%. Покупает оно ИЗОЛЯЦИЮ — все заметные ожидания в очереди (до 513 с) пришли от ДВУХ ЗАВИСШИХ сборок, занявших оба воркера по 891 с каждая. Больше воркеров не ускоряют одну сборку, они не дают одному плохому проекту заморить всех остальных. Ограничение — память, а не ядра: ~450 МБ resident на сборку, четыре штуки укладываются в свободные ~12 ГБ хоста |
| `MAX_QUEUED_JOBS` | `jobs.py` | 16 | сколько пушей ЖДЁТ воркера. Очередь ограничена намеренно: неограниченная превращает «хаб не успевает» в «хаб принял всё, держит по распакованному дереву на запись и отрапортовал CI успех про работу, до которой доберётся через час». 503 с `Retry-After: 60` — правда, и CI уже умеет её обрабатывать |
| `QUEUE_FULL_RETRY_AFTER_SECONDS` | `jobs.py` | 60 с | `Retry-After` при 503 «очередь сборки полна». Больше, чем 30 с у слота приёма, и намеренно: «занята очередь сборки» — это минуты, «занят слот приёма» — секунды |
| `MAX_LOG_BYTES` | `jobs.py` | 3 × `Limits.log_bytes` (3 MiB) | потолок на `log.txt` при записи. **Выведен, а не назначен:** `runner._Drain` держит `log_bytes` СЫРЫХ байт и декодирует их с `errors="replace"`, а недекодируемый байт становится U+FFFD, который кодируется обратно в ТРИ байта. То есть модель, печатающая бинарь, заставляет хаб записать втрое больше того потолка, под которым шла сборка, — и меньшее число здесь означало бы, что хаб отдаёт УСЕЧЁННЫМ свой собственный лог, да ещё и с предупреждением «больше, чем может произвести сборка» |
| `WORKER_JOIN_SECONDS` | `jobs.py` | 5 с | бюджет ВСЕЙ остановки, а не таймаут на поток и не только на join. Ждём **публикацию** (`rename` плюс перекладка указателей — миллисекунды), а не сборку: сборка может идти до `wall_seconds`, а compose не объявляет `stop_grace_period`, поэтому SIGKILL от docker прилетает через 10 с независимо от этого числа. Ожидание длиннее грейс-периода не спасает ни одной сборки — оно только превращает каждую нормальную остановку в SIGKILL. Отсюда и общий дедлайн: помноженный на воркеров, бюджет съедает грейс-период сам по себе — уже при двух, — и растёт вместе с пулом, которому расти по замерам. **Часы запускаются ДО дренажа очереди**, потому что дренаж — это работа на том же томе (до `MAX_QUEUED_JOBS` деревьев на удаление и запись задачи с `fsync` на каждое), и отсчёт после него означал бы «5 с» в комментарии при реальной остановке «дренаж плюс 5 с» — то есть SIGKILL внутри того самого join, ради которого число и подбиралось |
| `WORKER_JOIN_FLOOR_SECONDS` | `jobs.py` | 1 с | пол на join, если дренаж съел бюджет. Итог: остановка ограничена `max(WORKER_JOIN_SECONDS, дренаж + пол)`, а не бюджетом сам по себе, и это честная формулировка — **сам дренаж не обрывается**. Оборвать его нельзя: брошенный на середине, он оставляет ровно те распакованные деревья и неотвеченные задачи, ради которых он и существует (`Store._sweep_leftovers` не увидит их ещё час). Пол при этом никогда не больше бюджета — иначе хаб, перенастроенный на остановку короче пола, получил бы остановку ДЛИННЕЕ заданного числа |

**Параллелизм сборки — отдельное число от параллелизма приёма, и это требование шага
5.** Четыре слота приёма обоснованы телом на диске, tar-ридером и распакованным
деревом; параллелизм СБОРКИ обоснован памятью, а не ядрами (замер 2026-09-09,
issue #80: сборка фактически однопоточная, ядра простаивают, а ~450 МБ resident
на сборку — это то, чего на хосте конечное число). Числа берутся из кода, а не из
прикидки, и с 2026-08-30 они ВЫЧИСЛЯЕМЫЕ, поэтому здесь названы формулами:
`Limits.occt_threads = max(2, min(8, ядра // BUILDS_SHARING_THE_HOST))` — на
20-ядерном хабе это 5, — а `Limits.cpu_seconds = wall_seconds × occt_threads ×
1.25` против `Limits.wall_seconds = 300` (см. §8A.2 шаг 4), то
есть потолок разрешает до 1.25 процессорной секунды на секунду стены НА ПОТОК — отношение
сохранено НАМЕРЕННО: ниже `wall_seconds × occt_threads` потолок CPU перестаёт быть
страховкой и становится связывающим, убивая ядром здоровую параллельную сборку
внутри её же стенных часов — суммарно по потокам, потому что `RLIMIT_CPU` суммарный. Общее число
означало бы, что в день,
когда один из двух потолков перенастраивают по замерам, второй уезжает вместе с ним —
и восстановить, почему он там оказался, будет уже не по чему. По той же причине у
очереди сборки собственный `Retry-After` (60 с против 30 с у слота приёма): «занята
очередь сборки» — это минуты, а «занят слот приёма» — это секунды.

### 7.6 Локальный слот: публикация с ноутбука

Автор правит `model.py`, гоняет сборку и хочет увидеть результат **сейчас**, не делая
коммит. Коммита у такой работы нет, а вся адресация сборок построена на нём.

```text
POST /api/v1/publish/<pid>/dev
X-Hammerola-Token: <EDIT_TOKEN>
Content-Type: application/gzip
<тело: тот же gzip-сжатый tar, что у обычной публикации>
```

Всё, кроме двух вещей, — обычная публикация: та же валидация, та же распаковка в
staging, тот же атомарный swap, те же коды ответа. Различий ровно два: куда сборка
ложится и что после этого **не** происходит.

**Слот, а не сборка.** У проекта ровно один каталог `data/project/<pid>/dev/`, и каждый
пуш перезаписывает его целиком:

```text
data/project/<pid>/latest -> <commit>   СИМЛИНК на новейшую ревизию
data/project/<pid>/dev/                 КАТАЛОГ: то, что сейчас на экране автора
data/project/<pid>/<commit>/            неизменяемая сборка
```

Локальная работа — это не версия проекта, это состояние рабочей копии. Семнадцатая
попытка за вечер не «сборка №17», она просто то, что сейчас на экране, — как nightly.
Поэтому `dev` один, как `latest` один, и истории у него нет.

**Коммит кладёт себя в слот тоже** (issue #78, вместе с #20). Раньше слот
перезаписывал только `build`, и это оставляло состояние, в котором ссылка `dev`
показывает геометрию СТАРШЕ, чем `latest`: автор собрал, посмотрел, закоммитил — и
слот остался на предпоследней правке, молча, без единого признака, что он отстал.
Слот теперь означает «самое свежее, что хаб знает про этот проект», а не «последний
вызов `build`», и цена этого — ровно копия дерева ревизии: тот же swap, тот же
`.trash-`, ничего не валидируется второй раз. `meta.json` в слоте отличается от
`meta.json` ревизии тремя ключами: `commit`, `dev` и `job` (`render.build_meta`).

**`job` — память слота о сборке, которая его заполнила** (issue #79). Лога под именем
слота не хранится и храниться не может: лог лежит по ревизии, а слот ревизией не
адресуется. Но джоба, собравшая слот, свой лог отдаёт и дальше, поэтому одно поле с её
id превращает неотвечаемый адрес в поиск: `hammerola log dev` читает
`/api/v1/jobs/<id>/log` и печатает лог ровно той сборки, чья геометрия сейчас на экране.
Поле пишут оба пути — и `build`, и коммит, который копирует себя в слот, — а `commit` в
записи джобы говорит, какой это был push. У ревизии этого ключа нет. Отсутствие id —
не ошибка нигде: слот, записанный без него, остаётся опубликованным слотом, а клиент
про это говорит отдельной фразой.

| Код | Когда | Тело |
| --- | --- | --- |
| 201 | слот перезаписан | `{"url": "/project/<pid>/dev/"}` |
| 200 | в слоте ровно эти байты | то же |

Остальные коды — как у §7.

**Почему перезапись под одним URL здесь допустима.** Каталог коммита отдаётся с
годовым `immutable` (`public` у JSON и PNG, `private` у остальных файлов), и
перезапись такого URL сделала бы все розданные годовые кэши враньём, безотзывно — ровно поэтому §7 отвечает 409 на тот же
коммит с другим содержимым. Слот отдаётся `no-cache` — и страница, и все файлы внутри, —
поэтому обещания, которое можно нарушить, там просто нет. Это единственное, что делает
всю схему корректной, и `no-cache` на `<pid>/dev/**` — инвариант, а не настройка.

Отвергнутый вариант — **id от содержимого**, `dev-<12 hex sha256 нагрузки>`.
Он честно решал проблему кэша: каждая попытка получала свой неизменяемый URL. Но
следствие было хуже болезни — каждая попытка становилась отдельной сборкой, попадала в
`builds.json` и в переключатель рядом с настоящими коммитами (`dev-e9a448df778c`,
похожий на хеш, которого нет ни в одном репозитории), и оставалась там навсегда:
семнадцать вечерних попыток в списке версий проекта, из которого ничего не удаляется
(§5.3). Верный вывод из «неизменяемый URL нельзя перезаписывать» — **не отдавать
локальную сборку по неизменяемому URL вообще**, а не версионировать её.

**Идемпотентность осталась, но стала внутренней деталью.** Дайджест полезной нагрузки
(по именам и содержимому членов архива, без переписанного `meta.json`) сравнивается с
тем, что лежит в слоте: совпал — 200 и ни одной записи на диск. Смысл теперь не в
адресации, а в том, чтобы пересборка без изменений не дёргала страницу, которая открыта
перед автором. Ничего в URL из дайджеста не выводится.

**Публикация атомарна.** POSIX не умеет заменить непустой каталог под фиксированным
именем одним шагом (`rename` на каталог проходит только если целевой пуст), поэтому
swap — это: распаковать в скрытый `.tmp-…`, переименовать старый слот в сторону,
переименовать новый на его место, удалить старый. Читатель никогда не оказывается
внутри каталога, который наполняют; на ширину одного syscall он может застать имя
отсутствующим — это цена того, что слот **есть** сборка, а не симлинк на неё, и ровно
поэтому `latest`, который живёт в чужих чатах, устроен наоборот.

**`latest` не двигается, и карточки у слота нет.** `latest` — ссылка, которую кидают
людям, и она обязана значить «состояние на коммите»; незакоммиченная работа с одной
машины, двигающая её, ломает это обещание задним числом для всех, кому ссылку уже
дали, и отозвать её нечем. Главная — то же самое там, где смотрят все. Проект, у
которого есть только локальная сборка, не имеет ни карточки, ни `latest`: из коммита не
опубликовано ничего, и придумывать этому ссылку нечестно.

Сам файл `index.json` локальный пуш при этом ПЕРЕПИСЫВАЕТ, и это не противоречие:
карточка несёт флаг `dev` — «у проекта есть незакоммиченная работа», — и он должен
появляться тогда, когда появляется такая работа, а не на следующем коммите. Флаг не
говорит, ЧТО в слоте: коммит, заголовок, число деталей и время на карточке
по-прежнему берутся из последней коммит-сборки.

**«Слот занят» и «в слоте незакоммиченное» — с issue #78 это два разных вопроса, и
флаг карточки отвечает на второй.** Пока слот заполнял только `build`, они совпадали,
и флаг считался как «каталог `dev/` существует». Теперь слот есть у каждого проекта,
который хоть раз коммитил, — и такой флаг стоял бы у всех, то есть не различал бы
ничего. Считается он сравнением дайджестов полезной нагрузки: `.payload.sha256` в
слоте против того же файла в каталоге, на который смотрит `latest`. Совпали — в слоте
ровно опубликованное, флага нет; не совпали, не прочитались или коммита нет вовсе —
флаг есть. Нечитаемый дайджест толкуется в пользу флага намеренно: это тот же ответ,
который карточка давала до #78, когда слот означал незакоммиченную работу сам по себе.

**Слоту нечем копиться, и настраивать под него нечего.** Ретенции нет ни у кого (§7.3),
но у слота её нет ещё и по собственной причине: он ровно один каталог, и каждый пуш
перезаписывает его целиком, так что объём локальной работы не растёт вообще — ни от числа
попыток за вечер, ни со временем. Это единственное место в хабе, где что-то на томе
уменьшается само.

**Резервирование имён.** Занято ровно два имени, `latest` и `dev`: первое — симлинк,
второе — каталог слота, и оба ещё и последний сегмент маршрута публикации (`resolve`
зарезервирован отдельно и только для comment-API, §7A.2). Префикс `dev-` **не
зарезервирован**: он был нужен только отвергнутому варианту с `dev-<хеш>` выше — там
локальные сборки становились настоящими сборками, их приходилось отличать от коммитов и
считать отдельно, и коммит с именем `dev-1234` попадал бы не в ту кучу. Варианта нет —
`dev-1234` теперь обычный коммит с обычным вечным URL.

**Что видно снаружи.** В `builds.json` локальной сборки нет ни в каком виде: `builds` —
это история коммитов. Рядом со списком лежат два ответа про **имена** — `has_dev`
(занят ли слот) и `latest` (на какой коммит он сейчас смотрит), чтобы переключатель
сборок мог предложить их как отдельные пункты и не предлагал того, чего нет. `has_dev`
намеренно остался вопросом «слот ЕСТЬ» и НЕ считается как флаг карточки. Читают его
переключатель во вьювере, который решает, предлагать ли пункт `dev` вообще; резолвер
`/project/<pid>/` (`static/_v/pointer.js`), который по нему решает, отправить ли
запомнившего `dev` читателя в слот или откатить на `latest`; и `hammerola status` с
`hammerola rm` (`hammerola/admin.py`), которые докладывают, есть ли слот, — второй в
подтверждении удаления. Числа здесь нет намеренно: счёт читателей устаревает молча, и
его не держит ни одна проверка. Ответь `has_dev` «в слоте есть незакоммиченное» —
вьювер спрятал бы ссылку, которая прекрасно открывается, резолвер увёл бы читателя с
прекрасно открывающегося `/dev/` на `latest`, а CLI назвал бы занятый слот пустым. В
самом `meta.json` сборки флаг `dev` остался: `commit` там читается как `dev` — имя
слота — и без флага страница напечатала бы `dev` там, где ждут хеш коммита.

Комментарий (§7A) на слот оставить можно: `POST /api/v1/comments/<pid>/dev` — это
единственное имя-указатель, которое принимается как цель. Довод раньше был «весь его
зритель — тот, кто прямо сейчас смотрит на экран автора»; после шага 0 писать в
очередь и так может только держатель `EDIT_TOKEN`, то есть сам автор, — и маршрут от
этого не стал бесполезным: заметка «вот эта деталь в том, что сейчас на экране»
остаётся ровно тем, ради чего слот и существует. `latest` целью не принимается:
завтра это другая сборка, и комментарий перестал бы называть геометрию, о которой
он был.

## 7A. Комментарии к сборке

Тот, у кого есть `EDIT_TOKEN`, тыкает в деталь на модели, пишет «поправь вот
тут», прикладывает фото. Комментарий копится в очереди хаба. Агент читает очередь
через MCP и правит `model.py` в репозитории проекта.

**Посылка сменилась в шаге 0: это заметка агенту, а не публичный канал.** Раздел
писался про ЗРИТЕЛЯ — «тыкает и пишет», без всякого токена, — и это отменено
решением §8A.1: хаб теперь исполняет присланный код, и анонимная запись в
очередь, которую агент разбирает как задачи, была дорожкой до выполнения кода, не
требующей ни одной уязвимости. Кому выдаётся право писать, решено просто: тому
же, кто публикует, потому что секрет один на систему (issue #26). Да, если
писать может только автор модели, фича вырождается в заметку самому себе — и
именно так она теперь и называется; ценность её не в том, что пишет посторонний,
а в том, что якорь (§7A.1) переводит «вот эту деталь» в имя, за которым стоит
функция.

**Отвергнуто: issue в Gitea.** Один из двух доводов при этом отпал вместе с
анонимной записью: «публичная страница не должна иметь права писать в трекер»
больше не про нас. Остаётся второй — трекер под это избыточен; плюс issue требуют
аккаунта в форже, так что схемы всё равно не эквивалентны. Очередь в хабе даёт
агенту то же самое и оставляет место, где мусор можно отсеять, ничего не ломая.

### 7A.1 Якорь

Что несёт комментарий, помимо текста:

| Поле | Откуда | Зачем |
| --- | --- | --- |
| `pid`, `commit`, `view` | URL страницы | какая сборка и какой вид |
| `published` | страница, из `meta.published` открытой сборки | какая именно сборка: в локальном слоте `commit` — константа `dev` (§7.6), и только этот штамп отличает одну пересборку слота от следующей, поэтому точную координату страница берёт лишь при совпадении `published`. Присылает штамп именно СТРАНИЦА, а не хаб: каталог слота хранит последнюю собранную ревизию, а не ту, на которую смотрел читатель, — слот успевает пересобраться между кликом по детали и нажатием Send, и хаб, прочитав `meta.json` в момент POST, проштамповал бы координату чужой сборкой |
| `part` | пикинг во вьювере | путь до узла в дереве ТОЙ ревизии: где именно ткнули |
| `key` | ключ каталога того же листа | **главное**: identity детали, переживающая пересборку, — ведёт к записи каталога и дальше к функции в `model.py` |
| `point` | raycast, `[x, y, z]` | «рядом вот с этим местом» |
| `normal` | нормаль сетки выбранной детали в точке клика: луч через клик, иначе луч вдоль взгляда через точку пикера, иначе ближайший к этой точке треугольник; без сетки — `faceNormalAt`; развёрнута к камере, `[x, y, z]` или `null` | направление, по которому стрелка комментария торчит из грани; как и `point`, верна только на своей сборке, на других стрелка идёт сверху вниз (§4) |
| `camera` | `getCameraPosition`, `getCameraQuaternion`, `getCameraTarget`, `getZoom` | ссылка открывает ТОТ ЖЕ кадр |
| `photo` | загружает человек | фото напечатанной детали — то, чего в модели не видно |
| `shot` | `pinAsPng` вьювера | рендер текущего вида, достаётся бесплатно |

Про ожидания: **точка в пространстве не указывает на строку кода**. Полезен
прежде всего `key`, и путать его с `part` нельзя: `part` — это **путь до узла в
дереве вида** (`/model/pin(2)`), а не имя строки, которую видит читатель, и не
ключ каталога; имя листа даёт тесселятор — а листу-мешу его даёт сама сборка
(`_mesh_leaf`), тем же правилом — и повторы одного имени разводятся в `pin`,
`pin(2)`, чтобы пути оставались уникальными. Ключ каталога `parts()` едет
на каждом листе файла вида (`shaped_document` в `src/cadbuild/views.py`; хаб
сверяет это поле с каталогом `parts`, см. §7.1), и комментарий несёт его САМ,
полем `key`. Поэтому дорога к функции — прямая: ключ → запись каталога → то, что
её строит, без похода в файл вида за листом. Опираться на равенство двух ИМЁН
нельзя: ровно эту опору issue #75 и убрал. Координата работает как уточнение «в
этом углу детали», не более. Это ограничение, а не недоделка.

### 7A.2 API

```
POST /api/v1/comments/<pid>/<commit>              требует EDIT_TOKEN
    multipart/form-data: поле `comment` (JSON), необязательное поле `photo`
    201 {"id": "..."}   403 без токена  404 такой сборки нет
    413 слишком большой  422 битый JSON или неподдерживаемый тип фото
    429 не бывает: числа комментариев никто не считает, частоту не ограничивает
    (§7A.4)

GET  /api/v1/comments?project=&status=&since=     требует EDIT_TOKEN
GET  /api/v1/comments/<id>                        требует EDIT_TOKEN
GET  /api/v1/comments/<id>/photo                  требует EDIT_TOKEN
POST /api/v1/comments/<id>/resolve                требует EDIT_TOKEN
```

**Очередь непублична целиком — и на чтение, и на запись.** Асимметрии больше нет,
и она была здесь до шага 0: запись была открыта всем, кто знает URL.

Про ЧТЕНИЕ довод не менялся: очередь — сырой ввод, он может быть мусорным,
дублирующимся или оскорбительным, и раздавать его всем значит превратить витрину
проектов в доску объявлений.

Про ЗАПИСЬ довод новый и он из §8A.1: хаб теперь ИСПОЛНЯЕТ присланный код, а
значит анонимная запись была первым шагом дорожки, не требующей ни одной
уязвимости, — комментарий пишется без токена → попадает в очередь → агент читает
его через MCP как задачу → агент правит `model.py` → хаб исполняет `model.py`.
Закрывается первый шаг: он единственный из пяти, который вообще можно закрыть, не
отменяя самой фичи.

**Токен проверяется ПЕРВЫМ**, до маршрута и до `Content-Length`. Иначе
неаутентифицированный отправитель по-прежнему заставляет хаб принять двадцать
мегабайт и разобрать их как multipart — ровно ту работу, ради отказа от которой
потолки и существуют. (В прежней редакции здесь стоял ещё и рейт-лимит: «до
маршрута, до рейт-лимита и до `Content-Length`». Рейт-лимита больше нет, §7A.4.)

### 7A.3 Хранение

```
<data>/comments/<pid>/<id>.json      комментарий
<data>/comments/<pid>/<id>.<ext>     фото, если приложено
```

**Вне каталога сборки, и это намеренно.** Довод не про выживание — сборки не удаляются
вовсе (7.3), — а про ПРАВА и про кэш. JSON и PNG каталога сборки раздаются
анонимно, остальное — по токену или ключу из ссылки, всё с годовым `immutable` (3.2),
а очередь комментариев не публична на чтение (7A.2): это сырой ввод от кого угодно,
и место его хранения не должно совпадать с местом, которое хаб отдаёт всем.
Ошибка там ещё и необратима — комментарий, уехавший под годовой кэш, не отзывается.
Плюс комментарий привязан к ПРОЕКТУ, а не к каталогу одной ревизии — но держится
эта привязка на `key`, а не на `part` с координатой. Путь до узла (§7A.1 — это
`part`, а не имя строки и не ключ каталога) пересборка вправе перенумеровать, а
координата верна только на той геометрии, с которой её сняли: и то и другое
значит что-то ровно на своей ревизии. Через десять коммитов ту же сущность
называет КЛЮЧ КАТАЛОГА (issue #75) — по нему страница сборки находит деталь
заново, а когда такого ключа в каталоге больше нет, комментарий осиротел, и лента
говорит об этом прямо. Поэтому `<data>/comments/<pid>/` — естественный дом
очереди.

**Каталог растёт без потолка, и это принято.** Ни на число комментариев в
проекте, ни на число во всём хабе ограничения нет (§7A.4, решение 2026-08-27), и
удаляется отсюда ровно одно: очередь проекта целиком, когда удаляют сам проект
(`CommentStore.remove_project`) — иначе комментарии остались бы висеть на
`<pid>/<commit>`, которого никто не может открыть. Отдельный комментарий не
удаляется ничем: обработанный закрывается через `resolve`, который оставляет и
запись, и заметку. Это тот же размен, что в §5.3, и в тех же единицах — JSON-файл
и фотография против механизма, который надо написать и который умеет удалить не
то.

### 7A.4 Запись под токеном — что обязано быть и после этого

Раздел назывался «Публичная запись — что обязано быть» и перечислял, чем
огораживают эндпоинт, открытый всем, кто знает URL. Такого эндпоинта больше нет
(§7A.2, шаг 0). Список пришлось перебрать по одному пункту, и линия разреза
прошла по вопросу «а этот пункт вообще про отправителя?»: **всё, что про БАЙТЫ,
осталось; всё, что про ЧИСЛО и ЧАСТОТУ, ушло.** Первое не становится безопасным
от того, что у отправителя есть креденшл, — работа над телом остаётся работой.
Второе без анонимного отправителя оказалось ни про что.

Что осталось:

- **потолок длины текста и потолок размера фото**. Разбор с неограниченным телом —
  это работа, которую заказывает кто-то другой; у пуша проекта потолка размера нет
  (§4), а фото хаб сохраняет как пришло — две разные величины и разные поводы;
- **тип фото определяется по магическим байтам, не по расширению и не по
  `Content-Type` из запроса**. Это про ВЫДАЧУ: байты возвращаются на том же
  origin, где лежат сборки всех остальных проектов;
- **SVG отвергать.** Это активный контент, а не картинка: у нас уже есть ровно
  такая находка по загруженным файлам сборки (ревью, §5);
- текст комментария **попадает в DOM только как текст и никогда как разметка**.
  До задачи #33 здесь стояло «не рендерится вообще»: единственным потребителем
  текста был агент, и граница XSS держалась на том, что читателя у текста на
  странице нет. Читатель появился — рейка рисует всю очередь проекта, — и
  граница переехала, а не исчезла: React экранирует строку, `innerHTML` и
  подстановки в разметку на этом пути запрещены, и это закреплено тестом
  (`ui/tests/feed.test.js`, «draws the text and the anchor as TEXT on the
  page»), а не обещанием. Ответ на POST по-прежнему несёт один только `id`:
  эха текста в ответе нет и не нужно.

**Ограничителя частоты нет, и потолков на ЧИСЛО комментариев нет** — решение
2026-08-27. Три механизма исчезли разом: `COMMENT_MAX_PER_BUILD`,
`COMMENT_MAX_TOTAL` и рейт-лимит по адресу вместе со всем разбором
`X-Forwarded-For`, который его обслуживал. Это не «убрали, чтобы было проще»;
довод, на котором они стояли, кончился.

**Дверь теперь одна, и она под секретом.** Все три были написаны против
анонимного спама: писать мог кто угодно, кто знает URL, и вопрос стоял «как
ограничить постороннего, не зная о нём ничего». Шаг 0 закрыл этот вопрос целиком
— запись требует `EDIT_TOKEN` (§7A.2). А `EDIT_TOKEN` — единственный секрет
системы (§7.5): кто его предъявил, тот публикует сборки, переименовывает проект,
читает исходники любой ревизии и вызывает `DELETE /api/v1/projects/<pid>`, то
есть стирает проект вместе со всей его очередью комментариев одним запросом.
**Ограничивать частоту тому, кто и так может стереть проект, бессмысленно** — это
не защита, а способ отказать в шестом комментарии одного ревью. Прежняя причина
ушла вместе с анонимным отправителем, а новую придумывать не стали.

Отдельно про потолки на число, потому что у них была своя, отдельная роль
«СТЕНЫ»: комментарии не удаляются (§5.3), так что сборка, добравшая
`COMMENT_MAX_PER_BUILD`, комментироваться не могла бы больше никогда. Это худшая
форма потолка из возможных — не «выбросим старое», а «дальше нельзя», причём
навсегда и без способа починить. Ушли они по тому же решению, по которому нет
ретенции нигде (§5.3): комментарий — это JSON-файл и фотография, десятки
мегабайт на том, который и так растёт монотонно, и цена механизма выше цены
места. Ровно поэтому и **рейт-лимит перестал что-либо покупать**: единственное,
чем он оправдывался после шага 0, — «это единственный самозалечивающийся потолок,
он ловит зациклившегося клиента ДО того, как тот сожжёт сотню слотов сборки
навсегда». Слотов больше нет, жечь нечего, сторожить нечего.

Что при этом НЕ отменено и не должно быть отменено заодно: **потолки на размер**
(тела запроса, вложения, полей) — они про работу, которую хаб делает над телом, а
не про ретенцию; **проверка типа вложения по первым байтам** и **отказ от SVG** —
они про исполняемый контент, отдельная история. Число и размер — разные вопросы,
и ответ на один не является ответом на другой.

Одна вещь при удалении потеряна, и её стоит записать, чтобы не переоткрывать
дорогой ценой, если адрес клиента когда-нибудь понадобится снова (в логе,
например): **из `X-Forwarded-For` читается ПРАВАЯ запись, а не левая.** Каждый
прокси ДОПИСЫВАЕТ адрес, с которого принял соединение, значит при одном доверенном
прокси перед нами (Traefik) последняя запись — то, что прокси действительно
видел, а всё, что клиент вписал сам, приезжает ЛЕВЕЕ и должно игнорироваться.
Чтение левой записи — обычный способ это написать — даёт отправителю новую запись
на каждый запрос. И сам заголовок читается только тогда, когда пир — доверенный
прокси; при прямом доступе там ровно то, что напечатал отправитель.

Отменённых требований, таким образом, четыре, и все стоит назвать, чтобы не
восстановили: **«эндпоинт открыт всем, кто знает URL»**, потолок на сборку,
глобальный потолок и рейт-лимит. Всё остальное в списке пережило смену посылки,
потому что было выведено не из неё.

### 7A.5 MCP для агента — эндпоинт В ХАБЕ, не отдельный сервис

`POST /mcp`, авторизация заголовком, тем же `EDIT_TOKEN`. Инструменты:

- `list_comments(project?, status?, since?)` — очередь;
- `get_comment(id)` — комментарий целиком, включая фото;
- `resolve_comment(id, note)` — пометить обработанным, чтобы агент не разбирал
  один и тот же дважды.

**Первым решением был отдельный MCP-сервер, и это было ошибкой.** Обоснование
звучало как «хаб должен остаться чистым HTTP-сервисом», то есть как принцип, за
которым ничего не стоит. Разваливает его само устройство протокола: MCP работает
поверх HTTP (`type=http`, путь `/mcp`, авторизация заголовком) — это штатный
транспорт, а не экзотика. Значит отдельный сервер был бы **чистым прокси над HTTP
API хаба**: лишний деплой, второй токен, второй репозиторий, который обязан
догонять каждое изменение схемы комментария.

Данные лежат в хабе, авторизация в хабе, доменная модель в хабе. Эндпоинт
переиспользует всё это и не добавляет ни одного нового класса риска: на этом
origin аутентифицированные эндпоинты уже есть.

**Цена, которую надо принять осознанно.** `src/` намеренно держится на stdlib
поверх pydantic и loguru — ревью специально вынесло `httpx` в dev-зависимости,
чтобы это свойство сохранить. Тянуть ради трёх инструментов SDK `mcp` — значит
его потерять. MCP поверх HTTP это JSON-RPC 2.0 с маленьким набором методов
(`initialize`, `tools/list`, `tools/call`), поэтому пишем руками на stdlib.
Взамен мы сами отвечаем за соответствие спеке: **зафиксировать в коде, какую
ревизию протокола реализуем**, и сверяться с ней при обновлении.

### 7A.6 Что придётся вернуть во вьювере

`selectTool` выключен (см. коммит про редакторы внешнего вида), а **без пикинга
ткнуть в деталь нельзя**. Включать его в режиме комментария, а не постоянно:
в обычном просмотре выделение деталей зрителю не нужно.

## 7B. Разрез по грани

Инструмент для ЧЕЛОВЕКА, а не данные для агента. Section analysis из Fusion:
посмотреть, что внутри непрозрачной детали. Ничего не сохраняется, в комментарий
не уезжает, агент об этом не знает и знать не должен.

Ткнул в грань — она задала **ориентацию** плоскости. Дальше плоскость возится
мышью туда-сюда. Ползунки остаются индикатором положения, а не способом
управления: управлять ими и есть та неудобная часть, ради которой это делается.

Что уже даёт библиотека:

| Шаг | API |
| --- | --- |
| поставить плоскость по грани | `setClipNormal(index, normal, value)` — нормаль **произвольная**, оси в `resetClip` это лишь дефолты |
| двигать рез | `setClipSlider(index, value)` → внутри `clipping.setConstant` + перерисовка |
| прочитать текущее | `getClipSlider(index)` |
| разрез по взгляду | `setClipNormalFromPosition(index)` — уже готовое, стоит вывести кнопкой |

Чего библиотека НЕ даёт и что надо сделать самим:

- **Нормаль грани.** Пикер работает по id-буферу на GPU и возвращает точку, но
  не нормаль. Нужен обычный three.js `Raycaster` по тому же экранному пикселю,
  `intersection.face.normal`, переведённая в мировые координаты матрицей объекта.
- **Фильтр по типу.** Пикер разрешает приоритет **вершина > ребро > грань**.
  Для разреза нужна именно грань, иначе клик рядом с ребром даст чужую нормаль —
  у `pickAt` для этого есть `topoFilter`.

Два края, на которых это ломается, если сделать наивно:

1. **Система отсчёта слайдера.** `value` — константа плоскости в мировых
   единицах, но `resetClip` ставит её в `gridSize / 2`, то есть ноль привязан к
   сетке, а не к началу координат. `value` для клика надо вычислить как проекцию
   точки на нормаль **в той же системе**, а не подобрать. Промах виден сразу:
   плоскость прыгает в сторону от того места, куда ткнули.
2. **Вырожденное направление.** Перетаскивание мапится на экранную проекцию
   нормали. Когда нормаль смотрит почти в камеру, проекция вырождается и
   чувствительность уходит в бесконечность. Нужен потолок и минимальная длина
   проекции, ниже которой перетаскивание игнорируется.

### 7.7 Идентификатор ревизии: хеш исходников

**Ревизию именует хаб, и имя — это её содержимое.** `POST /api/v1/publish/<pid>`
без последнего сегмента: пушер не знает, под каким именем публикует, потому что
имени у него нет. `hammerola commit` значит «опубликуй версию этого», а не
«опубликуй под таким-то именем».

**Раньше имя приходило из git HEAD, и это было ошибкой в постановке.** Клиент
читал HEAD, отказывался публиковать грязное дерево и предлагал `--allow-dirty`.
Вся эта механика убрана: она отвечала на вопрос, которого никто не задавал.
Публикация версии — не свойство репозитория; каталог с `project.json` может её
сделать, репозиторий он или нет.

**Что именно чеканится.** `Store.mint_revision` возвращает `_payload_digest` —
sha256 по `{путь: sha256 содержимого}` всех членов архива, отсортированным по
пути. Тот самый отпечаток, на котором с шага 5 стоит идемпотентность
(`Store.settled`): второй механизм не заводился, взят существующий. Отпечаток по
построению не зависит ни от порядка членов в tar, ни от mtime, ни от прав, ни от
порядка обхода файловой системы — сортировка и хеш содержимого, больше ничего. Это
и позволяет двум машинам получить один адрес для одного дерева; клиент со своей
стороны пакует воспроизводимо (`pack._scrub` зачищает uid/gid/mode/mtime,
`pack.collect` сортирует), но хеш и без этого устойчив — он считается по
распакованному, а не по байтам архива.

**Почему не порядковый номер.** Номер читается человеком, и это единственное, что
он даёт. Взамен у публикации появляется состояние, которого сейчас нет: номер надо
где-то хранить, выдавать под локом и разводить два одновременных пуша, — а «те же
исходники — та же ревизия» становится проверкой, которая может разойтись с
идентификатором. С хешем это тождество: одно дерево не может получить два адреса.

**Полный хеш, не префикс.** sha256 в hex — ровно 64 символа, `SAFE_ID` разрешает
ровно 64, первый символ hex всегда буквенно-цифровой: влезает впритык, обрезать
нечего. Экономия длины URL ничего не покупает (в имени и так были 40 hex-символов
от git, и URL копируют, а не набирают), а платить пришлось бы вероятностью
коллизии: при n ревизиях и b оставленных битах она примерно n²/2^(b+1), то есть
~3e-8 для 64-битного префикса на миллионе ревизий. Мало — но цена события не мала
и не чинится: два разных дерева уехали бы на один URL, второе получило бы 409
навсегда, а другого имени у пушера нет, он их больше не выбирает.

**Что стало с 409.** «То же имя, другое содержимое» на этом маршруте невозможно по
построению: другое содержимое — другое имя. Мёртвым кодом ветка при этом не стала,
и это стоит держать в голове.

- На **именованном** маршруте (`<pid>/<commit>`) 409 — обычный случай, каким и был:
  маршрут жив, под ним публикуют репозитории моделей со старым `publish.yml`
  (§8A.2, шаг 7).
- На **чеканящем** — 409 остаётся ответом на каталог, который существует под этим
  именем, но не несёт читаемого `.payload.sha256`. `data/` — том, куда любая сборка
  пишет куда угодно (§8A.4): недописанный каталог, файл, снесённый чужой сборкой,
  проигранная гонка на unlink. Сравнивать тогда не с чем, а 200 объявил бы
  состоявшейся публикацию, которая могла не дойти.

**Связь с git односторонняя, и это следствие порядка действий.** Сначала
публикуем, потом коммитим — значит хаб физически не может знать git-sha (коммита
ещё нет), а сообщение git-коммита хеш ревизии знает. Поэтому после успешного
`hammerola commit` клиент **предлагает** команду:

```
git add -A && git commit -m '<то, что дали в -m>' -m 'hammerola-revision: <hex>'
```

Предлагает — печатает готовую строку и останавливается; ни `add`, ни `commit` он не
выполняет. Предложения нет, если git отсутствует (публикация от него не зависела) и
если коммитить нечего (команда бы упала). Сообщение из `-m` идёт через
`shlex.quote`: оно приходит от пользователя и попадает в командную строку, которую
он скопирует, так что кавычки, `$(...)` и обратные кавычки обязаны доехать текстом.
Обратной ссылки — из ревизии в git — нет и не будет: она потребовала бы второго
запроса после коммита, а ревизия неизменяема и выдана с годовым `immutable`.
(С issue #67 у второй половины этого довода есть оговорка — `message` в
`meta.json` переписать можно, см. §3.2. Первая половина от этого не слабеет:
довод держится на лишнем запросе после коммита, а не на том, что записать
физически некуда.)

**В ответе два идентификатора, и они про разное.** 202 несёт `job` — это ЗАДАЧА
(ход сборки и её лог, непредсказуемая, живёт одну попытку) — и `revision` — это
РЕВИЗИЯ (что будет опубликовано, вечная, попадает в URL). Один и тот же исходник,
посланный дважды, даёт две разные задачи и одну ревизию; ровно в этом смысл схемы.

### 7.8 Код ревизии: хаб хранит исходники и отдаёт их под токеном

Решение и его обоснование — issue #17. Здесь — как это устроено.

**Раскладка на томе.** Отдельное дерево рядом с `project/`, а не внутри каталога
сборки:

```text
data/sources/<digest>/source.tar.gz   тело пуша, байт в байт
data/sources/<digest>/log.txt         что напечатала сборка этой ревизии
data/.body-<uuid>                     то же тело, пока идёт сборка
```

**Не внутри каталога сборки** — потому что тот раздаётся по адресу или по ключу из ссылки и с
годовым `immutable`: ошибка там необратима, розданные копии не отзываются. Из `sources/`
наружу ведёт ровно один маршрут (ниже), а раздача файлов туда не дотягивается
вовсе — `_safe_build_path` смотрит только внутрь каталога сборки.

**Адрес — это содержимое.** `<digest>` — тот же `_payload_digest`, которым
чеканится имя ревизии (§7.7), так что адрес кода и имя ревизии — одна строка. Из
этого следует всё остальное и ничего не приходится проверять отдельно: то же
дерево, посланное дважды, не может лечь вторым архивом; лежит тот файл, который
приехал ПЕРВЫМ, — тела двух пушей одного дерева не обязаны совпадать побайтово
(gzip-заголовок), а менять архив под уже опубликованной ревизией нельзя. На
**именованном** маршруте (`<pid>/<commit>`) код тоже хранится, но по дайджесту, то
есть НЕ по имени из URL сборки: маршрут доживает до шага 7 (§8A.2), и заводить
ради него второй способ адресации незачем.

**Кладётся только после состоявшейся публикации.** Исходники провалившейся сборки
не хранятся: автор видит отказ сразу же, как только вернулась команда, и дерево
лежит у него на диске; хабу хранить нечего и незачем, а лежащее в `sources/`
дерево, за которым не стоит опубликованной ревизии, — это ревизия, за которую
хранилищу нечем отвечать. Отсюда инвариант, который и надо держать: **архив есть
тогда и только тогда, когда есть опубликованная ревизия.** Локальный слот `dev`
исключён по той же причине — он не ревизия (§7.6): истории у него нет, следующий
пуш его затирает, возвращаться не к чему. Как только то же дерево публикуется
ревизией, дайджест тот же и архив ложится.

**Тело живёт до конца сборки.** Спул `data/.upload-<uuid>` принадлежит потоку
запроса и удаляется им всегда; принятый пуш переименовывает его в `.body-<uuid>`,
и дальше владелец — задача, ровно как у распакованного дерева `.src-<uuid>`.
Публикация переносит его в `sources/`, любой другой конец — удаляет. Рядом с
распакованным деревом тело НЕ кладётся намеренно: это дерево уезжает сборке на
вход, и архив внутри него стал бы ещё одним файлом, который видит модель.

**Лог кладётся вторым файлом.** Не потому, что иначе потеряется — задачи не
подрезаются, `data/jobs/<id>/log.txt` лежит столько же, — а потому, что копия при
задаче адресуется id ЗАДАЧИ, а он живёт одну попытку и нигде против ревизии не
записан. Через месяц у ревизии есть только её имя, и лог по нему иначе не
достать. Пишет его, как и копию при задаче, РОДИТЕЛЬ из захваченного вывода
(`BuildOutcome.log`), через тот же `_capped_log` — потолок один на обе копии, иначе
они разошлись бы на одном и том же тексте.

**Раздача — под `EDIT_TOKEN`, тем же, что и публикация.** Один секрет на
систему: кто его держит, тому можно всё; вторых ключей не заводим.

| Путь | Ответ |
| --- | --- |
| `GET /api/v1/sources/<revision>` | `application/octet-stream` + `Content-Disposition: attachment; filename="<revision>.tar.gz"`: тело пуша как есть |
| `GET /api/v1/sources/<revision>/log` | `text/plain; charset=utf-8`: что напечатала сборка |

Оба — `no-cache`. Токен проверяется **до** того, как хаб посмотрит на
`<revision>`, и все промахи одинаковы: несуществующая ревизия, ревизия без
сохранённого кода и синтаксически кривой сегмент дают один и тот же 404 с одним
телом. Существует ли ревизия с таким id, и так видно — страница сборки публична; а вот
«чей код лежит на диске» хаб не подтверждает ничем, кроме выдачи самого кода.
Существование определяет АРХИВ, а не каталог: каталог с одним логом — это то, что
остаётся от убитого на полпути переименования, и читаться он обязан как «нет
кода», а не как половина ревизии. Тип содержимого — непрозрачное вложение, а не
`application/gzip`: это байты, которые прислал пушер, и отдаются они на том же
origin, где лежат сборки всех остальных проектов. Лог — `text/plain` по той же
причине, что и лог задачи (§7.4).

**Ретенции нет и здесь** (§5.3): код ревизии живёт ровно столько же, сколько сама
ревизия, и осиротеть не может по построению.

### 7.9 `model.py` — код владельца, а не недоверенный ввод

**Противника в этой системе нет, и это свойство схемы, а не пожелание.** Три
факта, каждый проверяется по коду:

- **Пушить может только владелец.** Приём пуша закрыт `EDIT_TOKEN` —
  единственным секретом системы (§7.5), тем же, которым
  `DELETE /api/v1/projects/<pid>` стирает проект целиком. Кто присылает модель —
  тот же человек, который держит хаб.
- **Модели — его собственные репозитории.** `model.py` пишет владелец, для
  деталей, которые сам собирается напечатать, и кладёт на хаб, который сам
  развернул.
- **Больше туда никто не дотягивается.** Публичного маршрута сборки нет,
  анонимная запись закрыта шагом 0 (§8A.1), арендаторов нет. Единственный факт
  о самом развёртывании, отвечаемый без аутентификации, — булево `empty` в
  манифесте `/start`; страницы сборок и то, из чего рисуется модель, читаются
  анонимно по решению §5.4 (файлы деталей — по токену или ключу в ссылке), но
  написать через них нельзя ничего.

Отсюда следствие, ради которого раздел и написан: **`model.py` не является
недоверенным вводом.** Он ровно настолько же свой, как `main.py` этого
репозитория; разница только в том, что его пишут в другом каталоге. Это не
смягчение §8A.1: там сказано ровно то же — «кто остаётся в модели угроз:
владелец токена (он же владелец репозиториев)», — просто из этой
строки не было сделано вывода про содержимое `model.py`.

**Что такое `src/buildproc/` на самом деле.** Отдельный процесс (spawn+exec),
`rlimit`, сторожевой таймер, `SIGKILL` — это граница против ОШИБКИ, а не против
умысла: бесконечный цикл, булева операция, съедающая память, сегфолт в OCCT,
вызов ядра, который проект уже наблюдал работающим 45 минут. Всё это случается с
человеком, который старается сделать деталь, и случается регулярно. **Эта
граница настоящая и под вопрос не ставится.** Выдумана была ВТОРАЯ — из проверок
типов ВНУТРИ того же процесса.

**Как выглядела выдумка.** Работа над issue #56 (происхождение чисел) прошла 23
круга ревью и 18 дефектов, и почти каждый круг закрывал очередную «дорожку»
модели, которая якобы борется с хабом: подкласс `str` с врущим `__eq__`,
встроенная функция, привязанная к дандеру, модульный `__getattr__`, отвечающий
`{}.pop`, отражённые операторы, подделанная строка лога, поля `Number`,
переписанные `object.__setattr__` в обход конструктора. Каждый круг находил
следующее написание, которое предыдущий пропустил, — потому что список написаний
у языка не кончается, а актор, ради которого его перебирали, в этой схеме не
существует.

**Признак был виден с первого круга, и мимо него прошли дважды.** Во-первых,
8A.4 уже отказывает ЛЮБОМУ внутрипроцессному барьеру (`exec()` в процессе хаба,
RestrictedPython) — а проверка типов внутри сборочного процесса и есть
внутрипроцессный барьер, просто самодельный. Во-вторых, на четырнадцатом круге
то же рассуждение уже было принято по ОДНОЙ оси — про подделку строки лога:
записали, что лог сборки принадлежит автору и фильтровать его на потоке вредно,
— и никто не спросил, почему рассуждение применяется только к ней.

**Критерий на будущее — не «работает ли эта защита», а «не выдумал ли я
противника».** Удалять надо по второму вопросу. Первый вопрос сам по себе
уступка: обсуждая эффективность, соглашаешься, что актор есть и просто нашёл
обход, — и следующий читатель делает вывод, что правильный ход это барьер
получше. Всё, чьё обоснование упоминает противника, подделку, врущий метод,
обход или уклонение, удаляется без разбирательства о том, насколько хорошо оно
работало.

**Что остаётся — то, что помогает автору починить СВОЮ сломанную модель:**

- `modelchecks.call_model` и `MODEL_DOORS` — чтобы отказ читался как
  `parts() raised TypeError (model.py:5)`, а не как падение хаба;
  `raised_by_the_model` — по той же причине и с той же оговоркой (признак
  достаточный, не необходимый);
- `modeltext` — чтобы одно сломанное `__repr__` среди пятидесяти чисел не стоило
  сообщения про остальные сорок девять, чтобы одно значение не вытесняло весь
  отказ и чтобы сообщение хаба оставалось одной строкой;
- исправление коллизии кодов выхода в `buildproc/child.py`: 1 означает и
  «сработал сторож», и «необработанное исключение», так что баг ХАБА уезжал
  автору как «сборка перестала отвечать» — и человека посылали искать поток,
  который никуда не завис;
- сама фича — `src/cadbuild/provenance.py`, правило про происхождение чисел, и
  `checklib.Number` под ним.

Замер, чтобы не перепроверять: модель, вызывающая `os._exit(4)`, даёт
`status='crashed', exit=4` — то есть граница проходит по процессу, а не по
проверкам внутри него.

## 8A. Хаб становится билдером — принятое решение

Решено 2026-08-24. Делает неверными: шапку документа, §1 (сценарий A, шаг 3),
строку «Доставка» в таблице §4 и §7 в части того, ЧТО приезжает в хаб. Переводит
issue #6 «Один образ: вьювер и билдер вместе» из «хотелось бы» в «делаем».
Делает неверным и довод из issue #10 «Сравнение двух ревизий» — «почти в восемь раз
дешевле»: он посчитан для узкого пути сравнения, где нужны только `OCP`, `numpy` и
`ocp-tessellate`, а сам `cadquery` не импортируется. Восьмикратной экономии не будет
по двум причинам сразу: хаб, который СОБИРАЕТ модели, требует полного `cadquery`, и
шаг 1 отказывается от пина `cadquery-ocp-novtk`, на котором держались те 250 МБ.

**Что решено.** Хаб принимает ИСХОДНИК модели и сам считает геометрию. Отдельного
образа `cad_builder` и workflow публикации моделей больше нет. Форж остаётся сбоку
как хранилище истории и в цепочке публикации не участвует: ни вебхуков, ни pull, ни
раннеров. Всё только пушем от разработчика, два адресата — `dev` (проверить сборку
на ходу) и ревизия по коммиту. Коммит-sha приезжает вместе с пушем и НЕ проверяется:
хаб не может убедиться, что такой коммит существует и что исходник соответствует
именно ему. Это тот же уровень доверия, что и токен публикации, но идентификатор
ревизии перестаёт быть верифицируемым, и на нём нельзя строить ничего, что требует
подлинности.

**Зачем.** Один артефакт вместо трёх репозиториев, одна версия ядра геометрии, один
деплой. И ядро рядом с хабом — без него не сделать сравнение ревизий с разностной
геометрией.

**Что доводом НЕ является — проверено, чтобы не выдвигали снова:**

- «CI медленный». Реальные прогоны публикации модели — 10–45 с на весь job.
  Оговорка: «десятки минут» из комментария в workflow относятся к сборке образа
  С CAD-СТЕКОМ, то есть ровно к тому, во что этот план превращает образ хаба;
  единственный замер такого образа — два прогона `cad_builder`, 37 с и 207 с;
- «нет быстрого локального цикла». На момент решения он был — `make build` собирал на
  build-node через docker context и публикует в `dev` с ноутбука. Но живёт он на
  `remote.py` и образе билдера, которые этот же план удаляет. После переезда
  локальный цикл — это пуш исходника и ожидание асинхронной задачи с логом, то есть
  его придётся построить заново (шаг 5);
- «нет гейта на геометрию». Он написан и работает в пакете `cad_publish`:
  `isValid()`, ненулевой объём, водонепроницаемость меша, непересечение деталей на
  плите, наличие всех печатных деталей в сборке, собственные `checks()` модели, у
  которых число проверок считается по AST и ноль отвергается. Требование issue #3
  «Гейт на геометрию в CI», называющее этот гейт несделанным, устарело. (Гейт с тех
  пор переехал в `src/cadbuild/` — шаг 3 — и issue #75 переписал его на каталог
  `parts()`; список выше описывает состояние на момент решения. Лежит он не в
  одном модуле и не в отведённом ему: отказывает тот, кто первым видит негодное,
  так что подетальные проверки — `isValid()`, объём, водонепроницаемость меша и
  «один кусок» — стоят в `printables.py`, по ходу экспорта; проверки, читающие вид
  целиком — раскладка на плите, непересечение, покрытие сборки, — в `gate.py`;
  счёт проверок `checks()` по AST — в `modelchecks.py`; деформированная деталь на
  плите — в `views.py`. Считать эти
  места и заучивать их перечень не надо — ни то, ни другое здесь не держится:
  искать надо `BuildError` по всему `src/cadbuild/`.)

### 8A.1 Модель угроз после решения

Хаб перестаёт только РАЗБИРАТЬ недоверенные данные и начинает ИСПОЛНЯТЬ присланный
код. Разница не в степени: чтобы получить питон-процесс через разбор архива, нужно
найти баг в коде, написанном против ровно этого класса атак; чтобы получить его через
исполнение — не нужно ничего, это штатное поведение.

**Довод «поверхность атаки не расширяется» из записи «Один образ» признан неверным.**
Его первый аргумент — «исполнение закрывается токеном и попадает в тот же уровень
доверия, что публикация» — не держится: сегодня токен даёт право записать
ПРОВЕРЕННЫЕ ХАБОМ байты в каталог, который выбирает ХАБ. Дать тому же токену shell —
это повышение привилегий существующего креденшла. Второй аргумент — «хаб и так
разбирает недоверенный ввод» — приравнивает путь ценой эксплойта к пути по протоколу.

Для калибровки — соседний верстак для LLM-агентов: наружу его выставить нельзя в
принципе, потому что он исполняет сгенерированный python, не имеет аутентификации и
работает от root внутри контейнера. Три свойства. Двумя хаб отличается — исполнение
под токеном и non-root процесс. Третьим, главным, совпадает: он тоже будет исполнять
недоверенный python. А по доступности отличается в ХУДШУЮ
сторону — тот верстак наружу не смотрит вовсе, а хаб публичен по построению.

**Анонимный вход закрыт — шаг 0 плана, сделано.** Без этого после переезда
возникала полная дорожка от анонимного ввода до выполнения кода, не требующая ни
одной уязвимости: комментарий пишется публично, без токена → попадает в очередь →
агент читает его через MCP как задачу → агент правит `model.py` → хаб исполняет
`model.py`. **Публичная запись комментариев отменена: запись под токеном.** Это
поменяло посылку §7A («зритель тыкает в деталь и пишет „поправь вот тут“» — теперь
это держатель токена), маршрут записи и обоснование публичности в 7A.2, требования
7A.4 и маршрут комментария к `dev` в §7.6. Заодно отпал один из двух доводов против
issue в Gitea — тот, что анонимная запись это спам-дверь; второй, «трекер под это
избыточен», остаётся, да и issue требуют аккаунта в форже, так что схемы всё равно не
эквивалентны. Право писать выдано тому же, кто публикует: секрет один на систему
(issue #26), и фича честно называется заметкой агенту, а не публичным каналом.

**Кто остаётся в модели угроз:** владелец токена (он же владелец репозиториев).
Утечка токена не рассматривается: с токеном и так доступно всё. Разделять право
«прислать код» и право «опубликовать» при этом бессмысленно: в новой схеме это один и тот же POST — прислать исходник и есть
запустить сборку, а её успех и есть публикация. А то, что `PUBLISH_TOKEN` был
секретом уровня организации, видимым всем 14 репозиториям, лечится само: он
перестаёт быть org-секретом вместе с workflow'ами. Шаг 0 добавил к этому имя:
переменная хаба называется `EDIT_TOKEN` (§7.5) — не потому, что имя что-то
защищает, а потому что `PUBLISH_TOKEN` читался как «креденшл CI на пуш» и тем
приглашал сделать ровно то повышение привилегий, о котором этот раздел.

**Радиус поражения измерен, а не предположен.** Хаб стоит не в вакууме, а в общей
docker-сети: из неё без единого опубликованного порта достижимы соседние сервисы и их
базы — включая сам форж с исходниками всех проектов и его базу. Это доступ, которого у
сегодняшнего исполнителя на CI-раннере нет. У контейнера хаба заданы потолок памяти
(3157 МиБ, без свопа) и `pids` (148) — по замеру 2026-10-06 (#119), см. шаг 0 в §8A.2.
CPU и `cap_drop` по-прежнему НЕ ЗАДАНЫ.

### 8A.3 Открытые решения

- **Зависимости модели.** Рекомендуется запретить всё, кроме того, что в образе.
  Причина: установка sdist гарантированно исполняет код (даже `pip install --dry-run`
  запускает build-бэкенд), а wheel может положить `.pth`-файл, который исполняется при
  КАЖДОМ старте интерпретатора, без всякого импорта — именно так работали обе крупные
  атаки на PyPI в этом году. Флаг `--only-binary=:all:` не спасает, если путь к архиву
  или каталогу передан явно.
- **Версия ядра становится общей, и отстать нельзя.** `cadquery` пинит `cadquery-ocp`
  непересекающимися диапазонами: 2.7 требует `>=7.8.1,<7.9`, 2.8 — `>=7.9.3.1,<8.0`.
  Два проекта на разных `cadquery` физически не могут делить одно окружение, а полный
  venv на проект — порядка 1.5 ГБ, то есть по проекту не размножишь.
- ~~**Ретенция.**~~ **Закрыто решением 2026-08-27: ретенции нет** (§5.3, §7.3) — вопрос
  снят решением, а не расчётом, и переоткрывать его не надо. Замер, ради которого он
  стоял, при этом остаётся полезным и превращается в вопрос про ОБЪЁМ ТОМА: считать надо
  по РАСПАКОВАННОМУ объёму и по числу видов — §5.3 говорит «примерно 2 МБ на вид», а
  0.31 МБ из §2.3 это gzip одного вида, то есть трафик, а не диск. Сто сборок — сотни
  мегабайт, а не 31, и теперь они не уходят никуда сами. Кэш диффов вне каталога сборки
  всё равно нужен, но уже не потому, что «ретенция съест половину пары» (issue #10
  «Сравнение двух ревизий»), а из-за прав и годового `immutable`.

### 8A.4 Чего не делать никогда

Проверено по источникам, чтобы не возвращаться:

- **docker-сокет хабу или билдеру** в любом виде, включая socket-proxy: дать доступ к
  сокету равносильно неограниченному root на хосте, а прокси не инспектирует тело
  запроса, поэтому `Binds` и `Privileged` проходят насквозь;
- **docker-in-docker и `privileged: true`** — снимает seccomp, AppArmor, все
  capabilities и маскировку `/proc`;
- **`exec()` модели в процессе хаба** — рядом с токенами и томом;
- **RestrictedPython, audit hooks и любой in-process барьер.** Авторы всех трёх сами
  пишут, что это не песочница; для нативного OCP это неприменимо в принципе, потому
  что придётся разрешить импорт модуля с прямым доступом к памяти процесса;
- **nsjail и bubblewrap внутри Docker** — цена входа `CAP_SYS_ADMIN` плюс
  `seccomp=unconfined`, то есть размен сильного внешнего слоя на слабый внутренний;
- **`userns-remap`** — настройка уровня демона, маскирует существующие слои образов;
  на живом хосте это пересоздание хоста.

## 9. Ограничения

- Снапшот, а не конфигуратор: параметры в браузере не крутятся. Интерактивная
  параметризация — это `parametric_configurator`, отдельный проект.
- Только код-CAD (CadQuery). Модель из Fusion CI пересобрать не может; для неё путь —
  коммитить экспортированный STEP, и это отдельная ветка работы, сейчас не покрытая.
- Аутентификации на чтение сборки нет и не планируется (5.4); списки — проектов и
  ревизий проекта — под токеном (7.4).
- Хаб не удаляет ничего сам: ретенции нет, том растёт монотонно, и разгребать его,
  когда он однажды кончится, придётся руками (5.3, 7.3).
