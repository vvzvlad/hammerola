# cad_snapshot_hub — техническое задание

Витрина 3D-моделей: хаб, который принимает по HTTP артефакты сборки CadQuery-проектов
из Gitea Actions и раздаёт по каждому проекту свой веб-вьювер на публичном домене.
Один контейнер на все проекты; заведение нового проекта не требует никаких действий
снаружи репозитория — только `git push` в него.

Задача выросла из чата по `home-network` 21.08.2026. Всё, что помечено ниже как
проверенное, проверено эмпирически — командой, вывод которой приведён. Перепроверять
это не нужно, это уже стоило времени.

---

## 1. Пользовательский сценарий

**Сценарий A — автор модели.**

1. Автор делает подпапку в `~/Data/Projects/3d/<project>/`, заводит репозиторий в
   организации `3d` в Gitea, пишет модель на CadQuery.
2. `git push` в `main`.
3. Gitea Actions: собирает модель, проверяет геометрию, экспортирует тесселяцию и
   файлы для печати, пушит артефакты в хаб.
4. Через минуту `https://<хаб>/project/<pid>/latest/` показывает текущее
   состояние модели.

**Сценарий B — тот, кому кинули ссылку.**

1. Открывает `https://<хаб>/project/<pid>/<commit>/`.
2. Видит модель: крутит, зумит, выключает отдельные детали, режет плоскостью,
   разносит сборку.
3. Жмёт STL / STEP / 3MF — получает файлы **той самой** сборки, которую видит на
   экране, а не «последней».
4. Ссылка показывает то же самое и через год: сборка по коммиту неизменяема.

**Сценарий C — обзор.**

1. Открывает `https://<хаб>/` — индекс всех проектов карточками: заголовок,
   короткий sha последней сборки, дата, число деталей, вес.

## 2. Внешние интерфейсы и факты (проверено эмпирически)

### 2.1 CadQuery: что умеет экспортировать

Версии, на которых проверено всё в этом разделе (`importlib.metadata.version`):

```
cadquery       2.8.0
cadquery-ocp   7.9.3.1.1
ocp_vscode     4.0.1
ocp-tessellate 3.4.1
trimesh        4.12.2
build123d      NOT INSTALLED
```

**Вывод: стек фактически CadQuery, а не build123d.** Это важно: часть публичных
рецептов написана под build123d и здесь не применима как есть.

Реально проверенный экспорт (тестовая коробка 20×10×5 со скруглением):

```
glb   OK     20596 bytes      step  OK     33721 bytes
gltf  OK      4381 bytes      stl   OK     26284 bytes
vrml  OK     17557 bytes      3mf   FAIL  ValueError: Unknown extension
```

Актуальный (не устаревший) API:

```python
a = cq.Assembly(part, name="part", color=cq.Color("steelblue"))
a.export(path, exportType="STEP"|"STL"|"GLTF"|"VRML"|"XML"|"XBF"|"VTKJS")
```

Точная сигнатура: `Assembly.export(self, path, exportType=None, mode='default',
tolerance=0.1, angularTolerance=0.1, unit='MM', outputUnit=None, **kwargs)`.

Две ловушки:

- `Assembly.save()` работает, но помечен `FutureWarning: save will be removed in the
  next release`. Использовать `.export()`.
- **3MF не берётся через `Assembly`** — расширение не распознаётся. Только через
  `exporters.export(shape, path, exportType=exporters.ExportTypes.THREEMF)` и только
  для `Workplane`/`Shape`, не для сборки. Проверено: 1239 bytes на той же коробке.

Полный список `exporters.ExportTypes`: `AMF, BIN, BREP, DXF, STEP, STL, SVG, THREEMF,
TJS, VRML, VTP`.

### 2.2 Вьювер: three-cad-viewer, тот же, что в OCP CAD Viewer

Главная находка разведки: **вьювер писать не надо**. Библиотека `three-cad-viewer`
(bernhard-42) — ровно тот рендерер, что внутри OCP CAD Viewer, и она лежит прямо
внутри пакета `ocp_vscode`:

```
<venv>/lib/python3.12/site-packages/ocp_vscode/static/js/three-cad-viewer.esm.js   3.57 MB
<venv>/lib/python3.12/site-packages/ocp_vscode/static/css/three-cad-viewer.css
```

Она полностью работает **статикой**, без вебсокета и без живого сервера. Данные для
неё генерирует `ocp_tessellate`:

```python
from ocp_tessellate.convert import export_three_cad_viewer_js

export_three_cad_viewer_js(
    None,                       # var=None → в файл пишется ГОЛЫЙ JSON,
                                # а не `var shapes = {...}` — это ключевой момент
    *objs, names=[...], colors=[...], alphas=[...],
    filename="assembled.json",
)
```

Страница поднимает вьювер так (проверено, рендерит реальную модель):

```js
import { Viewer, Display } from "/_v/three-cad-viewer.esm.js";
const shapes  = await (await fetch("./assembled.json")).json();
const display = new Display(box, displayOptions);
const viewer  = new Viewer(display, displayOptions, () => {}, null);
viewer.render(shapes, renderOptions, viewerOptions);
```

Что сохраняется по сравнению с GLB: дерево деталей с именами и цветами, поштучное
включение/выключение, изометрические виды, clip-плоскости, explode, рёбра. В GLB всё
это схлопнулось бы в один безымянный меш.

**Иконки тулбара — инлайновые data-URI прямо в CSS** (проверено: ноль внешних `url()`
кроме `data:`). Никаких дополнительных ассетов копировать не нужно, хватает двух
файлов выше.

### 2.4 Уже существующая практика в проектах моделей

В `~/Data/Projects/fusion/` лежит `VIEWER.md` и в каждом проекте — самодостаточный
`show_in_viewer.py`, который уже делает **ровно тесселяцию**, только пушит её в
вебсокет живого OCP CAD Viewer'а. Переезд на публикацию — это смена приёмника, а не
новый код: у него уже есть `load_model()` (исполняет модель без её side-effects) и
`collect(ns, layout)`, возвращающий `(objs, names, colors, alphas)` для вида
`assembled` / `print`.

Отсюда формат: **сборка содержит список видов, а не одну модель.** У T13 их два и оба
осмысленны. Для проекта с одной деталью список из одного элемента.

Известная ловушка оттуда же (задокументирована в их `VIEWER.md` и в коде): `show()` из
`ocp_vscode` после меша шлёт `send_backend(...)` и ждёт `ws.recv()` **без таймаута**;
подтверждение присылает только backend расширения VS Code, поэтому со standalone-вьювером
скрипт виснет навсегда с уже нарисованной моделью. Лечится
`importlib.import_module("ocp_vscode.show").send_backend = lambda *a, **kw: None`.
К нашему пути это не относится (мы не используем `show()`), но при переносе кода из
`show_in_viewer.py` этот патч тащить не надо.

### 2.5 Gitea: что можно и чего нельзя

Проверено curl-ом против Gitea:

```
GET /api/v1/packages/projects?limit=3
    → 401 {"message":"token is required"}          # ЛИСТИНГ ТРЕБУЕТ ТОКЕН ДАЖЕ ДЛЯ ПУБЛИЧНЫХ

GET /api/packages/projects/generic/nonexistent/latest/x.bin
    → 404                                          # не 401 → СКАЧИВАНИЕ анонимно разрешено

GET ... с Origin: https://example.com
    → в ответе НЕТ ни одного заголовка Access-Control-*
```

Три вывода:

- generic-пакеты **читаются анонимно**, если владелец публичный;
- **перечислить** пакеты без токена нельзя — автодискавери проектов через Gitea API
  требует PAT на стороне хаба;
- **CORS не настроен**, поэтому страница хаба не может фетчить модель напрямую из
  Gitea. Любой путь через Gitea требует серверного проксирования. Это одна из причин
  отказа от варианта «хаб тянет из реестра».

### 2.6 Почему адресация путём, а не поддоменом

Проект адресуется путём — `<хост>/project/<pid>/`, — а не собственным поддоменом.

Причина в стоимости заведения нового проекта. Поддомен на проект стоит отдельной записи
в имени и отдельного сертификата НА КАЖДЫЙ проект, и вайлдкардом это не спасается:
вайлдкард матчит ровно один лейбл, поэтому `<проект>.<хаб>` им уже не накрывается. Путь
не стоит ничего — сколько бы проектов ни завелось, имя одно и сертификат один.

Отсюда же следует схема URL целиком (раздел 3) и её кэширование (3.2).

Само размещение в требования не входит: под каким именем сервис отвечает и как туда
попадает — вопрос выката, а не этого документа.

## 3. Схема URL

```
/                                    индекс всех проектов (под EDIT_TOKEN, §7.5)
/project/<pid>/                      редирект на latest
/project/<pid>/latest/               новейшая сборка ИЗ CI
/project/<pid>/dev/                  локальный слот, одна сборка с ноутбука (§7.6)
/project/<pid>/<commit>/             одна сборка, неизменяемая
/project/<pid>/<commit>/?v=<view>    конкретный вид внутри сборки
/project/<pid>/builds.json           список сборок для переключателя
/_v/                                 общие ассеты вьювера, один экземпляр на сайт

POST /api/v1/publish/<pid>           приём пуша: 202 и задача,    EDIT_TOKEN
                                     имя ревизии чеканит ХАБ
POST /api/v1/publish/<pid>/<commit>  то же, под именем от пушера  EDIT_TOKEN
POST /api/v1/publish/<pid>/dev       то же, в локальный слот      EDIT_TOKEN
GET  /api/v1/jobs/<id>               как идёт эта сборка          EDIT_TOKEN
GET  /api/v1/jobs/<id>/log           что сборка напечатала        EDIT_TOKEN
```

Два **разных** идентификатора в пути, и это намеренно:

- `<pid>` — идентификатор **проекта**, живёт вечно;
- `<commit>` — идентификатор **сборки**, их накапливается много.

**Имя сборки чеканит хаб, а не пушер** — маршрут без последнего сегмента. Пушер
его и не знает: `hammerola commit` значит «опубликуй версию этого», а не
«опубликуй под таким-то именем», и к git имя отношения не имеет (§7.7). Отсутствие
сегмента — это и есть просьба назвать; правило «куда что ложится, решает URL, а не
тело» при этом не трогается. Маршрут с именем остаётся: под ним публикуют
репозитории моделей, у которых `publish.yml` ещё жив (§8A.2, шаг 7) — но клиент им
не пользуется и своего имени не выдумывает.

Третий идентификатор, `<id>` задачи сборки, в эту схему намеренно не встроен: он не
адресует ничего опубликованного — только ход одной сборки и то, что она напечатала, — и
он **непредсказуемый** — 16 байт из `secrets`, а не счётчик. Временным он при этом БЫТЬ
ПЕРЕСТАЛ: ретенции у задач нет (§7.3), лог сборки не подрезается и запись о ней с тома
сама не уходит, — то есть непредсказуемость больше не подпирается тем, что цель ссылки
рано или поздно исчезнет, и работать обязана сама по себе. Он появился вместе с
асинхронным приёмом (§8A.2, шаг 5) и он единственное, что отделяет лог сборки одного
пушера от лога другого: последовательный номер позволил бы вычитанием единицы
пройтись по логам всех чужих проектов, имея тот же самый `EDIT_TOKEN`.

### 3.1 Откуда берётся `<pid>` — и почему не из имени

Требование: ссылка не должна ломаться при переименовании проекта. Значит pid
**нельзя вычислять из имени** — иначе он меняется ровно тогда, когда должен был спасти
ссылку. Вычислять его не из чего, значит он должен храниться.

Решение: pid лежит **в самом репозитории проекта**, в `project.json`, генерируется
один раз при заведении проекта из шаблона:

```json
{ "id": "7f3c1a9e04d2", "title": "T13 ceiling mount" }
```

Свойства: переживает переименование репозитория, переезд между организациями и смену
форжа; виден в репозитории, а не спрятан в чужой БД; CI его читает, а не вычисляет.
Цена — правило «этот файл руками не редактируем».

Отвергнуто: брать id репозитория из Gitea (`github.repository_id`) — привязка к форжу,
и наличие этого контекста в Gitea Actions не проверено.

### 3.2 Кэширование следует из схемы

- `/project/<pid>/<commit>/*` — неизменяемо по построению → `Cache-Control: immutable,
  max-age=31536000`
- `/project/<pid>/latest/` и `/project/<pid>/dev/` — движущиеся имена, только они
  требуют `no-cache`
- `/_v/*` — общий бандл, один на весь сайт → тоже вечный кэш

`latest` реализуется **симлинком** на каталог коммита: не дублирует данные и, главное,
переключается атомарно — читатель никогда не увидит наполовину опубликованную сборку.
Публикация = «залить `<commit>/` целиком, потом перекинуть симлинк».

`dev` (§7.6) — не симлинк, а **сам каталог**: слот, который пуш с ноутбука
перезаписывает. Общего у них ровно одно — `no-cache`, и для `dev` это не оптимизация,
а условие корректности: перезапись содержимого под одним URL допустима **только**
потому, что годовых кэшей на него никто не раздавал.

## 4. Решения и отвергнутые варианты

| Решение | Почему так | Что отвергли и почему |
| --- | --- | --- |
| Свой хаб со статическими снапшотами | Публично, без аутентификации, ссылка живёт вечно | **Переиспользовать живой OCP CAD Viewer** — он рисует в открытый браузер, а без зрителя пишет в лог `No browser registered` и молча дропает модель; состояния у него нет вовсе. Публикация происходит ровно тогда, когда никто не смотрит, — то есть уходила бы в никуда. Третий блокер, в отличие от первых двух, конфигом не чинится: наружу по https он не встаёт в принципе — `standalone.py` делает `request.host.split(":")` и падает с 500 на `Host` без порта, а страница жёстко открывает `ws://`, который браузер режет как mixed content на `https://`. За обратным прокси это правится только в чужом коде; проверено 19.08.2026 |
| `three-cad-viewer` + JSON тесселяции | Сохраняет дерево деталей, clip, explode, виды; вьювер писать не надо | **GLB + `<model-viewer>`** — теряет всю структуру, модель становится одним безымянным мешем. GLB остаётся только кнопкой скачивания |
| Один хаб-контейнер на все проекты | Новый проект = только `git push`, ничего заводить не надо | **Контейнер на проект** — переиспользует готовый пайплайн «образ → реестр → обновление», но превращает заведение каждого проекта в отдельное развёртывание вместо пуша |
| Доставка: CI пушит артефакты в хаб по HTTP | Один общий секрет в CI, а не секрет на проект; никакого CORS и токенов на чтение | **Хаб тянет из Gitea generic packages** — листинг требует PAT, CORS не настроен, перезапись версии `latest` в generic-реестре ведёт себя не так, как хочется |
| Путевая адресация `<хост>/project/<pid>/` | Одно имя на весь сайт, сколько бы проектов ни завелось (2.6) | **Поддомен на проект** — вайлдкард матчит ровно один лейбл, значит своё имя заводится под каждый проект |
| `<pid>` хранится в `project.json` репозитория | Переживает переименование, переезд организации и смену форжа | **pid из имени** — ломается ровно при переименовании; **id репозитория Gitea** — привязка к форжу |
| Сборка содержит список **видов** | У реального T13 два осмысленных вида (`assembled`, `print`) | Одна модель на сборку — не хватает уже на первом настоящем проекте |

Живой OCP CAD Viewer остаётся песочницей для локальной интерактивной работы — это
нормально и менять не надо. Отдельно стоит верстак для LLM-агентов (build123d, gmsh,
CalculiX): он **выше по потоку** — там модель может рождаться, оттуда выходит STEP, а
публикует снапшот всё равно хаб.

## 5. Подводные камни

### 5.1 Данные вьювера нельзя грузить как ES-модуль

Наступили в прототипе. Если подключить данные как
`<script type="module" src="model.js">`, где внутри `var shapes = {...}`, то `shapes`
**остаётся в области видимости модуля и в `window` не попадает**. Внешне это выглядит
как полностью исправный вьювер: рисуются вкладки Tree/Clip/Material/Studio, рамки
тулбара — но сцена пустая, и ошибок в консоли нет.

Поэтому: данные лежат отдельным `.json` и грузятся `fetch`-ем (`var=None` в
`export_three_cad_viewer_js`). Плюс страница обязана иметь **видимый блок ошибки** —
молчаливый провал здесь неотличим от пустой сцены.

### 5.2 Размер канваса брать из контейнера, а не из окна

Тоже наступили. Если считать высоту как `window.innerHeight - <константа>`, шапка
уезжает за экран, потому что угаданный отступ не совпадает с реальной высотой шапки.
Правильно: `body` — flex-колонка, шапка `flex: 0 0 auto`, обёртка вьювера
`flex: 1 1 auto; position: relative; overflow: hidden; min-height: 0`, а размеры брать
из `box.clientWidth` / `box.clientHeight`. `position`/`overflow` на обёртке нужны, чтобы
в режиме `glass: true` дерево и тулбар не вылезали поверх шапки.

### 5.3 Ретенции нет

Камень настоящий: каждая сборка — примерно 2 МБ на вид, и том растёт линейно от числа
пушей. **Решение 2026-08-27 — принять этот рост и не заводить механизма очистки вообще:**
ни у сборок, ни у задач, ни у локального слота, ни у комментариев. У комментариев
механизма не было и раньше — там стояли ПОТОЛКИ, отказывавшие в следующем вместо
удаления старого (§7A.4), что то же решение и та же цена, только в более жёсткой
форме: не «выбросим давнее», а «дальше нельзя», причём навсегда.

Довод — цена сторон, а не «место бесплатное». Десятки мегабайт на ревизию против
механизма, который надо написать, покрыть тестами, объяснять в документе и который умеет
удалить не то. Правило «держим последние N на проект» опирается на метку времени, которую
хаб ставит сам, на порядок создания, который после рестарта приходится восстанавливать, и
на исключение «а на что смотрит `latest`» — три места, где ошибка стоит безвозвратно
удалённой чужой работы, а выигрыш меряется гигабайтами на дешёвом томе. Размен не в пользу
механизма.

**Взамен появляется свойство, которого с ретенцией не бывает.** Сборка неизменяема,
`latest` всегда указывает на новейшую, и ничего не удаляется — значит ни одна ссылка,
розданная наружу с годовым `immutable` (§3.2), никогда не перестаёт разрешаться. Не «почти
никогда» и не «пока не выпала из окна»: никогда. Ровно ради этого обещания и построена вся
адресация в §3, и ретенция была единственным, что его подтачивало.

**Цена называется честно:** том растёт монотонно, и когда он однажды кончится, это будет
ручная работа — человек, разбирающий проекты, а не автоматика, срабатывающая по потолку.
Это принято сознательно: редкое ручное решение об удалении лучше частого
автоматического, которое некому проверить.

### 5.4 Публичность

Домен наружу означает, что модели доступны всем, кто знает URL, а индекс на `/` делает
их ещё и перечислимыми. Выбор сделан сознательно (владелец выбрал «наружу, чтобы кидать
ссылку» + публичный индекс). Если появится проект, который нельзя показывать, — это
отдельная работа, а не флажок.

**Публичны СТРАНИЦЫ и файлы сборок — не API.** Всё, что под `/api/v1/`, требует
`EDIT_TOKEN` (§7.5): публикация, задачи сборки, исходники ревизии, маршруты
переименования и удаления и вся очередь комментариев вместе с записью в неё. Раздача
при этом остаётся анонимной на чтение и такой и задумана — ссылку кидают людям, а не
раздают им секрет.

### 5.5 Мелочи, на которых уже споткнулись

  трогать файлы с комментариями. Шапку надо снять — сам шаблон об этом и пишет.

## 7. Протокол приёма пуша

```
POST /api/v1/publish/<pid>            имя ревизии чеканит хаб (§7.7)
POST /api/v1/publish/<pid>/<commit>   имя приносит пушер
Authorization: Bearer <EDIT_TOKEN>
Content-Type: application/gzip
<тело: gzip-сжатый tar>
```

`pid` и `commit` берутся **из URL, а не из тела**: сервер — власть над тем, куда
что ложится. Токен сверяется `hmac.compare_digest`, не `==`. Отсутствие последнего
сегмента — не исключение из этого правила, а его частный случай: имени в запросе нет
вообще ни в URL, ни в теле, и хаб выводит его из содержимого сам (§7.7).

Архив — **дерево**, без ведущего каталога (§8A.2, шаг 2: сюда едет исходник модели, а
он деревом и является). Имя члена — относительный путь; правила имён и потолки — в
§7.1. В корне обязателен `meta.json`, и там же обязаны лежать все файлы, на которые
ссылаются `views[].file` и `downloads[*]`: раздача отвечает по
`/project/<pid>/<commit>/<имя>` и глубже не умеет, так что ссылка в подкаталог
опубликовалась бы 201-м, а открывалась 404-м. Остальное дерево — на усмотрение модели:

```
meta.json
assembled.json        # по одному файлу на вид, имена — из meta.json
print.json
model.step            # файлы для скачивания, необязательные
model.stl
model.3mf
model.py              # исходник модели — каталоги разрешены
enclosure.py
scripts/build.py
ref/vendor/rev2/part.step
```

`meta.json`:

```json
{
  "project": "t13-ceiling-mount",
  "title":   "T13 ceiling mount",
  "built":   "2026-08-21T04:16:00Z",
  "views":    [{"id": "assembled", "name": "assembled", "file": "assembled.json", "parts": 4},
               {"id": "print",     "name": "as printed", "file": "print.json",    "parts": 3}],
  "downloads": {"step": "model.step", "stl": "model.stl", "3mf": "model.3mf"}
}
```

Ответы:

| Код | Когда | Тело |
| --- | --- | --- |
| 202 | пуш принят, сборка поставлена в очередь | `{"job", "status_url", "log_url"}`, заголовок `Location` = `status_url`; на маршруте без имени ещё и `revision` |
| 201 | опубликовано | `{"url": "/project/<pid>/<commit>/"}` |
| 200 | этот коммит уже опубликован, содержимое совпадает | то же; на маршруте без имени ещё и `revision` |
| 400 | `Content-Length` отрицательный, либо тело оборвалось раньше объявленной длины | `{"error": ...}` |
| 401 | нет или плохой токен | `{"error": ...}`, заголовок `WWW-Authenticate: Bearer` |
| 408 | тело не пришло целиком за `BODY_DEADLINE_SECONDS` (300 с) | `{"error": ...}` |
| 409 | коммит уже есть, но содержимое ДРУГОЕ | `{"error": ...}` |
| 411 | заголовка `Content-Length` нет или он не число | `{"error": ...}` |
| 413 | больше `MAX_BUILD_BYTES` — по заголовку `Content-Length` или по объёму распакованного | `{"error": ...}` |
| 422 | битый архив, невалидный `meta.json`, битые ссылки, небезопасное имя члена архива, плохой `pid`/`commit` | `{"error": ...}` |
| 503 | нет свободного слота публикации за `PUBLISH_WAIT_SECONDS` | `{"error": ...}`, заголовок `Retry-After: 30` |

**Где именно теперь появляется 201.** С шага 5 (§8A.2) пуш асинхронный, и таблица
выше читается по одному правилу: всё, что решается **из самого пуша**, отвечается на
пуше, а всё, для чего нужна СБОРКА, уезжает в задачу. Токен, размер, целость архива,
имена членов и «этот пуш уже опубликован» — свойства загруженного тела, поэтому 401,
413, 411, 408, 400, 422, 409 и 200 приходят там же, где приходили всегда. 201 и
422-от-сборки приходят из задачи: их узнают через `GET /api/v1/jobs/<id>` (§7.4).
409 умеет прийти обоими путями, и это не дубль проверки: на пуше отвечает
`Store.settled`, а перед самым `rename` та же проверка делается ещё раз под локом
проекта — окно между ними теперь не миллисекунды, а целая сборка, и два пуша одного
коммита с разным содержимым запросто оказываются в нём одновременно.
503 бывает двух видов — «нет слота приёма за `PUBLISH_WAIT_SECONDS`» (тело не читалось
вовсе, `Retry-After: 30`) и «очередь сборки полна» (тело принято, задача заведена и
сразу помечена провалившейся, `Retry-After: 60`); для CI оба означают одно и то же —
повторить тем же телом.

409, а не перезапись: сборка по коммиту объявлена неизменяемой, и на неё выданы
вечные заголовки кэша. Молча подменить её содержимое — значит соврать всем, у кого
она уже в кэше. 200 на побайтово идентичный повтор делает ретрай CI безопасным.
На маршруте, где имя чеканит хаб, «то же имя с другим содержимым» вообще не
возникает — там 409 значит уже другое, см. §7.7.

**Что ретраить, а что нет.** 503 значит «попробуй ещё раз тем же телом»: хаб просто
занят, пуш ни в чём не виноват. 408 и 400 — про оборвавшуюся передачу, повтор тоже
имеет смысл. Остальные 4xx — про сам запрос, и повтор без изменений даст ровно тот
же код; CI должен упасть и показать `error` из тела. 401 закрывает соединение
(`Connection: close`), чтобы непрочитанное тело не разобралось как следующий запрос
на keep-alive-соединении; по той же причине его закрывают 400, 408, 411 и 413.

**Дедлайн на тело — отдельно от таймаута сокета.** `HubHandler.timeout` меряет
паузу между пакетами и взводится заново каждым из них, так что клиент, отдающий по
байту раз в 29 секунд, не трогает его никогда — и держит слот публикации сколько
захочет. Четверых таких хватает, чтобы занять весь `MAX_CONCURRENT_PUBLISHES`, и
вся легитимная CI получает 503; цена атаки — четыре сокета и ноль трафика. Поэтому
у тела есть свой дедлайн на всю передачу (`BODY_DEADLINE_SECONDS`, 300 с — это
~1.7 Мбит/с при потолке 64 MiB). Читать при этом надо `rfile.read1()`, а не
`read()`: буферизованный `read(n)` крутится внутри, пока не наберёт все n байт, и
до проверки дедлайна управление просто не возвращается.

### 7.1 Валидация до публикации

- каждый `views[].file` и каждый `downloads[*]` реально есть в архиве, лежит **в его
  корне** (в подкаталоге — 422: раздача таких URL не знает, см. §7 и §7.4) и **не**
  совпадает с `meta.json`, `index.html` или файлом дайджеста: `meta.json` хаб
  перезаписывает уже после этой проверки, а `index.html` из каталога сборки не
  раздаётся вовсе (§7.4), так что ссылка на них указывала бы не туда, что померили;
- ни один член архива не убегает из каталога. Фильтруем сами, а не через
  `tarfile(filter="data")`. Имя члена — относительный путь, и проверяется он
  **покомпонентно**: каждый кусок между `/` обязан целиком совпасть с
  `\A[A-Za-z0-9][A-Za-z0-9._-]{0,127}\Z` (якоря именно `\A`/`\Z` — `$` в Python
  матчится и перед завершающим `\n`, так что `model.stl\n` прошёл бы). Отдельного
  списка запрещённых форм нет и не нужно — всё умирает об это правило: `..` не
  начинается с буквы или цифры, у абсолютного пути и у ведущего `/` первый компонент
  пустой, у `a//b` и `a/./b` пустой или `.` компонент в середине, а backslash, NUL и
  любой не-ASCII (включая гомоглиф `⁄` U+2044) в алфавит не входят. Тип — только
  обычный файл, симлинки/хардлинки/устройства/FIFO отвергаются. Дальше две
  независимые линии, и после переезда на дерево их именно две, а не одна:
  `os.path.realpath(target)` обязан лежать **внутри** staging-каталога — проверка по
  компоненту пути, а не по префиксу строки, иначе соседний `<staging>-evil/`
  считается «внутри», — и весь путь проходится по одному компоненту за раз через
  `mkdirat`/`openat` с `O_DIRECTORY|O_NOFOLLOW`, а файл создаётся
  `O_CREAT|O_EXCL|O_WRONLY|O_NOFOLLOW` относительно уже открытого каталога. Ядро при
  этом ни разу не разрешает путь длиннее одного компонента, поэтому симлинк на любом
  уровне — ошибка, а не перенаправление, даже если его положили между двумя членами;
- **записи-каталоги пропускаются молча, а каталоги хаб создаёт сам.**
  `tar -czf build.tar.gz .` — самая очевидная команда для CI модели — кладёт в архив
  запись `.` и по записи на каждый подкаталог, и отвергать их значит ломать всех на
  первом же шаге. Из записи-каталога не берётся ничего: ни имя, ни режим, ни сам факт
  её наличия. Каталоги делаются из путей ФАЙЛОВ, которым они нужны, с режимом 0755
  (`fchmod` по дескриптору, а не `mkdir(mode)`, — иначе umask процесса решал бы, сможет
  ли `app` читать собственную сборку), так что архив со списком `scripts/` и архив без
  него распаковываются одинаково;
- те же якоря и тот же принцип — для `pid` и `commit` из URL;
- `title`, `project` и `built` — не длиннее 200 (у `built` — 64) символов и без
  непечатаемых. Категория `Cf` отвергается вместе с `Cc`: U+202E RIGHT-TO-LEFT
  OVERRIDE печатаемым не считается ничем, но `textContent` его честно применяет и
  разворачивает соседний текст. `built` проверяется наравне с остальными именно
  потому, что он едет ещё и в общий `/index.json`, который с `no-cache` качает
  каждый посетитель `/`: полмегабайта `built` от одного проекта — это испорченный
  индекс у всех. На дату он при этом **не** парсится (см. §7.3);
- метки `downloads` — только `\A[A-Za-z0-9._-]{1,32}\Z` (метка едет в подпись
  кнопки);
- **содержимое каждого файла вида** — тоже вход, а не «данные». Файл целиком
  уходит в `viewer.render()`, а вендоренный `three-cad-viewer` строит дерево
  деталей через `label.innerHTML = node.name` и дописывает
  `<span style="color:${color}">`. Библиотеку править нельзя (3.6 МБ, меняется
  целиком с релизом), поэтому дерево `{"version":…, "parts":[…]}` обходится
  рекурсивно на приёме: `name` — печатаемый текст без угловых скобок (для `title`
  скобки безобидны — их рисует наш `textContent`, — а здесь это тег), `color` —
  только `\A(#[0-9A-Fa-f]{3,8}|[A-Za-z]{1,32})\Z` или список таких значений.
  CSP тут подстраховка, а не замена: она гасит `<script>`, но не `form-action` и
  не переходы, а URL сборки вечный и того же origin, что все остальные проекты —
  отозвать stored HTML injection оттуда нечем;
- минимум один вид;
- потолки: суммарный **записанный** размер (не тот, что заявлен в заголовке члена;
  `MAX_BUILD_BYTES`, 64 MiB — тот же потолок, что и на тело, поэтому сжатая бомба им
  же и ловится), число членов архива (`MAX_MEMBERS`, 1024 — было 256 под плоскую
  сборку, поднято под исходник, где `scripts/` и `ref/` на несколько десятков файлов
  каждый — норма) и глубина пути (`MAX_PATH_DEPTH`, 8 компонентов вместе с именем
  файла: `ref/vendor/rev2/part.step` — это 4, а восемь компонентов по 128 символов
  плюс staging-префикс всё ещё далеко от `PATH_MAX`, так что принятый архив не может
  упасть на `ENAMETOOLONG` посреди распаковки, то есть 500-м на архиве, который
  ничего не нарушил);
- дубли членов ловятся по **всему пути** и со свёрткой регистра: `a/File` и `A/file` —
  один файл на APFS и на bind-mount Docker Desktop, а `a/model.py` и `b/model.py` —
  два разных, так что свёртка только последнего компонента ломала бы обычное дерево;
- имя, занятое и файлом, и каталогом (`a` рядом с `a/b.py`), — это 422, а не 500:
  `EEXIST`/`ENOTDIR`/`EISDIR`/`ELOOP`/`ENAMETOOLONG` считаются виной пуша, всё
  остальное от ФС (в первую очередь `ENOSPC`) остаётся `OSError` и уходит 500-м —
  ровно по тому же правилу, по которому битый архив не путается с полным диском.

### 7.2 Атомарность

1. распаковка в `data/project/<pid>/.tmp-<commit>-<uuid>/`;
2. валидация и запись нормализованного `meta.json`;
3. `os.rename` → `data/project/<pid>/<commit>/` — атомарно в пределах ФС;
4. переключение `latest`: `os.symlink(commit, tmp)` + `os.rename(tmp, latest)` —
   атомарная замена симлинка, читатель не видит промежуточного состояния;
5. `builds.json` и корневой `index.json` — тоже «временный файл + rename».

Шестым шагом здесь стояла ретенция — её нет с решения 2026-08-27 (§5.3), и публикация
заканчивается на пятом.

Ни на одном шаге не должно существовать момента, когда `latest` указывает на
наполовину распакованный каталог.

Публикация в локальный слот (§7.6) идёт по тем же шагам 1–2, а вместо 3–4 делает swap
каталога: старый `dev/` переименовывается в `.trash-<uuid>`, новый занимает его место,
старый удаляется. Дальше — только шаг 5 (`builds.json`, чтобы переключатель узнал, что
слот занят) плюс перезапись `index.json`: `latest` локальная сборка не трогает, а
корневой индекс — трогает, потому что в карточке есть флаг «слот занят» (§7.6). Что
она не может — это создать карточку: её нет у проекта без коммит-сборки. Инвариант тот
же: читатель не оказывается внутри каталога, который наполняют.

Тело запроса пишется сразу в файл `data/.upload-<uuid>` и оттуда открывается
`tarfile` — не через `BytesIO`: сборка в памяти давала пик в два тела (64 MiB
превращались в 128 MiB), и нескольких параллельных ретраев CI хватало на OOM.
Принятый пуш это тело не выбрасывает, а переименовывает в `.body-<uuid>`: оно
живёт до конца сборки и на успешном пути становится кодом ревизии (§7.8).
Переименование — и есть смена владельца: `.upload-` удаляет поток запроса всегда,
`.body-` принадлежит задаче.

Все временные имена — с точки: `.tmp-*`, `.latest-*`, `.upload-*`, `.trash-*`,
`.wip-*`, `.src-*`, `.body-*`. Поэтому их не видит ни `builds_of`, ни раздача — и
поэтому же после SIGKILL они остаются на томе навсегда. `Store.__init__` сметает
такие записи старше часа (младше — могут принадлежать живой публикации; час
покрывает и `.src-*`/`.body-*`, живущие очередь плюс сборку, — это шестнадцать
минут при сегодняшних `MAX_QUEUED_JOBS`, `wall_seconds` и двух воркерах).

**`.trash-` в этом списке остался, хотя удалять сборки больше некому:** через него идёт
перезапись слота `dev` (§7.6, `_swap_dev_slot`) — старый каталог сначала уезжает в
`.trash-<uuid>` и только потом `rmtree`. Правило, ради которого так делалось у ретенции,
переживает саму ретенцию: `rmtree(ignore_errors=True)` НА МЕСТЕ оставляет каталог,
который всё ещё раздаётся, но уже потерял `meta.json`, — то есть выпал из `builds_of` и
не будет убран уже ничем. Переименование, наоборот, одним атомарным шагом делает каталог
невидимым для раздачи, а саму уборку — необязательной: не доделали `rmtree` — остаток
подметёт часовое отсечение.

### 7.3 Ретенции нет

Механизма нет ни у сборок, ни у задач, ни у локального слота, ни у комментариев —
решение 2026-08-27, обоснование в §5.3. Из кода удалены `RETENTION_BUILDS`, `Store._prune`,
`Store._delete_build` и всё, что существовало только ради них; тем же решением ушли
`COMMENT_MAX_PER_BUILD`, `COMMENT_MAX_TOTAL` и весь подсчёт комментариев, который их
обслуживал (§7A.4). Опубликованная сборка
лежит на томе, пока её не удалит человек, и другого способа нет.

Локальный слот исключением не является, но у него есть и своя причина не копиться: это
один каталог, который каждый пуш перезаписывает целиком (§7.6).

Единственное, что удаляется автоматически, — то, что сборкой и задачей НЕ является:
временные имена с точкой старше часа (`Store._sweep_leftovers`, §7.2) и посторонние
записи в `data/jobs/` (`_sweep_strangers`, §7.4). Это уборка мусора, и путать её с
ретенцией нельзя: под неё не попадает ни одна опубликованная сборка и ни одна запись о
задаче.

### 7.4 Раздача

| Путь | Кэш |
| --- | --- |
| `/project/<pid>/<commit>/*` — файлы сборки | `public, max-age=31536000, immutable` |
| `/project/<pid>/<commit>/` и `.../index.html` — сама страница | `no-cache` |
| `/project/<pid>/latest/*` и `/project/<pid>/dev/*` | `no-cache` |
| `/_v/three-cad-viewer.*` | `public, max-age=31536000, immutable` |
| `/_v/hammerola.js`, `/_v/pointer.js`, `/_v/site.css` | `no-cache` |
| `/`, `/index.json`, `/project/<pid>/builds.json` | `no-cache` |
| `/api/v1/jobs/<id>` и `/api/v1/jobs/<id>/log` | `no-cache` |
| `/api/v1/sources/<revision>` и `/api/v1/sources/<revision>/log` | `no-cache` |

`immutable` на `/_v/*` целиком было бы неправдой: вендоренный `three-cad-viewer.*`
действительно неизменяемый — новая версия приезжает файлом с другим именем, — а
`hammerola.js` и `site.css` наши и меняются с образом под тем же именем. Год `immutable`
на них означает, что после деплоя нового вьювера все, кто уже открывал сайт, до года
сидят на старом JS, и отозвать выданный кэш нечем.

Ровно поэтому **страница сборки не лежит в каталоге сборки**. Она одинакова для всех
сборок и всех проектов и меняется вместе с образом — первый же скрипт страницы,
которому понадобится новый элемент разметки, сломал бы все ранее опубликованные
сборки, если бы
их HTML был вкопан в каталог под годовым `immutable`. Хаб отдаёт её из шаблона
(`render.build_page_html()`), как и `/`, с `no-cache`; неизменяемо кэшируется только
содержимое сборки. По этой же причине `index.html` из архива не раздаётся никогда:
этот URL принадлежит генерируемой странице.

Плюс `GET /health` для healthcheck из compose и `GET /project/<pid>/` → 302 на
`latest/`.

**Статус и лог сборки** (§8A.2, шаг 5) — единственная часть раздачи, которая не
публичная:

| Путь | Ответ |
| --- | --- |
| `GET /api/v1/jobs/<id>` | `application/json`: запись задачи целиком плюс `log_url` |
| `GET /api/v1/jobs/<id>/log` | `text/plain; charset=utf-8`: что напечатала сборка |

Непубличного на раздаче с тех пор стало больше: там же живёт КОД опубликованной
ревизии, `GET /api/v1/sources/<revision>` и `/log`, под тем же `EDIT_TOKEN` и
по тем же правилам, что ниже. Раскладка, инвариант и типы — §7.8.

И там же — **`GET /index.json`, СПИСОК ПРОЕКТОВ** (решение 2026-08-27, вместе с
переносом главной на React). Линия проходит не по «страницы публичны, API — нет», и
это стоит проговорить, потому что рядом две половины выглядят несогласованно.
СБОРКА публична целиком: страница, `meta.json`, геометрия, анонимно и с годовым
`immutable`. Она и есть продукт — постоянная ссылка, которую человеку ДАЛИ и которую
он кинул в чат; ссылка, спрашивающая у получателя секрет, продуктом быть перестаёт.
ПЕРЕЧИСЛЕНИЕ — наоборот: `index.json` единственный отвечает на вопрос «что вообще
есть на этом хабе», его никому не дают, и каждый id в нём — префикс всех постоянных
URL этого проекта навсегда. Правило: по выданной ссылке открывается ЭТА сборка, а
перечисление не открывается ничем.

Токен проверяется **до** чтения файла с тома — по той же причине, что и у задач:
иначе хаб с сорока проектами отвечает не так, как пустой, самим временем ответа.
Из этого следует форма главной: без токена она показывает не «список только на
просмотр», а экран входа, потому что показывать нечего — 401 приходит с сервера.
Оболочка `/` при этом публична (в ней нет данных, один `<div>` и `<script>`),
иначе браузеру нечем было бы нарисовать сам экран входа.

Оба — под `EDIT_TOKEN`, и токен проверяется **до** того, как хаб посмотрит на
`<id>`: иначе разница между 401 и 404 сама по себе рассказывает, какие задачи
существуют. Несуществующий `<id>`, чужой `<id>` и синтаксически кривой `<id>` дают
**одинаковый** 404 с одинаковым телом — id это единственное, что отделяет лог одного
пушера от лога другого (§3), и ответ, подтверждающий существование, отдал бы половину
этого разделения.

`text/plain` для лога — не косметика: это вывод МОДЕЛИ, а origin тот же, на котором
лежат сборки всех остальных проектов. `text/html` здесь был бы stored XSS ровно того
же вида, от которого закрыт белый список типов файлов сборки выше.

Лог отдаётся **с тома** на каждый запрос, и это надо читать вместе с 8A.4: том
полностью доступен сборке на запись, так что модель может переписать чужой `log.txt`,
прочитать любой лог мимо HTTP и завести в `data/jobs/` сколько угодно собственных
записей. Разграничение по `<id>` действует на уровне HTTP и НЕ является границей на
уровне тома; границы там нет вообще, и появится она только вместе с отдельным uid или
mount namespace на сборку. Из-за этого хаб не верит тому, что читает: запись
приводится к известной схеме, а у `job.json` и `log.txt` есть свои потолки на размер
— и при чтении, и при записи. Прямая цена отсутствия потолка на чтении — один
`job.json` на 20 МБ, уехавший в память потока запроса; и один `NaN` в записи, из-за
которого хаб переставал стартовать НАВСЕГДА: `json.loads` его принимает, а
`json.dumps(allow_nan=False)`, которым хаб пишет, — нет.

**Потолка на ЧИСЛО записей при этом нет — и это принятое следствие отказа от ретенции
(§5.3), а не недосмотр.** Сколько записей прочитает один старт, ограничено только тем,
что лежит на томе; остаётся потолок на размер ОДНОЙ записи (`MAX_RECORD_BYTES`), и он
делает ровно то, на что способен, — не даёт одному `job.json` уехать в память
неограниченным. Счётного потолка нет потому, что любое число на его месте — это решение
«какие задачи выбросить», а такого решения хаб больше не принимает: удалять записи
некому и незачем.

**Цена этого называется прямо, потому что раньше документ обосновывал ею обратное.**
Каталогов в `data/jobs/` ровно столько, сколько сделала последняя писавшая на том
сборка, и все они читаются: 2000 подложенных записей предельного размера — это порядка
128 МиБ кучи на старте, амплификация примерно 1:1 с занятым на диске местом. То есть
сборка, заполнившая том, назначает, сколько памяти нужно хабу, чтобы подняться. Это
принято, а не решено, и принято ровно потому, что стоит в одном ряду с остальным, что
может сделать сборка, имеющая том на запись (8A.4): она и так может снести чужой каталог
задачи, переписать чужой `log.txt` и просто занять весь том — счётный потолок закрывал
одну грань из нескольких, а платой за него была потеря настоящих записей (см. ниже).
Листинг при этом идёт `os.scandir`, а не `iterdir` (тот материализует все имена сразу),
то есть обход остаётся потоковым, а сверх самих записей в памяти держится ограниченное —
`MAX_STRANGERS_SWEPT` посторонних имён на подметание. ОБХОД не ограничен намеренно: на
затопленном томе он стоит времени и O(1) памяти, а время восстановимо — хаб, убитый по
памяти на старте, не доживает до того, чтобы подмести затопление, которое его убило.

**И вот чего счётный потолок стоил, пока был, — это и есть та половина размена, ради
которой его не надо возвращать.** Он применялся ДО чтения, по ПОЗИЦИИ, а нечитаемая
запись до реестра не доезжает и одну живую задачу собой не удерживает. Порча N записей у
свежего конца стоила поэтому до N настоящих задач у старого, и сборка выбирала и N, и
какие именно: 20 задач, потолок 5, пять испорченных `job.json` — реестр поднимался
ПУСТЫМ (пятнадцать старых удалены не читая, а прочитанные пять — это ровно испорченные).
Лечилось это срезом не по самому потолку, а по числу записей, которые хаб МОГ написать
сам, — то есть ещё одной подпоркой; без потолка ни подпорки, ни самой потери нет.

**Что в приведении записи фатально, а что нет.** Выбросить запись целиком —
основания ровно три: неизвестное `state` (ни идёт, ни закончилась: `_load` такую не
проваливает — он закрывает только `queued` и `building`, — так что хаб отдавал бы
пушеру статус, которого сам никогда не пишет), негодный
`id` (не строка нужной формы — тогда его нечем сравнить с именем каталога, а
расхождение указывает запись одной задачи на лог другой) и превышение
`MAX_RECORD_BYTES`. Всё остальное **усыновляется**, и это осознанная асимметрия:
выброшенная запись остаётся лежать на томе как есть, а усыновлённую хаб приводит к своей
схеме и записывает обратно. Поэтому неконечное число (`NaN`, `Infinity`) приводится к
`None` — законному значению этих полей.

**Метки времени при этом только типизируются, а не проверяются, и это тоже поменялось
вместе с ретенцией.** Раньше `created` из будущего зажимался в «сейчас» (`_created`,
`_epoch`), потому что дата из 2999 не старше никакого отсечения — она давала записи
иммунитет от возрастного потолка навсегда. Потолка нет, `created` больше ничем не
меряется и ничем не сортируется: это строка, которую видит тот, кто читает запись.
Поэтому обе функции удалены, а не оставлены «на всякий случай» — код, приводящий
значение, которое никто не читает, со временем начинают считать проверкой. Цена названа
честно: подложенная дата из 2999 доедет до пушера в статусе как есть. **Но если на этом
томе что-нибудь снова начнёт МЕРЯТЬ метку — возраст, порядок, что угодно, — оно обязано
сначала ответить на этот вопрос заново**, потому что вернётся ровно тот иммунитет.

Порядка в записи при этом нет вообще — и отдельным файлом он тоже больше не лежит, см.
ниже.

**И всё приведённое ЗАПИСЫВАЕТСЯ ОБРАТНО НА ТОМ.** Приведение живёт в памяти, а том
доступен на запись каждой сборке: если результат не доехал до диска, там продолжает
лежать подложенное значение, и следующий старт начинает с него заново — то есть
«починка» держится до конца процесса и фактом не становится никогда. **Довод здесь
поменялся вместе с ретенцией, и старый повторять нельзя:** раньше главным был возрастной
потолок — подложенная дата из 2999 зажималась в «сейчас» на каждом старте, не старела и
вечно занимала слот в `MAX_JOBS`. Возрастного потолка у записей больше нет, и оснований
писать обратно осталось два, оба самостоятельные: провал задачи, застрявшей в
`queued`/`building` после рестарта, обязан доехать до тома — иначе следующий старт снова
найдёт её незакрытой и снова проиграет тот же переход, а пушер по логу решит, что
сборка живёт; и на томе должна лежать запись в той форме, в которой её пишет хаб, а не в
той, в которой её кто-то положил, — иначе всё, что читает том, обязано повторять
приведение целиком и одинаково. Поэтому `_load` пишет обратно КАЖДУЮ прочитанную запись,
а не только проваленные.

**И у этого правила есть вторая половина, которой оно само же и научило: то, что
является свойством НАБОРА записей, нельзя хранить ПО ЗАПИСИ.** Проход пишет N
файлов, значит у него N мест, где остановиться, и выбирает место сборка — бесплатно и
без единой уязвимости: `chmod 0500` на одном каталоге задачи проваливает ровно одну
запись и никакую другую (перенос временного файла в общий каталог тут не помогает,
`rename` требует того же права на КАТАЛОГ-ПРИЁМНИК, что и `open`, — проверено).
Доехавший наполовину проход смешивает на томе два поколения разом — состояние, в котором
живой хаб не был НИКОГДА, — причём том ДО попытки записи говорил правду: починка портит
ровно то, что чинила. Правило стоило четырёх кругов ревью и остаётся в силе для всего,
что появится дальше; свойство набора едет одной атомарной записью или не хранится вовсе.

**Порядка создания задач при этом нет вообще — ни числом в записи, ни отдельным файлом,
и это решение, а не пропуск.** Порядок существовал ровно ради ретенции: он отвечал на
единственный вопрос «кого подрезать первым». Ретенции нет (§5.3) — вопроса нет, и
`data/jobs/order.json` удалён вместе со всей механикой чтения и записи порядка. Других
потребителей у него не было и нет: эндпоинта со списком задач не существует, `GET
/api/v1/jobs/<id>` и `/log` читают запись ПО ID, а загрузка восстанавливала порядок
только затем, чтобы подрезке было что считать. Заводить его обратно «на всякий случай»
не надо: на писчем для сборки томе файл порядка — это ещё одна вещь, которую сборка
пишет сама и неотличимо от нас, а единственное, что он когда-то покупал (точечный отказ
записи не переставляет реестр), теперь не покупает ничего — переставлять реестр стало не
для чего.

Каталог, в котором записи нет вообще (пустой, с мусором вместо JSON, или недописанный
самим хабом при полном томе), не удаляется сразу — он чьё-то свидетельство, — но и не
живёт вечно: старше `STRANGER_MAX_AGE_SECONDS` его подметает `_sweep_strangers`. **Это
не ретенция, и путать нельзя:** записи о задачах не удаляются никогда, а здесь уходит
то, что задачей реестра НЕ является, — мусор, подложенный сборкой или оставшийся от
записи, которую убили на полпути. Без подметания он живёт на томе вечно, потому что в
`data/jobs/` не ходит больше никто. Покрывает оно ВСЁ, что там лежит и задачей не
является: имя любой формы, посторонний файл, симлинк — а не только каталоги с
именем-идентификатором, как было раньше.

**У имён с временным префиксом (`.wip-*`) отсечение своё, короткое — час, как у
`Store._sweep_leftovers`, — и это не мелочь, а то, без чего перенос временных файлов
из каталога задачи в общий делал бы хуже.** В `data/jobs/` не ходит НИКТО, кроме этого
подметания: `Store._sweep_leftovers` обходит корень данных и каталоги проектов, а
`data/jobs/` — ни то, ни другое, так что знакомый префикс там невидим. На общем
отсечении остаток от убитой записи ждал бы 14 суток и ближайший старт, а
`.wip-log.txt-*` — это до `MAX_LOG_BYTES`, то есть 3 МиБ на остаток. **Отказ от ретенции
этот довод усилил, а не ослабил:** пока подрезка была, остаток, лежащий ВНУТРИ каталога
задачи, рано или поздно уходил вместе с ним — теперь каталог задачи не удаляется
никогда, и подметание стало единственным, что вообще способно такой остаток убрать.
Короткое отсечение безопасно ровно
здесь: `_sweep_strangers` работает из `JobStore.__init__`, когда пула ещё нет и сокет
ещё не привязан, то есть в этом процессе в `data/jobs/` никто не пишет. Час, а не
меньше, — потому что том можно разделить со вторым хабом, и там на этот же вопрос уже
отвечено часом.

И `mtime` из
БУДУЩЕГО считается старым: сборка ставит его свободно, а дата из 2999 не старше ни
одного отсечения, и каталог с ней был бы неприкосновенен до конца жизни тома. Это
единственная метка на этом томе, которую хаб ещё МЕРЯЕТ (у записей возрастного потолка
нет, см. выше), поэтому вопрос про будущее приходится закрывать именно здесь.
Исправить `mtime` и записать обратно нельзя: он и ЕСТЬ свидетельство, исправленный
уничтожил бы ровно то, что подметание бережёт. Поэтому он не исправляется — дата из
будущего просто не даёт неприкосновенности.

**Заголовки безопасности.** На каждом ответе — `X-Content-Type-Options: nosniff`; на
HTML — `Content-Security-Policy: default-src 'self'; img-src 'self' data:`. Отсюда
требование: ни одного инлайн-скрипта в шаблонах, весь JS страниц — файлами в `/_v/`.

`img-src ... data:` обязателен: `three-cad-viewer.css` держит весь тулбар в 74
свойствах `--tcv-icon-*: url("data:image/svg+xml,...")` (§2.2), а `'self'` схему
`data:` **не покрывает** — с голым `default-src 'self'` браузер молча режет все
иконки и тулбар приезжает пустыми квадратами. Скриптов это не ослабляет: SVG в
`data:`-URI грузится как картинка и скрипт в нём не исполняется, а `script-src`
остаётся унаследованным от `default-src 'self'`.

**Content-Type файлов сборки — по белому списку.** Имена членов архива проверяются,
а расширения нет, поэтому в сборке может лежать `page.html` или `logo.svg`. URL сборки
вечный, того же origin, что все остальные проекты, и с годовым `immutable` — отдать
такой файл «естественным» типом значит получить stored XSS, который уже нельзя
отозвать. Поэтому: `.json` → `application/json`, `.stl`/`.step`/`.stp`/`.3mf` → свои
`model/*`, **всё остальное** → `application/octet-stream` + `Content-Disposition:
attachment`. Исключение — `meta.json`, который хаб перезаписывает сам после валидации,
и `index.html`, который вообще не берётся из каталога сборки (см. выше). Ссылаться на
них из `views[].file` и `downloads` нельзя.

**Секрет ровно один, и имя у него не `PUBLISH_TOKEN`.** До шага 0 переменных было
две — `PUBLISH_TOKEN` на приём пуша и `COMMENT_READ_TOKEN` на чтение очереди, — и
схлопнулись они в одну по решению 2026-08-27 (§8, запись 26): «можно делать что
угодно», на систему, а не на проект. Имя выбрано новое, потому что старое врало
задолго до того, как лишилось пары: тем же `PUBLISH_TOKEN` уже открывались
исходники ЛЮБОГО проекта на хабе (§7.8) и маршрут, УДАЛЯЮЩИЙ проект. Переменная с
таким именем читается как «креденшл для CI на пуш» — и ровно поэтому её тянет
отдать CI общей организации, что после переезда (§8A.1) означает выдать
исполнение кода. `EDIT_TOKEN` называет право, а не один из способов им
воспользоваться, и совпадает со словом, которым это же значение уже называет
интерфейс: без него «View only», с ним «Editing on».

**Токен, а не пароль** — хотя человек и вводит его в форму. Это одна общая
строка, сверяемая на равенство; не на человека, не хешируется, отзывается только
вместе со всеми, и кто её предъявил, хаб не записывает. Слово «пароль» обещало бы
аутентификацию, которой нет (§8, запись 26 говорит это прямо), а
`hammerola login` значит «сохрани общий секрет», и ничего сверх.

**Миграция стоит одной строки в compose.** Переименование не трогает тех, кто
публикуется: по проводу едет ЗНАЧЕНИЕ в заголовке `Authorization`, а как свой
секрет называет чужой workflow — его дело.

Часть потолков **не** конфигурируется через ENV и живёт константами — их значения ни
от окружения, ни от проекта не зависят, а лишняя ручка в конфиге, которую никто не
крутит, только даёт возможность выставить её неправильно:

| Константа | Где | Значение | Зачем |
| --- | --- | --- | --- |
| `SOCKET_TIMEOUT` | `app.py` | 30 с | таймаут сокета на соединение. Соединение принимается до проверки токена (токен — в заголовке), так что без таймаута неаутентифицированный клиент держит поток бесконечно — slowloris |
| `MAX_CONCURRENT_PUBLISHES` | `app.py` | 4 | сколько **приёмов** идёт одновременно. Каждый держит тело на диске, tar-ридер и распакованное дерево; ретраи CI нескольких проектов разом — это ровно тот случай, который иначе всё умножает |
| `PUBLISH_WAIT_SECONDS` | `app.py` | 60 с | сколько ждать свободный слот приёма. Дальше — 503 с `Retry-After`, который CI отретраит, а не поток, залипший до таймаута сокета |
| `MAX_CONCURRENT_BUILDS` | `jobs.py` | 2 | сколько **сборок** считается одновременно. ПРЕДВАРИТЕЛЬНОЕ число, и оно об этом честно говорит: не измерено ничего, потому что сервис ни разу не выкатывался. Двойка не может быть очевидно неверной — сборка CPU-bound и держит тредпул OCCT, так что больше сборок, чем ядер, это чистая конкуренция за них. Заменить замером при первой выкатке, вместе с лимитами контейнера из шага 0 |
| `MAX_QUEUED_JOBS` | `jobs.py` | 16 | сколько пушей ЖДЁТ воркера. Очередь ограничена намеренно: неограниченная превращает «хаб не успевает» в «хаб принял всё, держит по распакованному дереву на запись и отрапортовал CI успех про работу, до которой доберётся через час». 503 с `Retry-After: 60` — правда, и CI уже умеет её обрабатывать |
| `STRANGER_MAX_AGE_SECONDS` | `jobs.py` | 14 суток | возраст, после которого из `data/jobs/` подметается то, что задачей реестра НЕ является: каталог без читаемой записи, посторонний файл, симлинк (§7.4). **Не ретенция:** записи о задачах не удаляются никогда, ни по числу, ни по возрасту (§7.3) — здесь уходит только мусор, которому в реестре не место. **Кроме имён с префиксом `.wip-`:** это остатки собственных незавершённых записей хаба, они ничьё не свидетельство, а `.wip-log.txt-*` — до `MAX_LOG_BYTES` каждый; им даётся час (`LEFTOVER_MAX_AGE_SECONDS`, но не длиннее самого возрастного потолка). Безопасно, потому что `_sweep_strangers` работает из `JobStore.__init__`, когда в этом процессе в `data/jobs/` ещё никто не пишет |
| `QUEUE_FULL_RETRY_AFTER_SECONDS` | `jobs.py` | 60 с | `Retry-After` при 503 «очередь сборки полна». Больше, чем 30 с у слота приёма, и намеренно: «занята очередь сборки» — это минуты, «занят слот приёма» — секунды |
| `MAX_STRANGERS_SWEPT` | `jobs.py` | 1024 | сколько посторонних записей каталога `data/jobs/` один старт запоминает под подметание. Список требует потолка: сколько всего лежит в каталоге, решает не хаб. Затопление собирается за несколько стартов, и это осознанно — темп, а не дыра |
| `MAX_RECORD_BYTES` | `jobs.py` | 64 KiB | сколько байт `job.json` хаб вообще прочитает. Запись — это сотни байт; потолок не про наш вывод, а про том, писчий для каждой сборки (§7.4): без него подложенный `job.json` на 20 МБ уезжает в память потока запроса. Не влезло — значит, писали не мы: запись пропускается целиком. Единственный потолок реестра, который остался: на ЧИСЛО записей потолка нет и не будет — это было бы решение «какие задачи выбросить» (§7.4) |
| `MAX_LOG_BYTES` | `jobs.py` | 3 × `Limits.log_bytes` (3 MiB) | потолок на `log.txt` — и при чтении, и при записи. **Выведен, а не назначен:** `runner._Drain` держит `log_bytes` СЫРЫХ байт и декодирует их с `errors="replace"`, а недекодируемый байт становится U+FFFD, который кодируется обратно в ТРИ байта. То есть модель, печатающая бинарь, заставляет хаб записать втрое больше того потолка, под которым шла сборка, — и меньшее число здесь означало бы, что хаб отдаёт УСЕЧЁННЫМ свой собственный лог, да ещё и с предупреждением «больше, чем может произвести сборка» |
| `WORKER_JOIN_SECONDS` | `jobs.py` | 5 с | бюджет ВСЕЙ остановки, а не таймаут на поток и не только на join. Ждём **публикацию** (`rename` плюс перекладка указателей — миллисекунды), а не сборку: сборка может идти до `wall_seconds`, а compose не объявляет `stop_grace_period`, поэтому SIGKILL от docker прилетает через 10 с независимо от этого числа. Ожидание длиннее грейс-периода не спасает ни одной сборки — оно только превращает каждую нормальную остановку в SIGKILL. Отсюда и общий дедлайн: помноженный на воркеров, бюджет съедает грейс-период сам по себе — уже при двух, — и растёт вместе с пулом, которому расти по замерам. **Часы запускаются ДО дренажа очереди**, потому что дренаж — это работа на том же томе (до `MAX_QUEUED_JOBS` деревьев на удаление и запись задачи с `fsync` на каждое), и отсчёт после него означал бы «5 с» в комментарии при реальной остановке «дренаж плюс 5 с» — то есть SIGKILL внутри того самого join, ради которого число и подбиралось |
| `WORKER_JOIN_FLOOR_SECONDS` | `jobs.py` | 1 с | пол на join, если дренаж съел бюджет. Итог: остановка ограничена `max(WORKER_JOIN_SECONDS, дренаж + пол)`, а не бюджетом сам по себе, и это честная формулировка — **сам дренаж не обрывается**. Оборвать его нельзя: брошенный на середине, он оставляет ровно те распакованные деревья и неотвеченные задачи, ради которых он и существует (`Store._sweep_leftovers` не увидит их ещё час). Пол при этом никогда не больше бюджета — иначе хаб, перенастроенный на остановку короче пола, получил бы остановку ДЛИННЕЕ заданного числа |

**Параллелизм сборки — отдельное число от параллелизма приёма, и это требование шага
5.** Четыре слота приёма обоснованы телом на диске, tar-ридером и распакованным
деревом; сборка обоснована ядрами и памятью, и её числа берутся из кода, а не из
прикидки: `Limits.occt_threads = 2`, `Limits.cpu_seconds = 300` против
`Limits.wall_seconds = 120`, то есть потолок разрешает до 2.5 процессорных секунд на
секунду стены — суммарно по потокам, потому что `RLIMIT_CPU` суммарный. Общее число
означало бы, что в день,
когда один из двух потолков перенастраивают по замерам, второй уезжает вместе с ним —
и восстановить, почему он там оказался, будет уже не по чему. По той же причине у
очереди сборки собственный `Retry-After` (60 с против 30 с у слота приёма): «занята
очередь сборки» — это минуты, а «занят слот приёма» — это секунды.

### 7.6 Локальный слот: публикация с ноутбука

Автор правит `model.py`, гоняет сборку и хочет увидеть результат **сейчас**, не делая
коммит. Коммита у такой работы нет, а вся адресация сборок построена на нём.

```text
POST /api/v1/publish/<pid>/dev
Authorization: Bearer <EDIT_TOKEN>
Content-Type: application/gzip
<тело: тот же gzip-сжатый tar, что у обычной публикации>
```

Всё, кроме двух вещей, — обычная публикация: та же валидация, та же распаковка в
staging, тот же атомарный swap, те же коды ответа. Различий ровно два: куда сборка
ложится и что после этого **не** происходит.

**Слот, а не сборка.** У проекта ровно один каталог `data/project/<pid>/dev/`, и каждый
пуш перезаписывает его целиком:

```text
data/project/<pid>/latest -> <commit>   СИМЛИНК на новейшую сборку ИЗ CI
data/project/<pid>/dev/                 КАТАЛОГ: текущая сборка с ноутбука
data/project/<pid>/<commit>/            неизменяемая сборка
```

Локальная работа — это не версия проекта, это состояние рабочей копии. Семнадцатая
попытка за вечер не «сборка №17», она просто то, что сейчас на экране, — как nightly.
Поэтому `dev` один, как `latest` один, и истории у него нет.

| Код | Когда | Тело |
| --- | --- | --- |
| 201 | слот перезаписан | `{"url": "/project/<pid>/dev/"}` |
| 200 | в слоте ровно эти байты | то же |

Остальные коды — как у §7.

**Почему перезапись под одним URL здесь допустима.** Каталог коммита отдаётся с
`Cache-Control: public, max-age=31536000, immutable`, и перезапись такого URL сделала бы
все розданные годовые кэши враньём, безотзывно — ровно поэтому §7 отвечает 409 на тот же
коммит с другим содержимым. Слот отдаётся `no-cache` — и страница, и все файлы внутри, —
поэтому обещания, которое можно нарушить, там просто нет. Это единственное, что делает
всю схему корректной, и `no-cache` на `<pid>/dev/**` — инвариант, а не настройка.

Отвергнутый вариант — **id от содержимого**, `dev-<12 hex sha256 нагрузки>`.
Он честно решал проблему кэша: каждая попытка получала свой неизменяемый URL. Но
следствие было хуже болезни — каждая попытка становилась отдельной сборкой, попадала в
`builds.json` и в переключатель рядом с настоящими коммитами (`dev-e9a448df778c`,
похожий на хеш, которого нет ни в одном репозитории), и оставалась там навсегда:
семнадцать вечерних попыток в списке версий проекта, из которого ничего не удаляется
(§5.3). Верный вывод из «неизменяемый URL нельзя перезаписывать» — **не отдавать
локальную сборку по неизменяемому URL вообще**, а не версионировать её.

**Идемпотентность осталась, но стала внутренней деталью.** Дайджест полезной нагрузки
(по именам и содержимому членов архива, без переписанного `meta.json`) сравнивается с
тем, что лежит в слоте: совпал — 200 и ни одной записи на диск. Смысл теперь не в
адресации, а в том, чтобы пересборка без изменений не дёргала страницу, которая открыта
перед автором. Ничего в URL из дайджеста не выводится.

**Публикация атомарна.** POSIX не умеет заменить непустой каталог под фиксированным
именем одним шагом (`rename` на каталог проходит только если целевой пуст), поэтому
swap — это: распаковать в скрытый `.tmp-…`, переименовать старый слот в сторону,
переименовать новый на его место, удалить старый. Читатель никогда не оказывается
внутри каталога, который наполняют; на ширину одного syscall он может застать имя
отсутствующим — это цена того, что слот **есть** сборка, а не симлинк на неё, и ровно
поэтому `latest`, который живёт в чужих чатах, устроен наоборот.

**`latest` не двигается, и карточки у слота нет.** `latest` — ссылка, которую кидают
людям, и она обязана значить «состояние на коммите»; незакоммиченная работа с одной
машины, двигающая её, ломает это обещание задним числом для всех, кому ссылку уже
дали, и отозвать её нечем. Главная — то же самое там, где смотрят все. Проект, у
которого есть только локальная сборка, не имеет ни карточки, ни `latest`: из коммита не
опубликовано ничего, и придумывать этому ссылку нечестно.

Сам файл `index.json` локальный пуш при этом ПЕРЕПИСЫВАЕТ, и это не противоречие:
карточка несёт флаг `dev` — «у проекта есть незакоммиченная работа», — и он должен
появляться тогда, когда появляется слот, а не на следующем коммите. Флаг говорит, что
слот ЕСТЬ, и ничего о том, что в нём: коммит, заголовок, число деталей и время на
карточке по-прежнему берутся из последней коммит-сборки.

**Слоту нечем копиться, и настраивать под него нечего.** Ретенции нет ни у кого (§7.3),
но у слота её нет ещё и по собственной причине: он ровно один каталог, и каждый пуш
перезаписывает его целиком, так что объём локальной работы не растёт вообще — ни от числа
попыток за вечер, ни со временем. Это единственное место в хабе, где что-то на томе
уменьшается само.

**Резервирование имён.** Занято ровно два имени, `latest` и `dev`: первое — симлинк,
второе — каталог слота, и оба ещё и последний сегмент маршрута публикации (`resolve`
зарезервирован отдельно и только для comment-API, §7A.2). Префикс `dev-` **не
зарезервирован**: он был нужен только отвергнутому варианту с `dev-<хеш>` выше — там
локальные сборки становились настоящими сборками, их приходилось отличать от коммитов и
считать отдельно, и коммит с именем `dev-1234` попадал бы не в ту кучу. Варианта нет —
`dev-1234` теперь обычный коммит с обычным вечным URL.

**Что видно снаружи.** В `builds.json` локальной сборки нет ни в каком виде: `builds` —
это история коммитов. Рядом со списком лежат два ответа про **имена** — `has_dev`
(занят ли слот) и `latest` (на какой коммит он сейчас смотрит), чтобы переключатель
сборок мог предложить их как отдельные пункты и не предлагал того, чего нет. В самом
`meta.json` сборки флаг `dev` остался: `commit` там читается как `dev` — имя слота —
и без флага страница напечатала бы `dev` там, где ждут хеш коммита.

Комментарий (§7A) на слот оставить можно: `POST /api/v1/comments/<pid>/dev` — это
единственное имя-указатель, которое принимается как цель. Довод раньше был «весь его
зритель — тот, кто прямо сейчас смотрит на экран автора»; после шага 0 писать в
очередь и так может только держатель `EDIT_TOKEN`, то есть сам автор, — и маршрут от
этого не стал бесполезным: заметка «вот эта деталь в том, что сейчас на экране»
остаётся ровно тем, ради чего слот и существует. `latest` целью не принимается:
завтра это другая сборка, и комментарий перестал бы называть геометрию, о которой
он был.

## 7A. Комментарии к сборке

Тот, у кого есть `EDIT_TOKEN`, тыкает в деталь на модели, пишет «поправь вот
тут», прикладывает фото. Комментарий копится в очереди хаба. Агент читает очередь
через MCP и правит `model.py` в репозитории проекта.

**Посылка сменилась в шаге 0: это заметка агенту, а не публичный канал.** Раздел
писался про ЗРИТЕЛЯ — «тыкает и пишет», без всякого токена, — и это отменено
решением §8A.1: хаб теперь исполняет присланный код, и анонимная запись в
очередь, которую агент разбирает как задачи, была дорожкой до выполнения кода, не
требующей ни одной уязвимости. Кому выдаётся право писать, решено просто: тому
же, кто публикует, потому что секрет один на систему (§8, запись 26). Да, если
писать может только автор модели, фича вырождается в заметку самому себе — и
именно так она теперь и называется; ценность её не в том, что пишет посторонний,
а в том, что якорь (§7A.1) переводит «вот эту деталь» в имя, за которым стоит
функция.

**Отвергнуто: issue в Gitea.** Один из двух доводов при этом отпал вместе с
анонимной записью: «публичная страница не должна иметь права писать в трекер»
больше не про нас. Остаётся второй — трекер под это избыточен; плюс issue требуют
аккаунта в форже, так что схемы всё равно не эквивалентны. Очередь в хабе даёт
агенту то же самое и оставляет место, где мусор можно отсеять, ничего не ломая.

### 7A.1 Якорь

Что несёт комментарий, помимо текста:

| Поле | Откуда | Зачем |
| --- | --- | --- |
| `pid`, `commit`, `view` | URL страницы | какая сборка и какой вид |
| `part` | пикинг во вьювере | **главное**: имя детали ведёт к функции в `model.py` |
| `point` | raycast, `[x, y, z]` | «рядом вот с этим местом» |
| `camera` | `getCameraPosition`, `getCameraQuaternion`, `getCameraTarget`, `getZoom` | ссылка открывает ТОТ ЖЕ кадр |
| `photo` | загружает человек | фото напечатанной детали — то, чего в модели не видно |
| `shot` | `pinAsPng` вьювера | рендер текущего вида, достаётся бесплатно |

Про ожидания: **точка в пространстве не указывает на строку кода**. Полезен
прежде всего `part` — он отображается на конкретный объект в `views()` и дальше
на функцию, которая его строит. Координата работает как уточнение «в этом углу
детали», не более. Это ограничение, а не недоделка.

### 7A.2 API

```
POST /api/v1/comments/<pid>/<commit>              требует EDIT_TOKEN
    multipart/form-data: поле `comment` (JSON), необязательное поле `photo`
    201 {"id": "..."}   401 без токена  404 такой сборки нет
    413 слишком большой  422 битый JSON или неподдерживаемый тип фото
    429 не бывает: числа комментариев никто не считает, частоту не ограничивает
    (§7A.4)

GET  /api/v1/comments?project=&status=&since=     требует EDIT_TOKEN
GET  /api/v1/comments/<id>                        требует EDIT_TOKEN
GET  /api/v1/comments/<id>/photo                  требует EDIT_TOKEN
POST /api/v1/comments/<id>/resolve                требует EDIT_TOKEN
```

**Очередь непублична целиком — и на чтение, и на запись.** Асимметрии больше нет,
и она была здесь до шага 0: запись была открыта всем, кто знает URL.

Про ЧТЕНИЕ довод не менялся: очередь — сырой ввод, он может быть мусорным,
дублирующимся или оскорбительным, и раздавать его всем значит превратить витрину
проектов в доску объявлений.

Про ЗАПИСЬ довод новый и он из §8A.1: хаб теперь ИСПОЛНЯЕТ присланный код, а
значит анонимная запись была первым шагом дорожки, не требующей ни одной
уязвимости, — комментарий пишется без токена → попадает в очередь → агент читает
его через MCP как задачу → агент правит `model.py` → хаб исполняет `model.py`.
Закрывается первый шаг: он единственный из пяти, который вообще можно закрыть, не
отменяя самой фичи.

**Токен проверяется ПЕРВЫМ**, до маршрута и до `Content-Length`. Иначе
неаутентифицированный отправитель по-прежнему заставляет хаб принять двадцать
мегабайт и разобрать их как multipart — ровно ту работу, ради отказа от которой
потолки и существуют. (В прежней редакции здесь стоял ещё и рейт-лимит: «до
маршрута, до рейт-лимита и до `Content-Length`». Рейт-лимита больше нет, §7A.4.)

### 7A.3 Хранение

```
<data>/comments/<pid>/<id>.json      комментарий
<data>/comments/<pid>/<id>.<ext>     фото, если приложено
```

**Вне каталога сборки, и это намеренно.** Довод не про выживание — сборки не удаляются
вовсе (7.3), — а про ПРАВА и про кэш. Каталог сборки раздаётся публично и с годовым
`immutable` (3.2), а очередь комментариев не публична на чтение (7A.2): это сырой ввод от
кого угодно, и место его хранения не должно совпадать с местом, которое хаб отдаёт всем.
Ошибка там ещё и необратима — комментарий, уехавший под годовой кэш, не отзывается.
Плюс комментарий привязан к ПРОЕКТУ, а не к каталогу одной ревизии: имя детали и
координата продолжают значить что-то в модели и через десять коммитов, поэтому
`<data>/comments/<pid>/` — их естественный дом.

**Каталог растёт без потолка, и это принято.** Ни на число комментариев в
проекте, ни на число во всём хабе ограничения нет (§7A.4, решение 2026-08-27), и
удаляется отсюда ровно одно: очередь проекта целиком, когда удаляют сам проект
(`CommentStore.remove_project`) — иначе комментарии остались бы висеть на
`<pid>/<commit>`, которого никто не может открыть. Отдельный комментарий не
удаляется ничем: обработанный закрывается через `resolve`, который оставляет и
запись, и заметку. Это тот же размен, что в §5.3, и в тех же единицах — JSON-файл
и фотография против механизма, который надо написать и который умеет удалить не
то.

### 7A.4 Запись под токеном — что обязано быть и после этого

Раздел назывался «Публичная запись — что обязано быть» и перечислял, чем
огораживают эндпоинт, открытый всем, кто знает URL. Такого эндпоинта больше нет
(§7A.2, шаг 0). Список пришлось перебрать по одному пункту, и линия разреза
прошла по вопросу «а этот пункт вообще про отправителя?»: **всё, что про БАЙТЫ,
осталось; всё, что про ЧИСЛО и ЧАСТОТУ, ушло.** Первое не становится безопасным
от того, что у отправителя есть креденшл, — работа над телом остаётся работой.
Второе без анонимного отправителя оказалось ни про что.

Что осталось:

- **потолок длины текста и потолок размера фото**, отдельно от `MAX_BUILD_BYTES`.
  Разбор с неограниченным телом — это работа, которую заказывает кто-то другой; и
  сборка на 64 MiB через архивные правила, и фото, которое хаб сохраняет как
  пришло, — две разные величины и разные поводы;
- **тип фото определяется по магическим байтам, не по расширению и не по
  `Content-Type` из запроса**. Это про ВЫДАЧУ: байты возвращаются на том же
  origin, где лежат сборки всех остальных проектов;
- **SVG отвергать.** Это активный контент, а не картинка: у нас уже есть ровно
  такая находка по загруженным файлам сборки (ревью, §5);
- текст комментария **не рендерится на странице** — вообще. Зритель видит только
  «отправлено». Единственный потребитель текста — агент, и он получает его как
  данные. Страница, рендерящая собственный ввод, была бы stored XSS на
  same-origin URL независимо от того, чей креденшл был у писавшего.

**Ограничителя частоты нет, и потолков на ЧИСЛО комментариев нет** — решение
2026-08-27. Три механизма исчезли разом: `COMMENT_MAX_PER_BUILD`,
`COMMENT_MAX_TOTAL` и рейт-лимит по адресу вместе со всем разбором
`X-Forwarded-For`, который его обслуживал. Это не «убрали, чтобы было проще»;
довод, на котором они стояли, кончился.

**Дверь теперь одна, и она под секретом.** Все три были написаны против
анонимного спама: писать мог кто угодно, кто знает URL, и вопрос стоял «как
ограничить постороннего, не зная о нём ничего». Шаг 0 закрыл этот вопрос целиком
— запись требует `EDIT_TOKEN` (§7A.2). А `EDIT_TOKEN` — единственный секрет
системы (§7.5): кто его предъявил, тот публикует сборки, переименовывает проект,
читает исходники любой ревизии и вызывает `DELETE /api/v1/projects/<pid>`, то
есть стирает проект вместе со всей его очередью комментариев одним запросом.
**Ограничивать частоту тому, кто и так может стереть проект, бессмысленно** — это
не защита, а способ отказать в шестом комментарии одного ревью. Прежняя причина
ушла вместе с анонимным отправителем, а новую придумывать не стали.

Отдельно про потолки на число, потому что у них была своя, отдельная роль
«СТЕНЫ»: комментарии не удаляются (§5.3), так что сборка, добравшая
`COMMENT_MAX_PER_BUILD`, комментироваться не могла бы больше никогда. Это худшая
форма потолка из возможных — не «выбросим старое», а «дальше нельзя», причём
навсегда и без способа починить. Ушли они по тому же решению, по которому нет
ретенции нигде (§5.3): комментарий — это JSON-файл и фотография, десятки
мегабайт на том, который и так растёт монотонно, и цена механизма выше цены
места. Ровно поэтому и **рейт-лимит перестал что-либо покупать**: единственное,
чем он оправдывался после шага 0, — «это единственный самозалечивающийся потолок,
он ловит зациклившегося клиента ДО того, как тот сожжёт сотню слотов сборки
навсегда». Слотов больше нет, жечь нечего, сторожить нечего.

Что при этом НЕ отменено и не должно быть отменено заодно: **потолки на размер**
(тела запроса, вложения, полей) — они про работу, которую хаб делает над телом, а
не про ретенцию; **проверка типа вложения по первым байтам** и **отказ от SVG** —
они про исполняемый контент, отдельная история. Число и размер — разные вопросы,
и ответ на один не является ответом на другой.

Одна вещь при удалении потеряна, и её стоит записать, чтобы не переоткрывать
дорогой ценой, если адрес клиента когда-нибудь понадобится снова (в логе,
например): **из `X-Forwarded-For` читается ПРАВАЯ запись, а не левая.** Каждый
прокси ДОПИСЫВАЕТ адрес, с которого принял соединение, значит при одном доверенном
прокси перед нами (Traefik) последняя запись — то, что прокси действительно
видел, а всё, что клиент вписал сам, приезжает ЛЕВЕЕ и должно игнорироваться.
Чтение левой записи — обычный способ это написать — даёт отправителю новую запись
на каждый запрос. И сам заголовок читается только тогда, когда пир — доверенный
прокси; при прямом доступе там ровно то, что напечатал отправитель.

Отменённых требований, таким образом, четыре, и все стоит назвать, чтобы не
восстановили: **«эндпоинт открыт всем, кто знает URL»**, потолок на сборку,
глобальный потолок и рейт-лимит. Всё остальное в списке пережило смену посылки,
потому что было выведено не из неё.

### 7A.5 MCP для агента — эндпоинт В ХАБЕ, не отдельный сервис

`POST /mcp`, авторизация заголовком, тем же `EDIT_TOKEN`. Инструменты:

- `list_comments(project?, status?, since?)` — очередь;
- `get_comment(id)` — комментарий целиком, включая фото;
- `resolve_comment(id, note)` — пометить обработанным, чтобы агент не разбирал
  один и тот же дважды.

**Первым решением был отдельный MCP-сервер, и это было ошибкой.** Обоснование
звучало как «хаб должен остаться чистым HTTP-сервисом», то есть как принцип, за
которым ничего не стоит. Разваливает его само устройство протокола: MCP работает
поверх HTTP (`type=http`, путь `/mcp`, авторизация заголовком) — это штатный
транспорт, а не экзотика. Значит отдельный сервер был бы **чистым прокси над HTTP
API хаба**: лишний деплой, второй токен, второй репозиторий, который обязан
догонять каждое изменение схемы комментария.

Данные лежат в хабе, авторизация в хабе, доменная модель в хабе. Эндпоинт
переиспользует всё это и не добавляет ни одного нового класса риска: на этом
origin аутентифицированные эндпоинты уже есть.

**Цена, которую надо принять осознанно.** `src/` намеренно держится на stdlib
поверх pydantic и loguru — ревью специально вынесло `httpx` в dev-зависимости,
чтобы это свойство сохранить. Тянуть ради трёх инструментов SDK `mcp` — значит
его потерять. MCP поверх HTTP это JSON-RPC 2.0 с маленьким набором методов
(`initialize`, `tools/list`, `tools/call`), поэтому пишем руками на stdlib.
Взамен мы сами отвечаем за соответствие спеке: **зафиксировать в коде, какую
ревизию протокола реализуем**, и сверяться с ней при обновлении.

### 7A.6 Что придётся вернуть во вьювере

`selectTool` выключен (см. коммит про редакторы внешнего вида), а **без пикинга
ткнуть в деталь нельзя**. Включать его в режиме комментария, а не постоянно:
в обычном просмотре выделение деталей зрителю не нужно.

## 7B. Разрез по грани

Инструмент для ЧЕЛОВЕКА, а не данные для агента. Section analysis из Fusion:
посмотреть, что внутри непрозрачной детали. Ничего не сохраняется, в комментарий
не уезжает, агент об этом не знает и знать не должен.

Ткнул в грань — она задала **ориентацию** плоскости. Дальше плоскость возится
мышью туда-сюда. Ползунки остаются индикатором положения, а не способом
управления: управлять ими и есть та неудобная часть, ради которой это делается.

Что уже даёт библиотека:

| Шаг | API |
| --- | --- |
| поставить плоскость по грани | `setClipNormal(index, normal, value)` — нормаль **произвольная**, оси в `resetClip` это лишь дефолты |
| двигать рез | `setClipSlider(index, value)` → внутри `clipping.setConstant` + перерисовка |
| прочитать текущее | `getClipSlider(index)` |
| разрез по взгляду | `setClipNormalFromPosition(index)` — уже готовое, стоит вывести кнопкой |

Чего библиотека НЕ даёт и что надо сделать самим:

- **Нормаль грани.** Пикер работает по id-буферу на GPU и возвращает точку, но
  не нормаль. Нужен обычный three.js `Raycaster` по тому же экранному пикселю,
  `intersection.face.normal`, переведённая в мировые координаты матрицей объекта.
- **Фильтр по типу.** Пикер разрешает приоритет **вершина > ребро > грань**.
  Для разреза нужна именно грань, иначе клик рядом с ребром даст чужую нормаль —
  у `pickAt` для этого есть `topoFilter`.

Два края, на которых это ломается, если сделать наивно:

1. **Система отсчёта слайдера.** `value` — константа плоскости в мировых
   единицах, но `resetClip` ставит её в `gridSize / 2`, то есть ноль привязан к
   сетке, а не к началу координат. `value` для клика надо вычислить как проекцию
   точки на нормаль **в той же системе**, а не подобрать. Промах виден сразу:
   плоскость прыгает в сторону от того места, куда ткнули.
2. **Вырожденное направление.** Перетаскивание мапится на экранную проекцию
   нормали. Когда нормаль смотрит почти в камеру, проекция вырождается и
   чувствительность уходит в бесконечность. Нужен потолок и минимальная длина
   проекции, ниже которой перетаскивание игнорируется.

### 7.7 Идентификатор ревизии: хеш исходников

**Ревизию именует хаб, и имя — это её содержимое.** `POST /api/v1/publish/<pid>`
без последнего сегмента: пушер не знает, под каким именем публикует, потому что
имени у него нет. `hammerola commit` значит «опубликуй версию этого», а не
«опубликуй под таким-то именем».

**Раньше имя приходило из git HEAD, и это было ошибкой в постановке.** Клиент
читал HEAD, отказывался публиковать грязное дерево и предлагал `--allow-dirty`.
Вся эта механика убрана: она отвечала на вопрос, которого никто не задавал.
Публикация версии — не свойство репозитория; каталог с `project.json` может её
сделать, репозиторий он или нет.

**Что именно чеканится.** `Store.mint_revision` возвращает `_payload_digest` —
sha256 по `{путь: sha256 содержимого}` всех членов архива, отсортированным по
пути. Тот самый отпечаток, на котором с шага 5 стоит идемпотентность
(`Store.settled`): второй механизм не заводился, взят существующий. Отпечаток по
построению не зависит ни от порядка членов в tar, ни от mtime, ни от прав, ни от
порядка обхода файловой системы — сортировка и хеш содержимого, больше ничего. Это
и позволяет двум машинам получить один адрес для одного дерева; клиент со своей
стороны пакует воспроизводимо (`pack._scrub` зачищает uid/gid/mode/mtime,
`pack.collect` сортирует), но хеш и без этого устойчив — он считается по
распакованному, а не по байтам архива.

**Почему не порядковый номер.** Номер читается человеком, и это единственное, что
он даёт. Взамен у публикации появляется состояние, которого сейчас нет: номер надо
где-то хранить, выдавать под локом и разводить два одновременных пуша, — а «те же
исходники — та же ревизия» становится проверкой, которая может разойтись с
идентификатором. С хешем это тождество: одно дерево не может получить два адреса.

**Полный хеш, не префикс.** sha256 в hex — ровно 64 символа, `SAFE_ID` разрешает
ровно 64, первый символ hex всегда буквенно-цифровой: влезает впритык, обрезать
нечего. Экономия длины URL ничего не покупает (в имени и так были 40 hex-символов
от git, и URL копируют, а не набирают), а платить пришлось бы вероятностью
коллизии: при n ревизиях и b оставленных битах она примерно n²/2^(b+1), то есть
~3e-8 для 64-битного префикса на миллионе ревизий. Мало — но цена события не мала
и не чинится: два разных дерева уехали бы на один URL, второе получило бы 409
навсегда, а другого имени у пушера нет, он их больше не выбирает.

**Что стало с 409.** «То же имя, другое содержимое» на этом маршруте невозможно по
построению: другое содержимое — другое имя. Мёртвым кодом ветка при этом не стала,
и это стоит держать в голове.

- На **именованном** маршруте (`<pid>/<commit>`) 409 — обычный случай, каким и был:
  маршрут жив, под ним публикуют репозитории моделей со старым `publish.yml`
  (§8A.2, шаг 7).
- На **чеканящем** — 409 остаётся ответом на каталог, который существует под этим
  именем, но не несёт читаемого `.payload.sha256`. `data/` — том, куда любая сборка
  пишет куда угодно (§8A.4): недописанный каталог, файл, снесённый чужой сборкой,
  проигранная гонка на unlink. Сравнивать тогда не с чем, а 200 объявил бы
  состоявшейся публикацию, которая могла не дойти.

**Связь с git односторонняя, и это следствие порядка действий.** Сначала
публикуем, потом коммитим — значит хаб физически не может знать git-sha (коммита
ещё нет), а сообщение git-коммита хеш ревизии знает. Поэтому после успешного
`hammerola commit` клиент **предлагает** команду:

```
git add -A && git commit -m '<то, что дали в -m>' -m 'hammerola-revision: <hex>'
```

Предлагает — печатает готовую строку и останавливается; ни `add`, ни `commit` он не
выполняет. Предложения нет, если git отсутствует (публикация от него не зависела) и
если коммитить нечего (команда бы упала). Сообщение из `-m` идёт через
`shlex.quote`: оно приходит от пользователя и попадает в командную строку, которую
он скопирует, так что кавычки, `$(...)` и обратные кавычки обязаны доехать текстом.
Обратной ссылки — из ревизии в git — нет и не будет: она потребовала бы второго
запроса после коммита, а ревизия неизменяема и выдана с годовым `immutable`.

**В ответе два идентификатора, и они про разное.** 202 несёт `job` — это ЗАДАЧА
(ход сборки и её лог, непредсказуемая, живёт одну попытку) — и `revision` — это
РЕВИЗИЯ (что будет опубликовано, вечная, попадает в URL). Один и тот же исходник,
посланный дважды, даёт две разные задачи и одну ревизию; ровно в этом смысл схемы.

### 7.8 Код ревизии: хаб хранит исходники и отдаёт их под токеном

Решение и его обоснование — §8, запись 17. Здесь — как это устроено.

**Раскладка на томе.** Отдельное дерево рядом с `project/`, а не внутри каталога
сборки:

```text
data/sources/<digest>/source.tar.gz   тело пуша, байт в байт
data/sources/<digest>/log.txt         что напечатала сборка этой ревизии
data/.body-<uuid>                     то же тело, пока идёт сборка
```

**Не внутри каталога сборки** — потому что тот раздаётся публично и с годовым
`immutable`: ошибка там необратима, розданные копии не отзываются. Из `sources/`
наружу ведёт ровно один маршрут (ниже), а раздача файлов туда не дотягивается
вовсе — `_safe_name` живёт на один сегмент внутри каталога сборки.

**Адрес — это содержимое.** `<digest>` — тот же `_payload_digest`, которым
чеканится имя ревизии (§7.7), так что адрес кода и имя ревизии — одна строка. Из
этого следует всё остальное и ничего не приходится проверять отдельно: то же
дерево, посланное дважды, не может лечь вторым архивом; лежит тот файл, который
приехал ПЕРВЫМ, — тела двух пушей одного дерева не обязаны совпадать побайтово
(gzip-заголовок), а менять архив под уже опубликованной ревизией нельзя. На
**именованном** маршруте (`<pid>/<commit>`) код тоже хранится, но по дайджесту, то
есть НЕ по имени из URL сборки: маршрут доживает до шага 7 (§8A.2), и заводить
ради него второй способ адресации незачем.

**Кладётся только после состоявшейся публикации.** Исходники провалившейся сборки
не хранятся: автор видит отказ сразу же, как только вернулась команда, и дерево
лежит у него на диске; хабу хранить нечего и незачем, а лежащее в `sources/`
дерево, за которым не стоит опубликованной ревизии, — это ревизия, за которую
хранилищу нечем отвечать. Отсюда инвариант, который и надо держать: **архив есть
тогда и только тогда, когда есть опубликованная ревизия.** Локальный слот `dev`
исключён по той же причине — он не ревизия (§7.6): истории у него нет, следующий
пуш его затирает, возвращаться не к чему. Как только то же дерево публикуется
ревизией, дайджест тот же и архив ложится.

**Тело живёт до конца сборки.** Спул `data/.upload-<uuid>` принадлежит потоку
запроса и удаляется им всегда; принятый пуш переименовывает его в `.body-<uuid>`,
и дальше владелец — задача, ровно как у распакованного дерева `.src-<uuid>`.
Публикация переносит его в `sources/`, любой другой конец — удаляет. Рядом с
распакованным деревом тело НЕ кладётся намеренно: это дерево уезжает сборке на
вход, и архив внутри него стал бы ещё одним файлом, который видит модель.

**Лог кладётся вторым файлом.** Не потому, что иначе потеряется — задачи не
подрезаются, `data/jobs/<id>/log.txt` лежит столько же, — а потому, что копия при
задаче адресуется id ЗАДАЧИ, а он живёт одну попытку и нигде против ревизии не
записан. Через месяц у ревизии есть только её имя, и лог по нему иначе не
достать. Пишет его, как и копию при задаче, РОДИТЕЛЬ из захваченного вывода
(`BuildOutcome.log`), через тот же `_capped_log` — потолок один на обе копии, иначе
они разошлись бы на одном и том же тексте.

**Раздача — под `EDIT_TOKEN`, тем же, что и публикация.** Один секрет на
систему: кто его держит, тому можно всё; вторых ключей не заводим.

| Путь | Ответ |
| --- | --- |
| `GET /api/v1/sources/<revision>` | `application/octet-stream` + `Content-Disposition: attachment; filename="<revision>.tar.gz"`: тело пуша как есть |
| `GET /api/v1/sources/<revision>/log` | `text/plain; charset=utf-8`: что напечатала сборка |

Оба — `no-cache`. Токен проверяется **до** того, как хаб посмотрит на
`<revision>`, и все промахи одинаковы: несуществующая ревизия, ревизия без
сохранённого кода и синтаксически кривой сегмент дают один и тот же 404 с одним
телом. Какие ревизии существуют, и так видно — страница сборки публична; а вот
«чей код лежит на диске» хаб не подтверждает ничем, кроме выдачи самого кода.
Существование определяет АРХИВ, а не каталог: каталог с одним логом — это то, что
остаётся от убитого на полпути переименования, и читаться он обязан как «нет
кода», а не как половина ревизии. Тип содержимого — непрозрачное вложение, а не
`application/gzip`: это байты, которые прислал пушер, и отдаются они на том же
origin, где лежат сборки всех остальных проектов. Лог — `text/plain` по той же
причине, что и лог задачи (§7.4).

**Ретенции нет и здесь** (§5.3): код ревизии живёт ровно столько же, сколько сама
ревизия, и осиротеть не может по построению.

   считать нельзя», а потому, что он уже есть и до него уже дотягивается CI.

   Промежуточный вариант, если браться и вес мешает: общая база с пинами, два тонких

   удержание Cmd с зажатой кнопкой сейчас панит. Значит перехват придётся делать
   раньше контролов и гасить событие, либо выбрать другую клавишу — решать при
   реализации, но не удивляться на месте.

   Отдельный край: браузер и система забирают часть сочетаний с Cmd себе, и событие
   `keyup` после переключения окна может не прийти вовсе — режим залипнет включённым.
   Нужен сброс по `blur` окна и по потере видимости вкладки.

8. **Сохранять разрез при автообновлении dev/latest.** Камера уже переносится
   (7C), а плоскость разреза сбрасывается — и это надо изменить.

   Почему её сбросили: глубина отмерена от грани, которой в новой сборке может не
   быть, а ноль слайдера привязан к ЦЕНТРУ СЕТКИ, который едет вместе с габаритами
   модели. То есть то же число слайдера после пересборки означает другую физическую
   плоскость — перенести значение «как есть» нельзя, это дало бы разрез не там, где
   он был, и выглядело бы как случайный сдвиг.

   Как переносить правильно: хранить не значение слайдера, а **нормаль и точку в
   мировых координатах**, и после пересборки пересчитывать значение той же
   аффинной связью, которую инструмент разреза уже использует при постановке
   плоскости на грань — `v_new = v − plane.distanceToPoint(P)` (7B). Тогда
   плоскость встанет туда же в пространстве модели, независимо от того, куда уехал
   центр сетки.

   Край, который надо принять осознанно: если геометрия изменилась сильно,
   перенесённая плоскость может оказаться за пределами детали. Это честное
   поведение — видно, что разрез «уехал», и его можно подвинуть. Хуже был бы
   разрез, молча вставший не туда.

9. **Запоминать выбранный указатель (latest / dev) и открывать его по умолчанию.**
   Человек, который правит модель, живёт в `dev` и не хочет каждый раз переключаться.

   **Главная ловушка, и без неё фича становится вредной:** ссылка на конкретный
   указатель — это то, что кидают людям. Если открыть `/project/<pid>/latest/` и
   перебросить читателя на `dev` только потому, что так стоит в его localStorage,
   он увидит НЕ ТО, что ему прислали, и никак об этом не узнает. Явный URL обязан
   побеждать сохранённый выбор всегда.

   Отсюда разделение:

   - `/project/<pid>/latest/` и `/project/<pid>/dev/` — показывают ровно то, что
     написано в URL, и заодно ЗАПОМИНАЮТ этот выбор;
   - `/project/<pid>/` (без указателя) — вот здесь и применяется запомненное,
     с откатом на `latest`.

   Хранить **по проекту**, а не глобально: человек может править один проект и
   одновременно просто смотреть другой, и общий флаг перепутал бы их.

   Реализационная деталь: `localStorage` читается только в браузере, а
   `/project/<pid>/` сейчас редиректит на `latest` на сервере. Значит либо этот
   маршрут начинает отдавать маленькую страницу, которая сама решает, куда уйти,
   либо остаётся серверный редирект и страница `latest` прыгает на `dev` — второе
   даёт видимую двойную навигацию и лишний запрос.

10. **Сравнение двух ревизий** — в беклоге, обсуждено 2026-08-22, переписано
    2026-08-24 после разведки с замерами.

    Требование уточнилось и стало жёстче: **обе версии детали показываются
    полупрозрачными, а МЕСТО РАЗНИЦЫ — ярким**, всё в ОДНОМ окне. Это не «две
    сборки рядом» и не «пометить изменившиеся детали»: нужна сама разностная
    геометрия — где материала прибавилось и где убыло.

    Адресация не поменялась: `/project/<pid>/compare/<a>/<b>/`, где `<a>` и `<b>`
    — любые указатели или коммиты, то есть `dev` против `latest` будет самым
    частым случаем. Правило кэша выводится из уже написанной ветки выбора:
    `immutable`, только если ОБА сегмента — коммиты, иначе `no-cache`. Это про
    ФАЙЛЫ: сама страница сравнения, как и страница сборки, всегда отдаётся
    `no-cache` — так закреплено в 7.4, и годовой кэш на генерируемый HTML вешать
    нельзя. Одна засада: слово `compare` сегодня **валидный идентификатор
    сборки**, его придётся зарезервировать, а это ломающее изменение для проекта,
    который уже опубликовал коммит с таким именем.

    **Хеш буфера остаётся, но меняет роль.** Исходная посылка «геометрическая
    разность не нужна» верна ровно до требования показать МЕСТО разницы. Сам
    хеш при этом проверен на живых данных и работает: две независимые пересборки
    одного исходника дают побайтово одинаковый файл, а после правки одного
    параметра меняется хеш ровно той детали, которую параметр двигает. Держится
    это на двух свойствах, которых могло не быть: тесселяция детерминирована, а
    качество считается от bbox САМОЙ детали (в коде рядом комментарий «try to
    come up with stable a quality value»), поэтому добавление детали не портит
    хеши соседей.

    Новая роль хеша — **предфильтр**: неизменившаяся деталь стоит булевой
    операции ровно столько же, сколько изменившаяся (0.86 с при пустом
    результате), так что без отсева сборка платит за каждую деталь ни за что.
    Второй плюс пофайлового сравнения выше скорости: булева врёт молча на
    почти-совпадающей геометрии, а в сборке детали стоят вплотную и их грани
    почти совпадают по построению. Сравнивая деталь с её же версией, в эту
    ловушку не лезешь; считая всю сборку разом — лезешь добровольно.

    **Инстансированная форма экспорта (`keep_instances`) рассмотрена и
    отвергнута 2026-08-24.** Она схлопнула бы повторяющиеся детали (у T13 это
    `rib_web_0..3` и `rib_flange_0..3`) и дала настоящую экономию по проводу —
    gzip её не даст, у zlib окно 32 КБ, а буферы разнесены дальше. Но она
    меняет формат целиком: буферы едут base64, лист несёт `{"ref": n}`, и
    сравнение по байтам буфера ломается — одна и та же деталь может приехать
    телом в одной ревизии и ссылкой в другой. Размер сейчас не жмёт; вернуться,
    если станет.

    **Путь A, булева ядром — выбран и замерен целиком.** Собран настоящий
    артефакт на T13: чтение двух STEP 0.33 с, General Fuse 0.86 с, тесселяция
    0.30 с — **1.49 с на произвольную пару**, 2.37 МБ raw / 0.41 МБ gzip, то
    есть примерно как одна обычная сборка. На выходе один JSON, который
    скармливается СУЩЕСТВУЮЩЕМУ `viewer.render()` без единой правки вьювера,
    без второго бандла и без форка:

    ```
    id=/Group/rev a     alpha=0.18  color=#7a8fa6
    id=/Group/rev b     alpha=0.18  color=#7a8fa6
    id=/Group/removed   alpha=1.0   color=#d1495b
    id=/Group/added     alpha=1.0   color=#2a9d5c
    ```

    Точность проверена на настоящей ревизии: щель вентиляции 4.0 → 4.4 мм дала
    435 мм³ убранного (12 тел) и 206 мм³ добавленного (8 тел) — это ровно число
    изменившихся щелей, а не слайверы; тождество `V(A∩B) + V(A−B) = V(A)`
    сошлось с невязкой 0.005 мм³ при объёме 360 000. Изменение в 10 микрон тоже
    видно.

    **Считать надо General Fuse, а не отдельные `cut`.** Результаты побитово те
    же, 0.82 с против 2.06 с — но 2.06 замерено на ТРЁХ операциях (`cut`, `cut`,
    `common`), а артефакту `common` не нужен, так что честное сравнение с двумя
    `cut` даёт около 1.4 с и преимущество ближе к 1.7×. Главный довод всё равно
    не в скорости: у `BOPAlgo_Builder` есть `HasErrors()`/`HasWarnings()`,
    которых у `BRepAlgoAPI_*` в питон-биндингах нет вовсе.

    **Путь B, сравнение мешей в браузере — отпадает по арифметике, а не по
    вкусу.** Прогиб тесселяции считается от габаритов детали, и на нашем корпусе
    это 0.142 мм односторонний и 0.284 мм двусторонний шумовой пол. Числа взяты с
    ГРУБЫМ bbox (`optimal=False`) не для удобства вывода, а потому что именно его
    берёт сам тесселятор, — то есть это и есть тот пол, который реально будет в
    наших артефактах, а не гипотетический. А настоящая ревизия, на которой всё
    мерилось, двигает стенку на 0.2 мм — ниже
    двустороннего пола. Инструмент, который не видит собственную тестовую
    ревизию, задачу не решает. Сверху — вторая копия three: аддоны вроде
    `three-mesh-bvh` держат three в peer, а наш бандл его не экспортирует.

    **Путь C, экранный трюк — отвечает не на тот вопрос.** Показывает
    расхождение силуэтов на текущем ракурсе; для корпуса, у которого весь смысл
    внутри, это почти ничего. Depth-вариант заблокирован тем, что конструкторы
    three наружу не отдаются, а stencil-вариант дерётся за буфер с уже сделанным
    разрезом на клавише `C`.

    **Чем платим за путь A — три вещи, и первая требует отдельного решения.**
    (Четвёртой была ретенция, съедающая половину пары; она отпала вместе с самой
    ретенцией — последний пункт списка.)

    - **Ядро переезжает к хабу.** Предвычисление в CI покрывает ровно одну пару
      («против предыдущей»), требует пересборки родительского коммита и
      протухает на движущихся `latest`/`dev`; сборок у проекта копится столько,
      сколько было пушей, и ничего не удаляется (§5.3) — уже на двадцати
      ревизиях пространство пар около 210, дальше квадратично, то есть
      предвычислить всё нельзя. Ядро рядом с хабом
      считает любую пару за 1.49 с из уже лежащих STEP. Значит запись «Один
      образ: вьювер и билдер вместе» становится обязательной — **но она почти в
      восемь раз дешевле, чем в ней записано**: в рантайме этого пути `vtk`
      (593 МБ) и сам `cadquery` не импортируются вовсе, нужны `OCP` плюс `numpy`
      плюс `ocp-tessellate` — около 250 МБ распакованных, а не 1.97 ГБ. Цена —
      пин в обход объявленной зависимости, то есть отдельная поддерживаемая
      хрупкость.
    - **Протокол пуша расширяется: B-Rep ПО ДЕТАЛЯМ.** Сегодня STEP один на
      модель, нужен отдельный файл на деталь — и вот это как раз НЕ бесплатно.
      Имя члена архива обязано матчиться `\A[A-Za-z0-9][A-Za-z0-9._-]{0,127}\Z`,
      а имя детали ограничено только печатностью и запретом `<` и `>`, плюс путь
      в дереве по построению содержит `/`. Пример выше, `rev a`, через этот
      фильтр не проходит из-за пробела. Значит нужна схема санитайза имени
      детали в имя файла И обратное отображение файла в путь дерева — это
      отдельная работа, а не «положить рядом». Рамок у схемы больше, чем кажется.
      Санитайзить надо ПУТЬ, а не имя листа — иначе две одноимённые детали в
      разных ветках схлопнутся, — а путь это до 65 узлов по 200 символов каждый
      (потолок глубины 64 считается от корня на нуле),
      причём печатный Unicode: кириллица и CJK в имени детали законны. Уложить
      это в имя члена архива (128 символов над алфавитом `[A-Za-z0-9._-]`) с
      сохранением ОБРАТИМОСТИ невозможно по принципу Дирихле. Значит схема такая:
      усечение плюс хеш-суффикс даёт инъективность с точностью до коллизии хеша,
      а обратное отображение берётся ТАБЛИЦЕЙ — из манифеста сборки или из самого
      дерева view-JSON, — а не вычисляется из имени файла. И инъективность обязана
      держаться ПОСЛЕ свёртки регистра: приём отбивает 422 на членах, различающихся
      только регистром, а `Front` и `front` в одной модели законны.
      Тут же `MAX_MEMBERS` (1024 после шага 8A.2.2; было 256, когда архив был
      плоской сборкой): пофайловый B-Rep впервые делает число членов
      архива функцией числа ДЕТАЛЕЙ (сегодня они считаются по видам), то есть
      этот потолок превращается в потолок на число деталей — за вычетом уже
      занятых членов: `meta.json`, view-JSON по каждому виду, общий STEP. По
      весу публикация примерно удваивается: плюс ~0.55 МБ gzip на сборку,
      ~11 МБ на двадцать ревизий — и это уже не «окно на 20», а просто двадцать
      первых: том не удаляет ничего (§5.3), поэтому число растёт вместе с
      числом пушей.
    - **Отпало: ретенция могла съесть половину пары.** Пока ретенция была, ссылка
      на сравнение не наследовала вечность ссылки на сборку, и это требовало
      отдельного решения — держать кэш диффов вне каталога сборки, как у
      комментариев (7A.3), либо честно отдавать 410 на выпавшую ревизию.
      Ретенции нет (§5.3): обе ревизии пары лежат, пока их не удалит человек, то
      есть ссылка на сравнение разрешается ровно столько же, сколько ссылки на
      обе сборки, и 410 придумывать не под что. Где держать кэш диффов —
      остаётся вопросом прав и кэширования (каталог сборки публичен и с годовым
      `immutable`), а не выживания.
    - **Две полупрозрачные оболочки будут переставляться местами при вращении.**
      Сортировка прозрачного пообъектная, по центру ограничивающей сферы, и знак
      разности переворачивается на медленном повороте. Не блокер: яркий слой
      идёт непрозрачным и пишет глубину, поэтому он стабилен, а мерцание
      маскируется тем, что обе оболочки красятся ОДНИМ нейтральным цветом.
      Правится `renderOrder` руками, но не раньше, чем это увидят глазами.

    **Гейт приёмки обязателен — булева врёт МОЛЧА.** Замерено на нашей же
    геометрии: сдвиг детали на 0.1 мм дал пересечение 0 % при `IsDone=True`,
    `HasErrors=False` и валидных на вид телах, причём зона отказа НЕ монотонна —
    0.05 мм работает, 0.1 нет, 0.5 снова работает. `SetFuzzyValue` не лечит и
    умеет сделать хуже: при одном из значений объём пересечения вышел БОЛЬШЕ
    объёма обоих операндов. И ломается это не на «деталь переформовали», а на
    «деталь передвинули» — то есть на частом случае. Проверять:

    - тождество объёмов, ОБЯЗАТЕЛЬНО нормированное на объём:
      `|V(A∩B) + V(A−B) − V(A)| / V(A) < eps`. На настоящих ревизиях невязка
      1.4e-8 — это 0.005 мм³ при объёме 360 000, — так что порог можно ставить
      жёстко. Абсолютный порог в мм³ писать нельзя: на модели другого масштаба
      он будет означать другое;
    - `V(added) − V(removed)` должно совпасть с `V(B) − V(A)`;
    - «пусто» не равно «нет разницы»: пустая разность при пересекающихся
      габаритах и разных объёмах — это ОТКАЗ;
    - слайверы отсеивать не по объёму, а по характерной толщине `2V/S`;
    - таймаут ОТДЕЛЬНЫМ ПРОЦЕССОМ: зависания булевы и `UnifySameDomain` не
      ловятся ни таймаутом на треде, ни `Ctrl+C`.

    **Отдельная грабля, не про OCCT.** В CadQuery 2.8 обёртка `Compound` поверх
    солида считает булеву ПО ОБОЛОЧКАМ: объём выходит в десять раз больше
    правильного, тел ноль, `isValid()` возвращает True, исключения нет. Лечится
    `Shape.cast(x.wrapped)`. Плюс `Workplane.cut(clean=True)` по умолчанию гонит
    `ShapeUpgrade_UnifySameDomain` — известный источник и неверных результатов,
    и вечных зависаний; `Shape.cut` не чистит.

    **Как класть две ревизии в одну сцену.** Склеить оба дерева в один JSON с
    префиксами путей (`/cmp/revA/front`, `/cmp/revB/front`) и вызвать обычный
    `render()` — проверено в живом браузере, библиотека не патчится нигде.
    `addPart` для этого не нужен и даже вреден: добавленная ревизия,
    помещающаяся внутрь габаритов уже отрисованной (наш типичный случай), **не
    получает клип-стенсилов вообще** и на разрезе выглядит полой, потому что
    пересборка стенсилов запускается только при РОСТЕ габаритов. Лечится
    публичным `ensureStencilSize` с раздутым bbox, но при склейке проблемы нет
    вовсе.

    **И тихая порча, которую надо знать:** склейка БЕЗ префиксов не бросает
    ошибку — она теряет совпавшие детали. Замерено: 5 деталей на входе, 4 пути в
    реестре, 3 листа в дереве, но 5 объектов в сцене. Дубликат рисуется и ест
    кадр, но не адресуется: его нельзя ни спрятать, ни перекрасить, ни
    разрезать, а подсветка по пути зажигает обе копии. Единственный, кто
    проверяет коллизию, — `addPart`.

    **Цвета.** Единой конвенции в отрасли нет: зелёный-добавлено у GitHub, NX и
    AutoCAD, у CATIA наоборот, а в метрологии (GOM, Geomagic) красный вообще
    значит «лишний материал». Совпадает у всех одно — неизменившееся приглушают,
    а не красят. Значит легенда обязательна, палитра — colorblind-safe, и
    метрологическую радугу с булевым диффом смешивать нельзя.

    **Что ложится даром:** `captureLive`/`restoreLive` уже умеют возвращать
    состояние на пересобранную сцену, `getStates`/`setStates` дают переключение
    ревизий, а разрез по удержанию `C` оказывается не украшением, а
    необходимостью — внутренние различия в наложении видно только сечением.
    Мешает пикинг: полупрозрачная оболочка спереди перехватывает клики, лечится
    выключением слоя. А подсветку сносит НЕ вход в режим комментария — он только
    показывает и прячет кнопку инструмента. Сносит её, помимо прочего, выключение
    select-инструмента и `Escape` — эти два снимают выбор целиком; `Backspace`,
    правый клик по канвасу и повторный клик по уже выбранной детали снимают
    только ПОСЛЕДНЮЮ выбранную, что при одной детали то же самое. А главное для
    этой записи — ЛЮБАЯ пересборка сцены: `render()` деактивирует активный
    инструмент первым же шагом (в коде так и написано, «disable it as the first
    step»), `clear()` — в середине разборки, но так же безусловно.
    То есть пересборка сцены, на которой построена вся эта запись, и которую
    делает каждое переключение варианта, гасит подсветку: её придётся
    переустанавливать после рендера — ровно так, как уже переустанавливаются
    режим разреза и режим комментария.

    **Минимальный откат, если ядро к хабу не переедет:** предвычислять в CI дифф
    только против предыдущего коммита и говорить это в интерфейсе прямо.
    Произвольная пара тогда деградирует до подсветки по хешу на уровне деталей —
    то есть без места разницы, то есть без того, что просили.

11. **Заметка у детали** — в беклоге, обсуждено 2026-08-23.

    У каждой детали своё текстовое поле: ссылка, параметры, название по
    каталогу. Например «M3×8 DIN912», ссылка на даташит, взятый допуск.

    ЗРИТЕЛЬ в браузере, он уезжает в очередь и адресован агенту. Заметка
    пишется АВТОРОМ в `model.py`, едет вместе со сборкой и адресована тому,
    кто смотрит. Разные источники, разные направления, разные права.

    Место напрашивается: у детали в `printables()`/`views()` уже есть словарь
    с ключами `shape`, `name`, `color`, `alpha` — `note` встаёт туда же, и
    контракт `model.py` расширяется, а не ломается.

    дереве: дерево рисует вендоренный бандл, и произвольный текст в нём
    означает патч бандла, который придётся ребейзить на каждое обновление.

    **Два места, где это станет дырой, если сделать наивно:**

    - Текст приходит из пуша, то есть от того, кто может влить коммит в любой
      репозиторий организации `3d`. Он обязан пройти ту же проверку, что
      `title` и имена деталей (`_plain_text` плюс запрет `<`/`>`), и попадать
      на страницу только через `textContent`. В этом проекте уже поймали два
      stored XSS ровно на таком пути.
    - **Ссылка в заметке — отдельная поверхность.** Если делать её кликабельной,
      схему надо брать по белому списку (`http`, `https`, и всё): `javascript:`
      в `href` — это исполнение скрипта на общем origin с вечным кэшем. Проще
      начать с текста без автоссылок и добавить их отдельно, осознанно.

    **Пересмотрено записью «Свой интерфейс вместо библиотечного» ниже.** Запрет
    «в дереве нельзя» держался на том, что дерево рисует вендоренный бандл. С
    `tools: false` дерево становится нашим, и заметка
    может жить прямо в нём — вместе с библиотечным деревом уходит и ограничение.

13. **Разрез как в Fusion: узел в дереве и штриховка на торце** — в беклоге,
    обсуждено 2026-08-23. Продолжение 7B, и напрямую зависит от записи
    «Свой интерфейс вместо библиотечного».

    Целевое поведение снято с Fusion 360 по документации Autodesk, а не по памяти:

    - разрез там — **сущность в дереве** (папка `Analysis`, узел `Section Analysis`
      с иконкой видимости, правый клик → Edit/Delete), а не режим и не вкладка;
      геометрию не меняет и в timeline не попадает;
    - торец красится **двумя слоями**: заливка плюс диагональная штриховка поверх.
      `Section Color` по умолчанию `From Component` — цвет самой детали;
      `Show Hatch` — чекбокс, включён по умолчанию, параметров у штриховки нет;
    - обе опции живут в диалоге команды, а не в глобальных настройках;
    - плоскость ставится выбором плоской грани ИЛИ origin-плоскости, двигается
      манипуляторами `Distance`/`Angle` на канвасе или числом, есть кнопка `Flip`;
    - **исключить деталь из разреза нельзя** — режется всё видимое, а ненужное
      гасят по видимости. То есть отдельный тумблер «резать/не резать» у детали не
      нужен ни нам, ни эталону;
    - несколько разрезов создать можно, но одновременно, судя по всему, виден
      один (официально Autodesk этого не декларирует).

    **Что у нас уже есть, а чего нет.** Торцы рисуются классическим stencil-приёмом:
    front/back-стенсилы с `colorWrite:false` плюс cap-квад `PlaneGeometry(2,2)` с
    `MeshStandardMaterial`. Значит:

    - **заливка есть.** Цвет по умолчанию — захардкоженный `PLANE_COLORS`, и берётся
      он по НОМЕРУ плоскости и по теме: `light: [0xff0000, 0x00ff00, 0x0000ff]`,
      `dark: [0xff4500, 0x32cd32, 0x3b9eff]`. Мы стартуем с `theme: "dark"`, то есть
      у нас вторая тройка. Но опция `clipObjectColors` переключает торец на цвет
      детали — это ровно фьюженовский `From Component`, и у нас он сейчас в
      дефолте `false`, потому
      что мы его не выставляем. **Одна строка в `viewerOptions`;**
    - **штриховки нет** — см. ниже;
    - **обводки контура нет, и геометрии сечения не строится вообще**: рёбра модели
      просто обрываются на плоскости. Честная обводка — это либо построение кривой
      сечения каждый кадр, либо отдельный рендер-проход с детекцией края. Отдельная
      и заметно более дорогая задача, и у Fusion её в документации тоже нет — не
      смешивать со штриховкой.

    **Штриховка делается и без форка, но правильное место для неё — апстрим.**

    Снаружи: у капа геометрия `PlaneGeometry(2,2)`, то есть `uv` 0..1 по всей
    плоскости среза уже есть, и штрихи считаются в плоскости — при повороте и зуме
    они едут вместе с моделью, а не плавают по экрану. Правится `onBeforeCompile`
    на существующем материале (конструкторы three.js нам не отдают, а это свойство
    есть у любого материала). Три обязательных условия, иначе картинка поедет:

    - `customProgramCacheKey` нужен НЕ всегда, и важно понимать, когда именно.
      Дефолтная реализация возвращает `onBeforeCompile.toString()`, поэтому
      патченный материал и непатченный различаются сами собой, а один и тот же
      патч на всех капах честно даёт одну скомпилированную программу — лишних
      компиляций не будет. Ключ становится обязателен ровно в одном случае: если
      параметры штриховки (шаг, угол, цвет) уезжают в ЗАМЫКАНИЕ. Замыкания
      `.toString()` не видит, и капы с разными параметрами схлопнутся в одну
      программу. От этого же библиотека защищается своим ключом в подсветке
      выбора — но на материалах капов её патча нет, туда подсветка не доходит;
    - материалы капов **нельзя схлопывать в один**: порядок отрисовки держится на
      `material.id`, и именно он ставит стенсил и его капу подряд;
    - штриховка должна быть плоской, иначе `MeshStandardMaterial` затенит штрихи
      светом.

    Переприменять патч надо только после `render()` — и это наша точка, рядом с уже
    существующим `applySectionMode()`. Второй путь пересоздания материалов —
    `rebuildStencils`, и у него ровно два вызова: рост габаритов на
    `addPart`/`updatePart` и публичный `ensureStencilSize(bb)`, которым область
    пресайзят заранее. Ни того, ни другого у нас сейчас нет — смена варианта это
    `clear()` + `render()`, — но если `ensureStencilSize` появится ради плавного
    слайдера, патч штриховки надо переприменить и там, иначе он молча пропадёт.
    Главная же хрупкость не в этом, а в строковой хирургии по шейдерным чанкам
    three.js внутри бандла: завязка на версию three, а не на релиз вьювера.

    **Апстрим-путь и почему он реалистичен.** Лицензия MIT, автор мержит внешние PR
    за 1–5 дней (медиана ~1.7 по шести смерженным за пять лет), место под опцию уже
    готово: в панели Clip есть чекбокс `tcv_clip_caps`, переключающий цвет торца, —
    `Show Hatch` встаёт рядом тем же способом. Аргумент для issue — паритет с
    Fusion, где это дефолт. Поправка на характер: чужие диффы он переписывает под
    себя (PR #32 закрыл без мержа и в тот же день сделал сам), поэтому ставка —
    issue с работающим прототипом, а не «вмержат наш diff». Если уедет наверх, к
    нам вернётся обновлением двух файлов с npm.

14. **Форк three-cad-viewer — план Б, и вот при каком условии** — обсуждено

    Вопрос поднимался дважды, и оба раза ответ один: форк ради правок не окупается,

    **Факты об апстриме** (`bernhard-42/three-cad-viewer`, проверено 2026-08-23):
    MIT; TypeScript, rollup, vitest; 32.8k строк в `src/`, 25.5k строк тестов;
    386 звёзд; 411 коммитов и 19 релизов за год, 406 из них — один человек;

    в npm копию никто не переиздавал — прецедента «форкнули и живут» нет.

    `rollup.config.mjs` апстрима поля `external` нет вообще, поэтому three,
    `postprocessing` и `n8ao` запекаются внутрь. Разбором sourcemap померено (доли
    от 3.57 МБ): three вместе со своими аддонами — 2.14 МБ, 60%;
    Studio-зависимости — 415 КБ, 11.6%; собственный код вьювера — 630 КБ, 17.7%;
    оставшиеся ~10% в sourcemap не отображены — это обвязка rollup, инлайненный
    HTML-шаблон и data-URI. Вынести three наружу даёт две вещи сразу: аддоны three
    (`TransformControls`, `DragControls`) в ТОМ ЖЕ экземпляре —
    а это и манипулятор плоскости разреза из предыдущей записи, и поворот деталей
    мышью, который обсуждался 2026-08-21 и был отброшен ровно по этой причине (в
    репозитории следов того решения не осталось, поэтому оно записано здесь) — и
    файл ~1.0 МБ вместо 3.57. Блокер, который был раньше, снят самим автором:
    монкипатчинг `THREE.Mesh.prototype.dispose` убран в августе 2025, в нашем
    бандле его уже ноль. `postprocessing` и `n8ao` держат three в peer, поэтому
    выносить их придётся вместе.

    **Чего форк не даст:** вес three.js как таковой — он останется, просто отдельным
    файлом; формат JSON тесселяции — его генерит питоновский `ocp-tessellate`, и
    рендерер владеет только одной половиной контракта; валидацию имён и цветов на

    любом случае.

    **Довод «вторая половина контракта уедет» оказался слабее, чем считался:**
    `PROTOCOL_VERSION` в `ocp-tessellate` равен 3 с апреля 2024 (два бампа за всю
    историю), а вьювер номер версии вообще не валидирует — разбор идёт структурными
    type guard'ами.

    **Порядок действий, по возрастанию цены:** тянуть копию с npm с пином (и
    переписать PROVENANCE) → отправлять правки в апстрим (`Show Hatch` для торцов,
    `textContent` вместо `innerHTML` в подписях дерева, починка `pinAsPngCallback`,

17. **Хранение исходников по ревизиям.** Решено 2026-08-26: раз хаб
    становится форжем, он обязан хранить код, а не только результат. Сегодня
    дерево исходников удаляется `shutil.rmtree` в `finally` внутри
    `_build_and_publish` — **на всех путях, включая успешный**, — и к ревизии
    привязано только то, что сборка произвела. От самого кода остаётся один
    отпечаток: `metrics.source_fingerprints()` кладёт в метаданные два хеша,
    `written` и `code` (с вырезанными комментариями). Этого хватает ответить
    «исходник менялся или нет» и не хватает ответить «чем именно», и уж точно
    не хватает восстановить модель.

    **Требование:** публично код НЕ раздаётся, но проектировщик должен уметь
    его выгрузить, чтобы вернуться к другой ревизии.

    Отсюда следует место хранения: НЕ внутри каталога сборки. Тот раздаётся
    публично и с годовым `immutable`, поэтому ошибка там необратима — розданные
    копии не отзываются. Хранилище отдельным деревом, отдача под токеном.

    **Дёшево это стоит ровно потому, что тело пуша уже на диске:** приём
    спулит gzip-tar во временный файл и сейчас делает `unlink`. Вместо этого
    `rename` в хранилище — один файл на ревизию, байт в байт присланное, ноль
    новых зависимостей. Ретенции цепляться не к чему и не за чем: её нет
    (§5.3), так что исходник живёт ровно столько же, сколько сборка, — то есть
    всегда, и осиротеть не может по построению. Килобайты кода рядом с
    мегабайтами геометрии этот выбор ничего и не стоит.

    **Git рассмотрен и отложен, чтобы не возвращаться.** Из трёх реализаций
    подходит одна: `dulwich` — чистый Python, не требует ни бинарника `git`
    (его нет в образе), ни нативного кода; `pygit2` тянет libgit2, `GitPython`
    это обёртка над бинарником, а не реализация. Но для заявленного требования
    git не нужен вовсе. Дедупликация ревизий почти ничего не даёт — исходники
    это килобайты против мегабайтов геометрии. И у кода **уже есть**
    канонический git-дом: репозиторий модели в форже, которым пуш и
    адресуется.

    Довод «зависимость дорога, потому что `src/` держится на stdlib» здесь
    НЕ приводится сознательно: проект переезжает на фреймворк (запись
    «Переезд на фреймворк» ниже), то есть это свойство мы отдаём сами, и
    обосновывать им отказ нельзя.

    **Проверено по пунктам, что именно git дал бы, и почти всё отпадает.**
    Диффы исходника ему не нужны: код это `.py`, а `difflib` в stdlib даёт и
    построчный, и unified. Слияния не нужны в принципе — хаб принимает
    снапшоты, а не ветки, сливать нечего. История уже есть и без него: ревизии
    адресуются идентификатором коммита, лежат упорядоченно и никуда не
    деваются (§5.3), то есть список сборок проекта И ЕСТЬ история в нужном
    хабу виде — причём полная, без выпавшего хвоста.
    Остаётся ровно одно, чего иначе не получить: быть настоящим git-ремоутом,
    чтобы с хаба можно было склонировать. Это отдельная фича, а не следствие
    хранения исходников, и вот под неё — `dulwich`, когда форж поедет внутрь.

    **Оговорка про обратимость, чтобы решение не выглядело безрисковее, чем
    оно есть.** Перейти потом с тарболлов на git можно, каждая ревизия станет
    коммитом, но история выйдет ЛИНЕЙНОЙ и бедной: идентификаторы коммитов из
    URL пуша у нас есть, а графа, авторов и сообщений нет. Настоящий DAG
    задним числом не восстанавливается — он может прийти только из форжа, и
    значит забирать его надо В МОМЕНТ переезда, а не собирать потом из того,
    что накопил хаб.

    **Вместе с исходником хранится ЛОГ СБОРКИ.** Довод здесь НЕ «иначе лог
    потеряется»: задачи не подрезаются ни по числу, ни по возрасту (§7.3), и
    `data/jobs/<id>/log.txt` лежит столько же, сколько всё остальное. Довод в
    ПРАВАХ: у кода и лога они одинаковые, и обоим одинаково нельзя туда, куда
    можно артефактам. Код не публичен, и лог не публичен тем же самым образом —
    там пути внутри контейнера, трейсбеки и всё, что напечатала модель, — тогда
    как каталог сборки раздаётся всем и с годовым `immutable`, то есть
    безотзывно. Второй довод — цельность записи: лог это часть ответа на вопрос
    «КАК получилась эта ревизия», ровно как её исходник, и держать две половины
    одного ответа в разных местах, с разной адресацией и разными глаголами CLI,
    незачем.

19. **Дедупликация одинаковых файлов между сборками.** Довод всплыл как
    аргумент за git и был сначала отвергнут слишком узко: дедупликацию оценили
    только для ИСХОДНИКОВ, где она и правда копейки — килобайты кода, из
    которых между ревизиями меняется один файл. Жирное лежит не там.

    **Жирное — артефакты.** Между соседними ревизиями меняются одна-две детали,
    а буферы остальных байт в байт те же — это ровно та посылка, на которой
    стоит запись «Сравнение двух ревизий»: одинаковый хеш буфера = деталь не
    менялась. Ретенции нет (§5.3), то есть копий геометрии на томе столько,
    сколько было пушей, и подавляющее большинство их идентичны. Отказ от
    ретенции этой записи цену и поднял: удалять хаб больше не умеет, значит
    дедупликация — единственный оставшийся рычаг на объём, кроме рук.

    **Git для этого не подходит, хотя идея контент-адресуемого хранилища
    верна.** Чтобы дедуплицировать им артефакты, артефакты надо положить В git,
    а они раздаются напрямую с диска по неизменяемым URL с годовым кэшем.
    Значит поверх появится слой извлечения на каждый запрос: «отдать файл»
    превратится в «достать блоб из пакфайла и отдать». Это размен раздачи на
    место, и не в нашу пользу.

    **Дешевле и без зависимостей — жёсткие ссылки.** Файлы с одинаковым
    содержимым в разных каталогах сборок связываются, и тогда: раздача не
    меняется вообще (это по-прежнему обычный файл), ручное удаление проекта или
    сборки не ломается (`unlink` уменьшает счётчик ссылок, место освобождает
    последний удалённый — а удаляет здесь человек, §7.3),
    том один — а жёсткие ссылки и работают в пределах файловой системы.

    **Цена, которую надо назвать заранее.** Связывание безопасно ровно потому,
    что каталог сборки объявлен НЕИЗМЕНЯЕМЫМ. Оно перестаёт быть безопасным в
    ту секунду, когда что-нибудь начнёт писать в существующий файл сборки на
    месте: правка прилетит во все связанные копии сразу. Сегодня такого пути
    нет — публикация делает `rename` целого каталога, — но это инвариант,
    который придётся защитить проверкой, а не памятью о том, что так задумано.

    Выигрыш числами оценивается только на реальных данных: он целиком зависит
    от доли деталей, меняющихся между ревизиями. Механизм от этого не зависит,
    а «стоит ли оно того» — зависит полностью, поэтому мерить до того, как
    делать.

20. **Локальной сборки не остаётся, и любая успешная сборка двигает `dev`.**
    Решено 2026-08-26.

    **Как сегодня.** «Проверить» и «опубликовать» — два разных действия, и
    первое происходит на ноутбуке: `make build LOCAL=1 NOPUBLISH=1` в клиенте
    `cad_publish` (`init_project.py`, `project.py`) собирает модель локально и
    ничего никуда не отправляет. То есть геометрия считается в двух разных
    местах — на машине автора и в образе, — и совпадение результата ничем не
    обеспечено.

    **Как должно стать.** Локального пути сборки нет вовсе. Единственный способ
    собрать модель — отправить её; сервер собирает, и если сборка УСПЕШНА, она
    обновляет `dev`. Проверка перестаёт быть отдельным режимом: проверить —
    значит отправить. `NOPUBLISH` исчезает вместе с `LOCAL`.

    **Ради чего.** Одно место, где считается геометрия. Пока их два, посылка
    «тот же исходник — та же геометрия» не проверяема даже в принципе: у
    ноутбука своя версия ядра, свои плавающие зависимости и своя ОС. Это та же
    линия, по которой принято решение 8A (хаб становится билдером) — здесь она
    просто доводится до конца, потому что оставленный локальный путь и есть
    второе место.

    **Цена, которую надо принять явно.** Автор теряет быстрый цикл: сегодня
    итерация — это запуск на своей машине, завтра — сетевой круг через сервер.
    Раздел 8A уже называет «нет быстрого локального цикла» среди последствий
    переезда; эта запись делает его не последствием, а решением. Смягчает её
    ровно то, что `dev` — слот с перезаписью (7.6): каждая следующая отправка
    затирает предыдущую, истории не копится, `latest` не двигается.

    **Что для этого уже готово.** Механика `dev` есть (`publish_dev`,
    `_swap_dev_slot`), приём асинхронный (шаг 5), а провалившаяся сборка
    гарантированно не двигает ни `latest`, ни `dev` — это доказано тестом
    `test_a_failed_build_moves_neither_latest_nor_the_slot`. То есть требование
    «двигает ТОЛЬКО успешная» выполнено заранее.

    **Что придётся сделать.** Убрать из клиента ветки `LOCAL` и `NOPUBLISH`
    вместе с их сообщениями и подсказками (это часть шага 7), и решить, чем
    заменяется сегодняшняя подсказка «прогнать сборку и гейт локально» в
    `init_project.py` — она предлагает пользователю ровно тот путь, который
    отсюда исчезает.

    Вторая половина того довода — «настройка читателя теряется на следующей

    Цена самой смены темы неизвестна и должна быть замерена глазами, а не

26. **Клиент — один системный инструмент вместо Makefile в каждом проекте.**
    Решено 2026-08-26. Имя команды — `hammerola`, как и всё остальное.

    **Как сегодня.** Работа с моделью ведётся через Makefile, лежащий В КАЖДОМ
    репозитории модели, плюс пин `cad_publish` тегом там же. Этот пин уже
    разъехался — одна модель на `v1.0.0`, шаблон на `v1.1.0` (см. шаг 7 в
    8A.2), — и это не случайность, а свойство схемы: копия инструмента в
    каждом проекте расходится ровно настолько, насколько давно её не трогали.

    **Как должно стать.** Один инструмент на всю систему, по образцу `gh` или
    `tea`, обновляющий себя сам. Сценарий:

    Makefile из репозиториев моделей исчезает вместе с пином.

    **Набор команд, обсуждён 2026-08-27. СДЕЛАН ВЕСЬ, кроме самообновления** —
    `src/client/`, тесты в `tests/client/`. Что именно вышло и какие решения при
    этом приняты — в конце записи, «Как это легло».

        hammerola create              завести проект
        hammerola build               исходники → слот dev, напечатать лог
        hammerola commit -m "…"       исходники → неизменяемая ревизия
        hammerola source <ревизия>    забрать КОД ревизии
        hammerola artifacts <ревизия> забрать STL/STEP/3MF
        hammerola diff <рев> <рев>    что изменилось между ревизиями
        hammerola comments            прочитать очередь проекта
        hammerola comments resolve …  закрыть комментарий, с заметкой
        hammerola status              latest, dev, сборки, последняя задача
        hammerola log [dev|<ревизия>] перечитать лог сборки
        hammerola rename              сменить ЗАГОЛОВОК проекта
        hammerola rm                  удалить проект целиком
        hammerola login               адрес хаба и токен

    Пояснения там, где имя обманывает:

    *`rename` — только заголовок.* У проекта есть `id` и `title`, и разведены
    они намеренно (3.1): id нельзя вычислять из имени, иначе он меняется ровно
    тогда, когда должен был спасти ссылку. Переименование id ломает КАЖДЫЙ
    вечный URL проекта, а сборки розданы с годовым `immutable` и не отзываются.
    Такой команды не должно быть.

    *`rm` — только проект целиком.* Удаление отдельной сборки ломает вечные URL,
    а ретенции нет (§5.3) — то есть руки стали ЕДИНСТВЕННЫМ способом что-либо
    убрать с тома. Тем более этот способ должен быть крупным и редким: `rm` для
    случая «завёл тестовый, надоел», а не инструмент уборки по мелочи.

    *`source` и `artifacts` — разные права.* Код не публичен и идёт под токеном
    (запись 17), артефакты раздаются публично уже сейчас. Поэтому два глагола, а
    не один флаг.

    *`diff` почти написан.* `metrics_diff` уже выдаёт готовый текст — новая
    деталь, исчезнувшая деталь, что сдвинулось в измерениях, как изменились
    пересечения. CLI-глагол над ним тонкий. Текстовый дифф самого кода
    добавится вместе с хранилищем, через `difflib`.

    *`log` адресуется тремя способами*, потому что у сборки в `dev` ревизии нет
    вовсе: без аргумента — последняя из этого каталога, `dev` — что в слоте,
    `<ревизия>` — конкретная. Идентификатор задачи остаётся аварийным входом для
    сборки В ПОЛЁТЕ, когда ревизии ещё не существует.

    *Комментарии — ДА, в CLI, хотя MCP для них уже спроектирован (7A.5).*
    Возражение «два интерфейса к одним данным» здесь не работает: это два
    ТРАНСПОРТА над одним HTTP API, а вредно, когда расходятся две реализации.
    MCP работает только там, где есть MCP-клиент; из шелла, из скрипта, из
    чужого агента — нет.

    **Почему это ложится на уже сделанное.** `hammerola build` НЕ собирает
    локально (запись 20) — он отправляет дерево, получает 202 с идентификатором
    задачи, опрашивает статус и печатает лог сборки. Ровно это шаг 5 и построил:
    `GET /api/v1/jobs/<id>` и `/log`. То есть серверная половина готова, и
    инструмент — тонкий клиент над ней, а не второе место, где что-то считается.

    **Три решения, которые придётся принять явно.**

    *Первое — ОДИН ПАРОЛЬ РЕДАКТИРОВАНИЯ на систему, решено 2026-08-27.*
    Никаких токенов во множественном числе: `PUBLISH_TOKEN` и
    `COMMENT_READ_TOKEN` исчезают, остаётся один секрет в ENV — «можно делать
    что угодно». На систему, а не на проект.

    Им же входят в ВЕБ и получают права редактора, им же `hammerola login` в
    CLI. Форму входа заводить не надо, она уже есть: окно ввода живёт в
    `ui/src/HammerolaViewer.jsx`, значение кладётся в хранилище браузера
    (`readToken`/`writeToken`/`clearToken`) и уходит заголовком `Authorization:
    Bearer`. Серверная сессия для этого не нужна, и разделение уже написано —
    `viewer() { return !this.state.token; }`, то есть нет пароля значит только
    смотреть; кнопка так и подписана, `View only` против `Editing on`. Меняется
    не механика, а то, какой секрет туда вводят: сегодня интерфейс жёстко знает
    про `COMMENT_READ_TOKEN`, общий на очереди ВСЕХ проектов.

    Что остаётся открытым: сегодня секрет сравнивается на равенство и не
    различает, кто его предъявил. Логин на машину подразумевает ключ на
    человека — выдача, отзыв, срок жизни, — и этого нет. Пока нет,
    `hammerola login` означает «сохрани общий секрет в конфиг», и это стоит
    говорить вслух, чтобы не приняли за реализованную аутентификацию.

    *Второе — откуда он обновляется. Ответ: с хаба, после логина.* Записано,
    потому что вопрос «а как же подпись и доверенный источник» напрашивается и
    является ложным. Новой границы доверия здесь не возникает: инструмент УЖЕ
    доверяет хабу полностью — отправляет ему исходники, получает от него
    собранную геометрию, которую потом печатают, и держит его токен. Хаб,
    способный подсунуть подменённый бинарник, ровно так же способен подсунуть
    подменённую геометрию, так что отдельная подпись поверх этого канала не
    добавляет ничего.

    Требование отсюда ровно одно, и оно про то, чего делать НЕЛЬЗЯ: обновляться
    только с хаба и по тому же аутентифицированному каналу. Любой второй
    источник — зеркало, релизы форжа, сторонний индекс пакетов — добавляет
    границу доверия, которой сейчас нет, и вот тогда подпись действительно
    понадобится.

    *Третье — откуда берётся идентификатор версии.* `commit` здесь НЕ операция
    git: он означает «создай версию», и всё. Обе команды ложатся ровно на два
    пути публикации, которые в хабе уже есть: `build` — это `dev`, слот с
    перезаписью без истории (7.6), а `commit` — неизменяемая ревизия
    `<pid>/<commit>`, которая раздаётся годовым `immutable` и не переписывается
    никогда. То есть новой машинерии инструмент не требует, он даёт двум
    существующим путям по имени.

    Отсюда и вопрос. Сегодня `<commit>` — это идентификатор коммита ИЗ ФОРЖА:
    пуш приходит по адресу, который вычислил CI. Если версию создаёт сам хаб по
    команде человека, идентификатор надо чем-то заполнить, и вариантов
    немного — выдавать его хабу самому, брать из git, если он рядом есть, или
    просить у пользователя. Решать это надо вместе с записью 17 (хранение
    исходников): там же выяснится, что вообще связывает версию с породившим её
    кодом. Плюс `-m "…"` добавляет ревизии СООБЩЕНИЕ, которого у неё сейчас
    нет вовсе — сегодня она несёт только метаданные сборки.

    **Как это легло, 2026-08-27.** Шесть оставшихся команд написаны; ниже —
    только то, что было решено ПО ХОДУ и не выводится из текста выше.

    *`metrics_diff` вынесен, а не скопирован.* Чистая половина
    `src/cadbuild/metrics.py` переехала в `src/metricsdiff.py`, и обе стороны
    импортируют её оттуда: сборка печатает диффом что сдвинулось против `dev`,
    `hammerola diff` — что сдвинулось между двумя ревизиями. Копия была бы ровно
    той конструкцией, которая уже стоила публикации (`cad_publish/hubspec.py`),
    поэтому проверять соответствие нечего — реализация одна.
    `tests/test_metricsdiff.py` держит это: сравнивает объекты через `is` и
    проверяет, что модуль тянет только стандартную библиотеку. Наверх, а не в
    `src/cadbuild/`: импорт подпакета сборки повесил бы клиента на обещание
    «этот `__init__` остаётся лёгким».

    *Переименование — файл `title.json` рядом с `builds.json`, а не правка
    сборок.* Заголовок — свойство ПРОЕКТА, а сборка неизменяема и роздана с
    годовым `immutable`: перезапись `meta.json` опубликованной сборки не дошла
    бы до розданных копий и рассинхронизировала бы диск с ними. Файл
    перекрывает заголовок ровно на двух проектных поверхностях — шапке
    `builds.json` и карточке индекса — и СНИМАЕТСЯ следующей публикацией:
    сборка несёт заголовок из `project.json`, то есть пуш является более
    поздним утверждением имени. Поэтому клиентский `rename` пишет в два места
    сразу — в `project.json` (что понесёт следующий пуш) и на хаб (что видно
    сейчас); иначе одно переименование навсегда перебивало бы все будущие пуши.

    *`rm` и `data/sources/`.* Архивы адресуются дайджестом дерева, а не
    проектом, поэтому один каталог может обслуживать две публикации. Удаляются
    только те дайджесты проекта, на которые не ссылается НИ ОДНА сборка
    оставшихся проектов; порядок — сначала снести дерево проекта, потом собрать
    ссылки, потом удалять, и он же закрывает гонку с параллельной публикацией
    (`jobs._keep_the_code` кладёт архив ПОСЛЕ переименования каталога сборки,
    так что либо мы видим сборку и оставляем архив, либо архива ещё нет и его
    положат после нас). Если обход ссылок не удался, не удаляется ничего:
    неполный ответ на «кто ещё на это ссылается» неотличим от «никто».
    Инвариант §7.8 держится в обе стороны — архив есть тогда и только тогда,
    когда есть опубликованная ревизия.

    *`log dev` ответить нечем, и команда говорит это вслух.* Лог сборки в слоте
    существует только у ЗАДАЧИ: в `sources/` хаб для `dev` не кладёт ничего
    (§7.8), а адресация там по ревизии, которой у слота нет. Отвечать вместо
    этого логом `latest` нельзя — это другая сборка. Команда печатает, где лог
    всё-таки читается (`hammerola build` печатает его по ходу, и
    `/api/v1/jobs/<id>/log` продолжает его отдавать), и выходит ненулевым кодом.
    Закрыть это можно только новым маршрутом на хабе — не сделано намеренно.

    *Всё, что команды притаскивают с хаба, ложится в `.hammerola/` в проекте.*
    Скрытый каталог: `pack` выбрасывает скрытые имена, поэтому распакованная
    ревизия рядом с `model.py` не уедет в следующий пуш копией более старого
    дерева. Внутрь пишется `.gitignore` с `*` — иначе `git add -A` из
    предлагаемого коммита сложил бы туда же и её.

    **Про имя — исключения НЕ делаем.** Короткая форма (`hola`) рассматривалась
    и отвергнута: правило «одно имя везде» в `AGENTS.md` остаётся без дыр.
    Довод, которым обычно оправдывают короткую команду, — «её набирают руками
    десятки раз в день» — здесь не работает: команды набирает агент, а не
    человек, и стоимость лишних пяти символов равна нулю. Так что репозиторий,
    каталог, сервис, контейнер, образ и команда называются одинаково.

    и два в `tests/buildproc/test_build_child.py` — сборка настоящей модели
    (`@needs_cadquery`) и потолок тредпула OCCT (`@needs_occt`). Настоящую
    геометрию из них считают два.

    **Чем это оплачено.** Последний — единственная проверка того, что
    закоммиченная фикстура `ui/tests/fixtures/assembled.json` всё ещё совпадает
    по структуре с тем, что производит настоящий экспортёр. Пока он скипается,
    дрейф формата ловится только на машине разработчика, где ядро стоит: правка
    в `src/cadbuild/views.py`, сдвинувшая форму payload, проходит зелёный CI, а
    vitest продолжает проверять браузерную половину против документа, который
    ни одна сборка больше не отдаёт. Ровно эта тихая рассинхронизация и была
    причиной завести тот тест.

    **Почему гард поставили, а библиотеку — нет.** Гард ставился правкой,
    чинившей красный CI, и `apt-get install libgl1` в тестовый контейнер там
    технически сработал бы. Но он ЗАОДНО включил бы в CI тесты, которых в нём
    никогда не было и которые стоят процессорного времени — ровно того
    ресурса, исчерпание которого в тот момент и чинилось (`RLIMIT_CPU`,
    утёкший из `tests/buildproc/test_ceilings.py` во весь остальной набор).
    Смешивать «починить CI» и «включить новые тесты» в одну правку нельзя:
    если после этого что-то поедет, будет непонятно, что именно. Этот довод
    остаётся в силе — он про то, что правка отдельная, а не про то, что её не
    надо делать.

    **Цена оказалась другой, и решение отложить — переоткрыто.** Прежняя
    редакция записи говорила, что `libgl1` заодно включит 169 тестов,
    считающих настоящую геометрию, и именно этот довод отправил библиотеку в
    беклог. Довод неверен. `tests/cadbuild/` намеренно НЕ зависит от ядра —
    так прямо написано в его `conftest.py`, — и это измерено: с заглушками
    вместо `cadquery`, `OCP`, `ocp_tessellate` и `trimesh`, каждая из которых
    бросает `ImportError("libGL.so.1")`, каталог даёт 174 теста, из них
    173 passed и 1 skipped; с настоящим ядром — 174 passed. То есть ядро
    нужно ОДНОМУ тесту из 174, а не 169, и по всему набору таких тестов
    четыре (перечислены выше). Цена примерно в сорок раз меньше той, из-за
    которой откладывали, — значит выбор надо делать заново, а не наследовать
    вместе с числом, которого не было.

    **Что надо решить.** Ставить `libgl1` (и ровно то из списка Dockerfile,
    что реально нужно на импорт) в `apt-get` шага тестов ОБОИХ workflow — или
    оставить как есть, сознательно приняв, что дрейф формата фикстуры ловится
    только на машине разработчика. Данные, которые для этого есть: включаются
    четыре теста, а не 169, и настоящую геометрию считают два из них;
    `import cadquery` один только мапит ~222 МБ OCCT (та же цифра уже
    аукнулась в обосновании `timeout-minutes: 14` у гейта); apt-время
    установки самих библиотек ложится на шаг, у которого сегодня
    `timeout-minutes: 20`; действующий потолок `--memory=2g` выведен на
    наборе, в котором ничего не импортирует OCP.

    **Как мерить, если делать.** Тела шага тестов побайтово одинаковы в обоих
    workflow, правятся вместе и проверяются `tests/test_workflow_steps.py`.
    Потолок памяти мерить ТОЛЬКО парой «проходит / убит» при конкретном
    лимите. `memory.peak` контейнера для этого непригоден, и прежняя редакция
    записи ошибочно предлагала именно его: он считает вытесняемый страничный
    кэш, который этот прогон производит в количествах (apt, pip, распаковка
    дерева), растёт вместе с выданным лимитом и насыщается ниже него — 2.86 ГБ
    под 4g, 2.00 ГБ под 2g, 769 МБ под 768m на `cirunner-docker`. То есть он
    сообщает, сколько прогону РАЗРЕШИЛИ закэшировать, а не сколько ему нужно.
    Числа «пик 403 МБ, пол между 320 и 384 МБ», стоявшие здесь раньше, сняты с
    оборванного прогона (`RLIMIT_CPU` убивал набор на середине) и неверны.
    Настоящий пол набора без ядра — ВЫШЕ 512 МБ и не выше 768 МБ: при 512m
    ядро убивает контейнер (exit 137, `OOMKilled=true`), при 768m и при 2g
    набор проходит с rc 0. После установки библиотек снять ту же пару заново и,
    если пол сдвинулся, пересчитать `--memory` и оба `timeout-minutes`.

28. **Потолки памяти остальным контейнерам CI.** Записано 2026-08-26, рядом с
    записью 27 и по тому же поводу. `--memory` / `--memory-swap` сегодня стоят
    РОВНО ОДНОМУ контейнеру из нескольких — питоновскому шагу тестов, — и
    только потому, что замерен только он. Довод, которым потолок обоснован, —
    свойство раннера, а не этого шага: 19 ГБ делятся со всеми остальными
    репозиториями, и разогнавшаяся аллокация перестаёт быть провалом одной
    задачи и становится общим. Значит довод применим к остальным ровно так же,
    а молчание рядом с ними читается как «забыли», хотя это не решение о том,
    что им потолок не нужен.

    Без потолка сейчас:
    - шаг `Run the JS test suite in a container` обоих workflow —
      `node:22-bookworm-slim`, `npm ci` плюс vitest;
    - шаг `Build the Docker image` обоих workflow — сам `docker build`, чей
      аппетит задаёт Dockerfile: apt, pip с колёсами OCCT и сборка бандла в
      стадии `ui`;
    - три контейнера, которые поднимает `ci/smoke.py` (долгоживущий, `-guard`
      и `-cmd`) — там же, где `remove_container()`.

    **Что сделать.** Каждому — та же методика, что в записи 27: пара
    «проходит / убит» при конкретном лимите, `memory.peak` не использовать.
    Наугад числа не ставить: это прямо против принципа «лимиты по замерам»
    (по той же причине их до сих пор нет у сервисного контейнера — шаг 0
    чеклиста в `AGENTS.md`). Отдельно проверить замером сборку: у `docker
    build` флаг `--memory` есть, но классический builder и BuildKit относятся
    к нему по-разному, так что сначала выясняется, принимает ли его docker на
    раннере вообще, и только потом подбирается число.

## 8A. Хаб становится билдером — принятое решение

Решено 2026-08-24. Делает неверными: шапку документа, §1 (сценарий A, шаг 3),
строку «Доставка» в таблице §4 и §7 в части того, ЧТО приезжает в хаб. Переводит
запись беклога «Один образ: вьювер и билдер вместе» из «хотелось бы» в «делаем».
Делает неверным и довод из записи «Сравнение двух ревизий» — «почти в восемь раз
дешевле»: он посчитан для узкого пути сравнения, где нужны только `OCP`, `numpy` и
`ocp-tessellate`, а сам `cadquery` не импортируется. Восьмикратной экономии не будет
по двум причинам сразу: хаб, который СОБИРАЕТ модели, требует полного `cadquery`, и
шаг 1 отказывается от пина `cadquery-ocp-novtk`, на котором держались те 250 МБ.

**Что решено.** Хаб принимает ИСХОДНИК модели и сам считает геометрию. Отдельного
образа `cad_builder` и workflow публикации моделей больше нет. Форж остаётся сбоку
как хранилище истории и в цепочке публикации не участвует: ни вебхуков, ни pull, ни
раннеров. Всё только пушем от разработчика, два адресата — `dev` (проверить сборку
на ходу) и ревизия по коммиту. Коммит-sha приезжает вместе с пушем и НЕ проверяется:
хаб не может убедиться, что такой коммит существует и что исходник соответствует
именно ему. Это тот же уровень доверия, что и токен публикации, но идентификатор
ревизии перестаёт быть верифицируемым, и на нём нельзя строить ничего, что требует
подлинности.

**Зачем.** Один артефакт вместо трёх репозиториев, одна версия ядра геометрии, один
деплой. И ядро рядом с хабом — без него не сделать сравнение ревизий с разностной
геометрией.

**Что доводом НЕ является — проверено, чтобы не выдвигали снова:**

- «CI медленный». Реальные прогоны публикации модели — 10–45 с на весь job.
  Оговорка: «десятки минут» из комментария в workflow относятся к сборке образа
  С CAD-СТЕКОМ, то есть ровно к тому, во что этот план превращает образ хаба;
  единственный замер такого образа — два прогона `cad_builder`, 37 с и 207 с;
- «нет быстрого локального цикла». Сегодня он есть — `make build` собирает на
  build-node через docker context и публикует в `dev` с ноутбука. Но живёт он на
  `remote.py` и образе билдера, которые этот же план удаляет. После переезда
  локальный цикл — это пуш исходника и ожидание асинхронной задачи с логом, то есть
  его придётся построить заново (шаг 5);
- «нет гейта на геометрию». Он написан и работает в пакете `cad_publish`:
  `isValid()`, ненулевой объём, водонепроницаемость меша, непересечение деталей на
  плите, наличие всех printables в сборке, собственные `checks()` модели, у которых
  число проверок считается по AST и ноль отвергается. Запись беклога, называющая
  этот гейт несделанным, устарела.

### 8A.1 Модель угроз после решения

Хаб перестаёт только РАЗБИРАТЬ недоверенные данные и начинает ИСПОЛНЯТЬ присланный
код. Разница не в степени: чтобы получить питон-процесс через разбор архива, нужно
найти баг в коде, написанном против ровно этого класса атак; чтобы получить его через
исполнение — не нужно ничего, это штатное поведение.

**Довод «поверхность атаки не расширяется» из записи «Один образ» признан неверным.**
Его первый аргумент — «исполнение закрывается токеном и попадает в тот же уровень
доверия, что публикация» — не держится: сегодня токен даёт право записать
ПРОВЕРЕННЫЕ ХАБОМ байты в каталог, который выбирает ХАБ. Дать тому же токену shell —
это повышение привилегий существующего креденшла. Второй аргумент — «хаб и так
разбирает недоверенный ввод» — приравнивает путь ценой эксплойта к пути по протоколу.

Для калибровки — соседний верстак для LLM-агентов: наружу его выставить нельзя в
принципе, потому что он исполняет сгенерированный python, не имеет аутентификации и
работает от root внутри контейнера. Три свойства. Двумя хаб отличается — исполнение
под токеном и non-root процесс. Третьим, главным, совпадает: он тоже будет исполнять
недоверенный python. А по доступности отличается в ХУДШУЮ
сторону — тот верстак наружу не смотрит вовсе, а хаб публичен по построению.

**Анонимный вход закрыт — шаг 0 плана, сделано.** Без этого после переезда
возникала полная дорожка от анонимного ввода до выполнения кода, не требующая ни
одной уязвимости: комментарий пишется публично, без токена → попадает в очередь →
агент читает его через MCP как задачу → агент правит `model.py` → хаб исполняет
`model.py`. **Публичная запись комментариев отменена: запись под токеном.** Это
поменяло посылку §7A («зритель тыкает в деталь и пишет „поправь вот тут“» — теперь
это держатель токена), маршрут записи и обоснование публичности в 7A.2, требования
7A.4 и маршрут комментария к `dev` в §7.6. Заодно отпал один из двух доводов против
issue в Gitea — тот, что анонимная запись это спам-дверь; второй, «трекер под это
избыточен», остаётся, да и issue требуют аккаунта в форже, так что схемы всё равно не
эквивалентны. Право писать выдано тому же, кто публикует: секрет один на систему
(§8, запись 26), и фича честно называется заметкой агенту, а не публичным каналом.

**Кто остаётся в модели угроз:** владелец токена (он же владелец репозиториев) и
кража токена. Разделять право «прислать код» и право «опубликовать» при этом
бессмысленно: в новой схеме это один и тот же POST — прислать исходник и есть
запустить сборку, а её успех и есть публикация. А то, что `PUBLISH_TOKEN` был
секретом уровня организации, видимым всем 14 репозиториям, лечится само: он
перестаёт быть org-секретом вместе с workflow'ами. Шаг 0 добавил к этому имя:
переменная хаба называется `EDIT_TOKEN` (§7.5) — не потому, что имя что-то
защищает, а потому что `PUBLISH_TOKEN` читался как «креденшл CI на пуш» и тем
приглашал сделать ровно то повышение привилегий, о котором этот раздел.

**Радиус поражения измерен, а не предположен.** Хаб стоит не в вакууме, а в общей
docker-сети: из неё без единого опубликованного порта достижимы соседние сервисы и их
базы — включая сам форж с исходниками всех проектов и его базу. Это доступ, которого у
сегодняшнего исполнителя на CI-раннере нет. У контейнера хаба при этом НЕ ЗАДАНЫ ни
потолок памяти, ни CPU, ни `pids`, ни `cap_drop` — один бесконечный цикл в модели
забирает всё, до чего дотягивается.

### 8A.2 План по шагам

Сначала переезд целиком, сравнение ревизий — последним шагом. Причина не в
приоритетах: если делать сравнение раньше, его придётся строить дважды, а так из
него выпадает целый кусок — расширение протокола под B-Rep по деталям вместе со
схемой санитайза имён в имена файлов. Когда хаб держит исходники и ядро, тела он
получает сам.

**Шаг 0. То, что верно и без этого плана.** Лимиты контейнеру хаба: память, CPU,
`pids`, `cap_drop` — НЕ СДЕЛАНО и намеренно отложено: числа берутся с замеров, а
сервис ни разу не выкатывался. **Комментарии под токен — СДЕЛАНО.** Мера была
упреждающей, а не аварийной: очередь по построению рассчитана на
потребителя-агента (7A.5), самого MCP-сервера ещё нет, так что цепочка обрывалась
на очереди — но замкнулась бы на исполнение в тот же день, когда он появится.

Вместе с этим схлопнулись два секрета в один (§8, запись 26, решение 2026-08-27):
`PUBLISH_TOKEN` и `COMMENT_READ_TOKEN` исчезли, в ENV остался `EDIT_TOKEN` —
«можно делать что угодно», на систему. Почему имя новое, а не `PUBLISH_TOKEN`, и
почему «токен», а не «пароль» — §7.5. Что стало с эндпоинтом записи — §7A.2 (токен
проверяется ПЕРВЫМ, до маршрута и до `Content-Length`) и §7A.4 (какие требования
пережили смену посылки, а какое отменилось).

Одну вещь этот шаг у проекта ЗАБРАЛ, и она записана, чтобы не считалась
покрытой: гейт `ci/smoke.py`, проверка (b), доказывал, что сторож на старте
называет КАЖДУЮ недостающую переменную, а не только первую, — и доказывал он это
тем, что переменных было две. С одной второй строки не существует. Свойство
переехало в `tests/test_config_errors.py`, где сторожу можно подсунуть класс
настроек с двумя обязательными полями; гейт, который работает против собранного
образа с настоящим `Settings`, так не умеет. Форма списка в
`REQUIRED_VARIABLES` при этом сохранена: вторая переменная, если когда-нибудь
появится, возвращает свойство одной строкой, а объявленное число проверок
считается выражением от этого списка и едет следом само.

**Шаг 1. Ядро в образ хаба.** Пины `cadquery`, `cadquery-ocp`, `ocp-tessellate`,
`trimesh`. Системные библиотеки в Dockerfile: `libgl1`, `libx11-6`, `libexpat1`,
`libxext6`, `libxrender1`, `libsm6`, `libice6` — и намеренно НЕ `libglu1-mesa`.
(`libexpat1` добавлен по факту разбора колеса: вендоренный в `cadquery-ocp`
fontconfig несёт незапатченный `DT_NEEDED libexpat.so.1`, а в `python:3.11-slim`
libexpat нет вовсе; сегодня он приезжает только транзитивно через `libgl1`.
Обоснование списка целиком — в комментарии Dockerfile.) В smoke добавить
`import cadquery` внутри собранного образа, иначе класс ошибок с `libGL` вылезет уже
в проде. VTK принимается как есть: его жёстко требует сам `cadquery-ocp`
(`vtk==9.6.2`), а не trame, и единственный способ избавиться — подменить дистрибутив
на `cadquery-ocp-novtk` в обход объявленной зависимости. Не делаем: экономия порядка
0.6 ГБ образа не стоит постоянной хрупкости, а довод про медленный откат при
ближайшем рассмотрении почти ничего не весит (откатов не было ни разу).

**Шаг 2. Приём дерева вместо плоского архива.** Сегодняшний приём принимает плоский
архив: в разрешённых именах членов нет даже символа `/`. Исходник модели — дерево.
Переписывается распаковка вместе со второй линией обороны от обхода путей: правила
имён с `/`, запрет `..`, абсолютных путей и симлинков, потолки на глубину, число
файлов и распакованный размер.

**Шаг 3. Перенос `cad_publish` внутрь.** СДЕЛАНО. Сборочная половина живёт в
`src/cadbuild/` — 19 модулей: `artifacts`, `assembly`, `build`, `checklib`, `errors`,
`gate`, `geometry`, `hubspec`, `legacy`, `matching`, `metrics`, `modelchecks`,
`palette`, `paths`, `preview_png`, `printables`, `project`, `project_title`, `views`.
Тесты — `tests/cadbuild/`, 9 файлов и свой `conftest.py`, 174 теста.

Клиентская половина ОСТАЛАСЬ в `cad_publish` и переезжать ей незачем: `cli`,
`__main__`, `settings`, `hub` (HTTP-пуш), `remote` (машинерия build-node), `gitinfo`,
`init_project`, `preview` (локальный HTTP-сервер предпросмотра — у хаба свой сервер и
свой вьювер) и `archive` (клиент пакует tar.gz, хаб его распаковывает своим кодом).
Из `metrics.py` не поехали ровно две функции — `fetch_baseline` (GET предыдущего

**Шаг 4. Исполнение.** СДЕЛАНО. Живёт в `src/buildproc/` — пять модулей:
`limits` (потолки и код, который их ставит), `wrapper` (внешняя обёртка: ставит
rlimit'ы на себя и делает `execv`), `child` (входная точка сборки: `faulthandler`,
тредпул OCCT, `chdir`, `build()`), `runner` (родитель: запуск, дедлайн, убийство,
захват лога, ПРОВЕРКА результата), `hardening` (единственное, что исполняется в
самом хабе: `prctl(PR_SET_DUMPABLE, 0)` на старте, вызывается из `main.py`).
Тесты — `tests/buildproc/`, 68 тестов (`test_isolation`, `test_ceilings`,
`test_build_child`, `test_result_forgery`, `test_hub_environ` плюс
`conftest`/`probes`); два требуют CAD-ядра, два — Linux, остальные гоняют
маленькие программы «по одному свойству каждая». Цепочка запуска:
`run_build(project, out, pid=…)` → `python -m src.buildproc.wrapper
'<rlimit-spec>' -- python -m src.buildproc.child --project … --out … --result …`.
К HTTP не подключено (шаг 5), гейт не переехал (шаг 6).

Что выяснилось по ходу и стоит знать, прежде чем что-то тут менять:

- **Файл результата подделывается моделью, и это воспроизведено.** Модель живёт в
  том же интерпретаторе, что и код, который пишет результат: читает `--result` из
  `sys.argv`, пишет свой JSON, делает `os._exit(0)` — и родитель, который файлу
  ВЕРИЛ, рапортовал `ok` с чужим `pid` и списком файлов, которых нет. Секрет внутри
  процесса не спасает: модель читает ту же память. Закрыто на стороне РОДИТЕЛЯ:
  `pid` берётся из принятого пуша (параметр `run_build`), `meta` не ездит вовсе
  (это `out/meta.json`), а каждое имя файла проверяется — существует, обычный файл,
  ни одна компонента пути не симлинк, нормальная форма, строго внутри `out_dir`.
  Статус `bad_result` — это «сборка заявила то, что хаб не может подтвердить».
- **Токены читались через `/proc/<pid хаба>/environ`.** Аллоулист окружения
  (`child_environment`) верен и его НЕ ХВАТАЕТ: сборка идёт под тем же uid и в том
  же PID-namespace, а `/proc/<pid>/environ` требует `PTRACE_MODE_READ_FSCREDS`, а
  не ATTACH, — то есть свой uid читает. Лечится `prctl(PR_SET_DUMPABLE, 0)` в
  процессе хаба: после него `/proc/<pid>/` принадлежит root. Флаг сбрасывается
  `execve`, поэтому ставить его в entrypoint бесполезно — только в питоне, из
  `main.py`, через `ctypes` (в stdlib prctl нет). Не удалось на Linux — хаб не
  стартует.
- **Том `/app/data` сборке полностью доступен на запись, и фенс это не закрывает.**
  Хаб и сборка — один `app`, один том: модель может писать и удалять в чужих
  сборках. Потолки `output_bytes`/`output_files` — это защита от исчерпания тома, а
  не граница. Настоящая граница требует своего uid или mount namespace на сборку,
  чего изнутри контейнера нет (8A.4).
- **`killpg` не накрывает потомка, сделавшего `setsid`.** Он в своей группе, номера
  её никто не перечислит, и он переживает убийство — держа унаследованную трубу, то
  есть поток и дескриптор хаба, пока не умрёт. Это не чинится здесь (это `pids`
  контейнера, шаг 0), поэтому факт вынесен в лог сборки и в
  `ProcessResult.stragglers`.
- **`killpg` нельзя слать по pgid, за который уже не ручаешься.** На ECHILD из
  `waitid` зомби нет, номер свободен и мог быть переиспользован: максимум
  `process.kill()`. Раньше ветка ECHILD возвращала «вышел», после чего безусловно
  летел `killpg` — ровно то, что докстринг объявлял недопустимым.
- **Спека потолков требует ровно известный набор ключей.** `spec.get(field) is None
  → continue` не отличает «выключено намеренно» от «потерялось», а незнакомый ключ
  глотался молча: `wrapper.py '{}' -- …` исполнял цель вообще без ограничений и
  печатал бодрое «ceilings in force:». Теперь отсутствующий или лишний ключ —
  отказ; `None` по-прежнему значит «выключено», но должен быть НАПИСАН.
- **`RLIMIT_FSIZE` — про ОДИН файл.** Ни суммы, ни числа файлов ядро не считает, а
  эффект переполнения тома переживает сборку (в отличие от CPU и памяти). Поэтому
  два потолка родителя: `output_bytes` и `output_files`, меряются на тех же
  опросах, что и wall-clock (раз в `OUTPUT_POLL_SECONDS`), с убийством при
  пересечении, и ещё раз после смерти процесса — второй замер решает, что вообще
  публикуется, первый спасает том. Симлинки при обходе не разыменовываются: иначе
  `ln -s /` заставил бы мерить всю ФС.
- **`except Exception` вокруг импорта `OCP.OSD` читал любую поломку как «OCP нет».**
  Отличать надо строго `ModuleNotFoundError` с `name == "OCP"`: всё остальное
  значит, что ядро в интерпретаторе ЕСТЬ и пул поднимется на все ядра против
  `RLIMIT_CPU`, посчитанного на два потока.

- **Успех — это ФАЙЛ результата, а не код возврата.** Модель может сделать
  `os._exit(0)` прямо из своего импорта, и процесс уходит с кодом «всё хорошо», не
  собрав ничего. Родитель считает чистый выход без читаемого результата крахом.
- **Убивать надо ДО reap'а.** `Popen.wait()` пожинает зомби, и в этот момент pid
  (а он же pgid, из-за `start_new_session`) становится свободен: `killpg` после
  этого целится в номер, который может уже не значить эту сборку. Поэтому
  `waitid(WNOWAIT)` → `killpg(SIGKILL)` → и только потом `wait()`.
- **`RLIMIT_AS` на Darwin не ставится ВООБЩЕ** — EINVAL при любом значении, от
  512 МиБ до 200 ГиБ, и для `RLIMIT_DATA`/`RLIMIT_RSS` тоже. Следствие: на macOS
  сборка под продовыми потолками не запускается — обёртка отказывается (fail
  closed), и это осознанно, потому что прод — линуксовый контейнер.
- **`soft == hard` держит только Linux.** Там при достижении hard ядро шлёт
  SIGKILL, и обработчик SIGXCPU не спасает (проверено). На Darwin тот же процесс с
  обработчиком живёт бесконечно — hard не enforced вовсе; на воркстейшене от
  враждебного кода спасает только wall-clock родителя.
- **`RLIMIT_NPROC` намеренно выключен.** Он считается ПО UID, а все сборки в
  контейнере идут от одного `app`: вторая параллельная сборка получала бы отказ
  из-за потоков первой. Это работа для `pids` контейнера (шаг 0).
- **Дедлайн `faulthandler` обязан быть строго меньше wall-clock**, иначе SIGKILL
  родителя приходит первым и стек — единственное, ради чего второй эшелон нужен, —
  теряется. Проверяется в `Limits.__post_init__`.
- **Приватный `MPLCONFIGDIR` на сборку стоит 6.5 с CPU** (замер: 0.24 с на
  прогретом). Лечится в образе — испечь кэш шрифтов при сборке образа и
  подсовывать его только на чтение; общий ЗАПИСЫВАЕМЫЙ каталог между сборками —
  плохой размен.
- **В smoke-гейт стоит добавить проверку (h)** — что потолки встают внутри образа
  под юзером `app` и `-m src.buildproc.*` резолвится от `/app`. Аргумент «пока
  хаб ничего не собирает, ломаться нечему» ИСТЁК на шаге 5: сборка теперь на пути
  запроса. Проверка всё ещё не добавлена, и это тоже намеренно — она переезжает
  вместе с гейтом на шаге 6, а писать в гейт код, который сегодня нечем проверить
  локально, хуже, чем записать долг. Долг записан отдельной записью беклога §8 —
  «Долг гейта: проверка (h) в `ci/smoke.py`».

Исходное обоснование, которое всё это и продиктовало:
Отдельный процесс, запуск через `spawn`/exec, НЕ через `fork`:
тредпул OCCT после форка виснет и падает. Окружение без токенов. Убивать зависшую
сборку придётся ИЗНУТРИ контейнера, и это сужает выбор: своего cgroup дочернему
процессу оттуда не создать (`/sys/fs/cgroup` смонтирован read-only), а `systemd-run`
нечем выполнить — в образе нет ни systemd, ни dbus. Рабочая схема: `rlimit` во
внешней обёртке плюс таймер в родителе и `SIGKILL`. Три механизма тут делают разное,
и путать их нельзя: cgroup-лимит CPU троттлит и не убивает вовсе; `RLIMIT_CPU`
убивает по ПОТРЕБЛЁННОМУ процессорному времени, то есть ловит цикл, который жжёт
ядро; а таймер wall-clock в родителе ловит зависание, которое процессорного времени
не потребляет — дедлок тредпула, например, — на нём `RLIMIT_CPU` не сработает вовсе.
Про булевы OCCT проверено другое и более узкое: их не снять ни таймаутом на треде, ни
`Ctrl+C`, потому что нативный код не возвращается в интерпретатор. Ориентир —
60–120 с вместо нынешних 45 минут.
`faulthandler.dump_traceback_later` вторым эшелоном: он единственный работает
изнутри, потому что реализован в C и не берёт GIL, и заодно даёт стек «где именно
застряло». Ограничить тредпул OCCT, иначе лимит по CPU сработает в двадцать раз
раньше ожидаемого: по умолчанию берутся все ядра, а `RLIMIT_CPU` суммарный по
потокам. Лимиты ставить внешней обёрткой, не через `preexec_fn` — хаб многопоточный,
и это прямо помечено в документации как небезопасное. Зависимости модели — по
решению 8A.3.

**Шаг 5. Асинхронный приём.** Публикация сейчас синхронна внутри HTTP-запроса: четыре
одновременно, ожидание 60 с, сокет-таймаут 30 с. Сборка туда не влезает. Нужен ответ
202, идентификатор задачи, эндпоинт статуса и ОТДАЧА ЛОГА СБОРКИ тому, кто пушил —
сегодня эту роль играет job log в Gitea, и сам собой он не заменится. Смена
фреймворка этой задачи не решает: и Flask, и асинхронные фреймворки дают
конкурентность по вводу-выводу, а сборка CPU-bound и всё равно уезжает в отдельный
процесс. Вместе с этим переписывается §7.5: параллелизм СБОРКИ — отдельное число от
параллелизма приёма, потому что нынешние четыре слота обоснованы телом на диске и
tar-ридером, а не потоками OCCT и `RLIMIT_CPU` (§7.5).

**СДЕЛАНО.** Живёт в `src/jobs.py`: `JobStore` — реестр (каталог на задачу под
`data/jobs/`, запись в `job.json`, лог рядом в `log.txt`), `BuildTask` — то, что
запрос передаёт воркеру, `BuildQueue` — ограниченная очередь и N потоков, которые
собирают и публикуют. Ответы и потолки — в §7 и §7.5, эндпоинты — в §3 и §7.4, тесты —
`tests/test_jobs.py`.

Что здесь решено и почему именно так:

- **Граница проходит по «нужна ли сборка».** Всё, что решается из самого пуша, на
  пуше и отвечается — иначе CI пришлось бы опрашивать задачу, чтобы узнать, что
  архив битый. Отдельный случай — 200 на идентичный повтор: он экономит не ответ, а
  МИНУТЫ CPU, потому что иначе хаб пересчитывал бы геометрию ради ответа, который уже
  лежит на диске.
- **Исходники и вывод — РАЗНЫЕ каталоги.** Дерево пуша распаковывается в
  `data/.src-<uuid>/`, сборка пишет в staging внутри каталога проекта, и публикуется
  именно staging. Поэтому то, что модель положила в дерево, которое ей ДАЛИ, не
  попадает наружу никак, кроме как через её собственный вывод.
- **Задача не остаётся без терминального состояния.** Это единственный отказ, который
  реестру запрещён: застрявшее `building` — это статус, который пушер опрашивает и
  который никогда не изменится, причём сборка при этом может быть опубликована. Из
  этого следуют три вещи: запись в памяти обновляется независимо от того, что скажет
  том; оба обращения к диску (лог и запись) — best effort с исключением в лог; и
  ошибка ПОСЛЕ `rename` не делает задачу провалившейся, потому что `rename` и есть
  публикация, а `latest`, пикер и индекс пересчитываются следующим пушем.
- **Порядка задач нет, и хранить его негде — в том числе не по записи.** Порядок
  создания был нужен ровно ретенции: он отвечал на вопрос «кого подрезать первым».
  Ретенции нет (§5.3), потребителя нет — `data/jobs/order.json` удалён вместе с
  механикой чтения и записи порядка, а задачи читаются по id (§7.4). Правило, которое
  эта история после себя оставила, шире файла и остаётся в силе: **то, что является
  свойством НАБОРА записей, нельзя хранить по записи.** Первая версия клала в каждую
  запись монотонный `seq`; проход, который пишет их по одному, останавливается там, где
  сборка ему велит (`chmod 0500` на одном каталоге, без единой уязвимости), и на томе
  остаются два пространства номеров разом — порядок, которого у живого хаба не было,
  плюс дубликаты. Понадобится когда-нибудь ещё одно свойство набора — оно поедет одной
  атомарной записью, а не по каталогам задач.
- **Задача не остаётся `queued` из-за того, что сломался сам приём.** Между
  `jobs.create` и `builds.submit` два оператора, и исключение между ними отвечало
  только ПУШЕРУ — 500, а при оборванном сокете вообще ничего. Задачу же не отвечал
  никто: статус рапортовал `queued` про сборку, которой нет, и так до перезапуска —
  ближайший старт переводит незакрытую задачу в `failed` (`_load`), но до него может
  пройти сколько угодно, а пушер опрашивает статус сейчас. Заваливается
  в обоих обработчиках `_queue_build` и только при `handed_over == False` — после
  `SUBMIT_ACCEPTED` задача принадлежит воркеру, и провалить её значило бы соврать про
  живую сборку.
- **Статус-полл не ждёт чужой `fsync`.** `_lock` в реестре один, и его берёт каждый
  `get`, то есть каждый опрос статуса каждым пушером. Поэтому лог сборки (до
  `MAX_LOG_BYTES`) пишется ДО взятия лока: порядок «лог на диске раньше, чем
  опрашивающий увидит терминальное состояние» держится записью В ПАМЯТИ, которая до
  возврата из записи лога не меняется, а не удержанием лока на время синка тома.
- **Остановка — это работа, а не её отсутствие.** SIGTERM (то есть `docker stop`, то
  есть каждый передеплой) обработчиком переводится в `server.shutdown()`, иначе
  штатная остановка не выполнялась в проде НИ РАЗУ — только Ctrl+C на ноутбуке.
  Обработчик при этом лишь БУДИТ поток, созданный заранее: `Thread.start()` берёт
  внутренний лок `threading`, который главный поток держит, запуская поток на
  очередное соединение, а обработчик сигнала выполняется на главном потоке между
  байткодами — то есть `start()` из обработчика может ждать лок, занятый им же.
  Очередь при остановке дренируется с удалением исходников каждой снятой задачи:
  `Store._sweep_leftovers` их не подметёт, он ходит только из `Store.__init__` и
  только по тому, что старше часа, а контейнер поднимается за секунды. Дренаж входит
  в бюджет остановки, а не идёт сверх него: часы стартуют ДО него, а join получает пол
  (§7.5). Слушающий сокет закрывается ДО дренажа — и польза тут не в том, что хаб
  «продолжал бы принимать пуши»: `serve_forever` к этому моменту уже вернулся и
  `accept()` никто не делает. Польза в том, что сокет перестаёт СЛУШАТЬ: непринятый
  слушающий сокет всё равно достраивает соединения в ядре и копит их в backlog, так
  что клиент, подключившийся во время остановки, отправляет пуш в соединение, которое
  выглядит установленным, и молча ждёт ответа до самого выхода процесса. Закрытый — он
  получает отказ сразу и ретраит на то, что поднимется следом.
  `submit` проверяет остановку и до, и после постановки в очередь: потоки запросов
  daemon-ные и переживают дренаж, так что иначе пушер получает 202 на задачу, которую
  никто не возьмёт. **Но «раз в очереди её нет — значит, я забрал её обратно» — вывод
  неверный:** задачу мог забрать ВОРКЕР и уже собирать по ней модель. Поэтому дренаж
  записывает id снятых задач, и `submit` отвечает отказом только по факту присутствия
  своей задачи в этом списке; иначе поток запроса не удалял бы дерево исходников
  из-под живой сборки. И два отказа `submit` различаются: «очередь полна» (задачу
  проваливает вызывающий, `Retry-After` есть) и «хаб останавливается» (задача уже
  отвечена — дренажом или самим `submit`, — `Retry-After` нет, перезаписывать её
  текстом про полную очередь нельзя).
- **Реестр лежит на томе, который сборке доступен на запись** (8A.4), и модуль этого
  не скрывает: см. §7.4 — приведение записи к известной схеме и потолки на размер,
  при чтении и при записи.

**Шаг 6. Гейт переезжает и меняет знак.** Сегодня он стоит ДО пуша, поэтому сломанная
модель просто не доезжает до хаба. Завтра он сработает ПОСЛЕ приёма запроса: значит
staging выбрасывается, `latest` и `dev` не двигаются, наружу уходит код ошибки с
логом. Механика staging плюс атомарный `rename` уже есть, и `PublishError` уже умеет
нести HTTP-статус.

**Шаг 7. Дать новую дорогу и убрать за собой — В ХАБЕ.** Переформулирован
2026-08-27, потому что прежняя редакция велела ходить в ЧУЖИЕ репозитории:
«удалить `publish.yml` в каждом репозитории модели, секреты в организации, пин
`cad_publish`». Это не работа хаба. Хаб даёт способ публиковаться; что после
этого сделают у себя одиннадцать репозиториев моделей, `cad_builder` и
`cad_publish` — их дело, и следующий агент не должен читать этот пункт как
задание туда идти.

**Что оказалось на деле, и почему шаг не был уборкой.** Публикация УЖЕ не
работала: с шага 5 хаб принимает дерево исходников и отвечает 202, а клиент
паковал плоскую сборку и ждал 201. Ни одна модель не пушила с тех пор, и связку
не проверял ни один тест — половины жили в разных репозиториях. Так что убирать
было нечего, а надо было построить дорогу заново.

**Сделано:**

- `src/client/` — команда `hammerola`, семь глаголов: `build`, `commit`,
  `login`, `create`, `status`, `comments`, `comments resolve`. Только stdlib.
  Живёт в ЭТОМ репозитории намеренно — контракт у клиента и хаба один, и
  расходится он молча, если обе половины не видит ни один тест (§7.7, §7.8;
  набор команд целиком — §8, запись 26);
- идентификатор ревизии — хеш её исходников, git ни при чём (§7.7);
- исходники и лог хранятся по ревизии, отдаются под секретом (§7.8);
- ретенции нет ни у сборок, ни у задач (§5.3, §7.3);
- вычищены утверждения, которые переезд сделал ложными: подпись
  `CadQuery → Gitea Actions` на главной, «`latest` — это из CI» в четырёх
  местах, «пакет никем не импортируется» в `src/cadbuild/__init__.py`.

**Осталось в хабе:** маршруты под `rename` и `rm`, которых нет; глаголы
`source`, `artifacts`, `diff`, `log <ревизия>` — хранилище под них появилось,
сами они не написаны; именованный маршрут публикации `<pid>/<commit>` живёт,
пока по нему кто-то пушит.

**Шаг 8. Сравнение ревизий.** Детали — в записи беклога «Сравнение двух ревизий».
К этому моменту у хаба есть и ядро, и исходники, и внепроцессное убийство зависшей
задачи из шага 4 — а оно там обязательно, потому что булева виснет так же, как
сборка, и на `ThreadingHTTPServer` зависшая операция навсегда занимает поток запроса.

**Раннер при этом не исчезает** — образ самого хаба кому-то надо собирать. «Форж
сбоку» относится к публикации моделей, а не к сборке образа.

### 8A.3 Открытые решения

- **Зависимости модели.** Рекомендуется запретить всё, кроме того, что в образе.
  Причина: установка sdist гарантированно исполняет код (даже `pip install --dry-run`
  запускает build-бэкенд), а wheel может положить `.pth`-файл, который исполняется при
  КАЖДОМ старте интерпретатора, без всякого импорта — именно так работали обе крупные
  атаки на PyPI в этом году. Флаг `--only-binary=:all:` не спасает, если путь к архиву
  или каталогу передан явно.
- **Версия ядра становится общей, и отстать нельзя.** `cadquery` пинит `cadquery-ocp`
  непересекающимися диапазонами: 2.7 требует `>=7.8.1,<7.9`, 2.8 — `>=7.9.3.1,<8.0`.
  Два проекта на разных `cadquery` физически не могут делить одно окружение, а полный
  venv на проект — порядка 1.5 ГБ, то есть по проекту не размножишь.
- ~~**Ретенция.**~~ **Закрыто решением 2026-08-27: ретенции нет** (§5.3, §7.3) — вопрос
  снят решением, а не расчётом, и переоткрывать его не надо. Замер, ради которого он
  стоял, при этом остаётся полезным и превращается в вопрос про ОБЪЁМ ТОМА: считать надо
  по РАСПАКОВАННОМУ объёму и по числу видов — §5.3 говорит «примерно 2 МБ на вид», а
  0.31 МБ из §2.3 это gzip одного вида, то есть трафик, а не диск. Сто сборок — сотни
  мегабайт, а не 31, и теперь они не уходят никуда сами. Кэш диффов вне каталога сборки
  всё равно нужен, но уже не потому, что «ретенция съест половину пары» (§8, «Сравнение
  двух ревизий»), а из-за прав и годового `immutable`.

### 8A.4 Чего не делать никогда

Проверено по источникам, чтобы не возвращаться:

- **docker-сокет хабу или билдеру** в любом виде, включая socket-proxy: дать доступ к
  сокету равносильно неограниченному root на хосте, а прокси не инспектирует тело
  запроса, поэтому `Binds` и `Privileged` проходят насквозь;
- **docker-in-docker и `privileged: true`** — снимает seccomp, AppArmor, все
  capabilities и маскировку `/proc`;
- **`exec()` модели в процессе хаба** — рядом с токенами и томом;
- **RestrictedPython, audit hooks и любой in-process барьер.** Авторы всех трёх сами
  пишут, что это не песочница; для нативного OCP это неприменимо в принципе, потому
  что придётся разрешить импорт модуля с прямым доступом к памяти процесса;
- **nsjail и bubblewrap внутри Docker** — цена входа `CAP_SYS_ADMIN` плюс
  `seccomp=unconfined`, то есть размен сильного внешнего слоя на слабый внутренний;
- **`userns-remap`** — настройка уровня демона, маскирует существующие слои образов;
  на живом хосте это пересоздание хоста.

## 9. Ограничения

- Снапшот, а не конфигуратор: параметры в браузере не крутятся. Интерактивная
  параметризация — это `parametric_configurator`, отдельный проект.
- Только код-CAD (CadQuery). Модель из Fusion CI пересобрать не может; для неё путь —
  коммитить экспортированный STEP, и это отдельная ветка работы, сейчас не покрытая.
- Аутентификации на чтение нет и не планируется (5.4).
- Хаб не удаляет ничего сам: ретенции нет, том растёт монотонно, и разгребать его,
  когда он однажды кончится, придётся руками (5.3, 7.3).
